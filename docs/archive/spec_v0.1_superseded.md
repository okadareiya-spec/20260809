# 会議室予約 LINE Bot 要件定義・技術仕様書

- 版数: 0.1（作成中）
- 作成日: 2026-08-08
- 読み手: 実装者（feature-dev / Claude Code）
- 運用形態: 自社運用

---

## 1. 概要とスコープ

### 1.1 目的

社内の会議室12室について、**社員が LINE 上で予約・確認・変更・キャンセルを完結できる**状態をつくる。予約データは Google スプレッドシートに保持し、**管理者はそのスプレッドシートを管理画面として運用する**。

専任の管理担当を置かず、月額の固定費を発生させないことを前提条件とする。

### 1.2 対象範囲

- LINE 公式アカウントを通じた、社員向けの予約・確認・変更・キャンセル機能
- 会議室の空き状況照会
- スプレッドシートによる予約データの保持と、管理者による直接運用
- 部屋・営業時間・定例枠・臨時ブロック・予約ルールの、管理者による設定
- 新規予約が入った際の管理者への通知
- 管理者が他人の予約を操作した際の、当該ユーザーへの通知

### 1.3 やらないこと（スコープ外）

**以下は意図的に実装しない。** 本文に記載がないことを理由に、実装者が補って作ってはならない。

| 実装しないもの | 理由 |
|---|---|
| リマインダー通知（前日・当日の自動通知） | 第1版のスコープ外。LINE の push 通知は無料枠を消費するため、採用時はプラン検討を伴う |
| 繰り返し予約（毎週◯曜など） | 実装量が提供価値に見合わない。定例枠は管理者のブロック設定で代替する |
| 予約の承認フロー | 予約は即時確定とする |
| 利用実績レポート・稼働率の集計 | 第1版のスコープ外。データは後から集計可能な形で蓄積する |
| 空予約（押さえたまま使わない）の検知・抑止 | 現在の運用課題として顕在化していない |
| 管理者向けの LINE インターフェース | 管理者の操作手段はスプレッドシートのみとする |
| 部屋の用途制限（例：大会議室は少人数利用を禁止） | 第1版では不要 |
| LIFF による Web フォーム | UI は LINE 内の会話形式で完結させる |
| 飛び込み利用のための予約枠の取り置き | 第1版では注意書きのみとし、必要性は運用で確認する |
| 予約と予約の間のバッファ時間 | 第1版では設けない。将来の拡張余地は残す |
| 外部カレンダー（Google カレンダー等）との連携 | 対象外 |
| 多言語対応 | 日本語のみとする |
| 決済・課金 | 対象外 |
| 1人あたりの予約数上限、キャンセルのペナルティ | 設けない |

## 2. 用語定義

本仕様書における用語は以下の意味で用いる。**解釈が割れやすい語を意図的に集めている。**

| 用語 | 定義 |
|---|---|
| ユーザー | 会議室を利用する社員。LINE 公式アカウントを友だち追加した者 |
| 管理者 | 会議室の運用を担う社員。複数名・兼任であり、**操作手段はスプレッドシートのみ** |
| 部屋 | 予約の対象となる会議室・ブース。本仕様における唯一のリソース単位 |
| 定員 | 部屋が収容できる人数。**空欄は「制限なし」を意味する**（大会議室が該当） |
| 枠 | 30分刻みで区切られた時間の単位。1件の予約は、連続する1つ以上の枠を占める |
| 営業時間 | **会社全体**の稼働帯。曜日ごとに稼働日か否かと開始・終了時刻を持つ |
| 部屋別予約可能時間 | **部屋ごと・曜日ごと**の予約可能な区間。営業時間との論理積（狭い方）が有効範囲となる。1つの曜日に複数の区間を持てる |
| 定例枠 | 定例会議などで恒常的に使用され、予約できない時間帯。**データとしての実体を持たず、部屋別予約可能時間の区間と区間の隙間として表現される** |
| 臨時ブロック | 工事・貸切など、特定の日付を指定して予約不可にする設定 |
| 受付締切 | 予約・変更・キャンセルを受け付ける限界。開始時刻の何分前かで指定する（既定は60分前） |
| 事前予約 | リッチメニューの「予約する」から行う通常の予約。受付締切が適用される |
| 飛び込み利用 | リッチメニューの「今すぐ使う」から行う即時予約。**個人ブース・1名に固定され、受付締切は適用されない** |
| 指名 | ユーザーが部屋を明示的に選んで予約すること |
| おまかせ割当 | 部屋を指定せず、システムが自動で部屋を決めること。人数を収容できる空室のうち定員が最小の部屋が選ばれる |
| 予約名 | 会議の名称。ユーザーの任意入力。未入力時は「〈氏名〉の予約」が自動生成される |
| 確定 | 予約が成立している状態。承認フローがないため、予約はすべて即時にこの状態になる |
| キャンセル | 予約が取り消された状態。**行は削除せず、状態列の値で表現する** |
| 代理予約 | 管理者がスプレッドシートに直接行を追加して登録する予約。登録元が `管理者` となる |
| 設定シート | 予約ルールの数値を保持するシート。管理者が値を書き換えることでルールが変わる |
| 応答メッセージ（reply） | ユーザーの発言に対する返信。無料・無制限だが、発言者本人にしか送れない |
| プッシュ通知（push） | システム側から任意のユーザーへ送るメッセージ。無料枠に上限がある |

## 3. 利用者要件（ユーザー）

ユーザーとは、会議室を利用する社員を指す。LINE 公式アカウントを友だち追加した者が対象。

### 3.1 ユーザーのゴール

**上位ゴール** — 使いたい会議室を LINE 上の数タップで確実に押さえ、予定が変わったら自分で手放せる。

| ID | ゴール | 満たされている状態 |
|---|---|---|
| G-U1 | 最小手数で予約を完了できる | 新規予約が、日付選択から確定まで一本道で完了する |
| G-U2 | LINE だけで完結する | ブラウザ・PC・他の社内システムを開かずに、予約・確認・変更・キャンセルができる |
| G-U3 | 初回から説明なしで使える | マニュアルを読まずに、最初の予約を完了できる |
| G-U4 | 今すぐ使える席を即座に確保できる | 日付・時刻を入力せず、数タップで個人ブースを押さえられる（複数名の当日利用は対象外。下記の制約を参照） |
| G-U5 | 人数に合った部屋を選べる | 利用人数を伝えるだけで、収容可能な部屋だけが提示される |
| G-U6 | 再入力が不要 | 2回目以降、氏名とメールアドレスの入力を求められない |
| G-U7 | 自分の予約を確認できる | いつ・どの部屋を・何時から押さえているかを、いつでも参照できる |
| G-U8 | 自分で変更・キャンセルできる | 管理者に依頼せず、自分の予約を変更・取り消しできる |
| G-U9 | 希望が埋まっていても代替が分かる | 希望の部屋が埋まっている場合、同じ時間帯で空いている他の部屋が提示される |
| G-U10 | 予約者が分かり交渉できる | 埋まっている枠について、予約者の氏名と予約名を確認できる |
| G-U11 | 二重予約が起きない | 同じ部屋・同じ時間帯に2件の予約が成立することがない |

**意図的に持たせないゴール**（実装者はこれらを満たそうとしないこと）

| 除外したゴール | 理由 |
|---|---|
| 使わなくなった枠を手放しやすくする | 空予約は現在の運用課題ではないため（管理者ゴールA8と対で除外） |
| 予約を忘れない（リマインド通知） | 第1版のスコープ外。LINE の push 通知は無料枠を消費するため、採用時は別途プラン検討が必要 |
| 定例会議を毎回入力しなくて済む（繰り返し予約） | 管理者が定例枠をブロックする運用（G-A4）で代替する |
| 希望時間帯が埋まっているとき別の時間帯を提案する | 実装量が提供価値に見合わないため。別の「部屋」の提示（G-U9）のみ行う |

### 3.2 想定利用シーン

| シーン | 内容 | 主に関係するゴール |
|---|---|---|
| S-1 計画予約 | 数日〜数週間先の会議のために部屋を押さえる | G-U1, G-U5 |
| S-2 飛び込み利用 | 集中作業や急な通話のため、今すぐ使える個人ブースを押さえる | G-U4 |
| S-3 予定変更 | 会議の日時がずれた、または中止になった | G-U7, G-U8 |
| S-4 空き確認のみ | 予約はせず、特定の日時に空きがあるかだけ調べる | G-U9, G-U10 |
| S-5 交渉 | 使いたい枠が埋まっているため、予約者に直接掛け合う | G-U10 |

S-2 は会議室予約に固有かつ頻度が高い。日付・時刻の入力を要求せず「今から使える席」に到達できる導線を、会話フロー仕様（6章）で必ず用意すること。

**既知の制約 — 当日直前の複数名利用に手段がない。** 事前予約は受付締切（開始1時間前）で弾かれ、飛び込み利用は個人ブース1名に固定されている。したがって「今から3名で30分だけ会議したい」という要求は、本システムでは満たせない。複数名での利用は事前に予約する運用を前提としているため、これは仕様どおりの挙動である。実装者はこの穴を独自の判断で埋めようとしないこと。

### 3.3 ユーザーができること／できないこと

**できること**

- 日付・開始時刻・利用時間・人数を指定して予約する
- 部屋を指名して予約する、または部屋を指定せず自動割当で予約する
- 指定した日時の空き状況を照会する（予約せずに参照のみも可）
- 自分の予約の一覧と詳細を確認する
- 自分の予約の日時・部屋・予約名・備考・人数を変更する
- 自分の予約をキャンセルする
- 他人の予約について、予約者の氏名・予約名・時間帯・部屋を参照する

**できないこと**

- 他人の予約を変更・キャンセルする
- 予約可能時間外、稼働日外、ブロックされた枠を予約する
- 60日より先の予約
- 開始時刻の1時間前を過ぎた**事前予約**・変更・キャンセル（**飛び込み利用は締切の適用外**。6.2参照）
- 日付をまたぐ予約
- 30分未満、または30分刻みでない時間の予約
- リソース（部屋）の追加・変更・削除
- 営業時間、稼働日、ブロック枠の設定

他人の予約を操作できない以上、変更が必要な場合の導線は **予約者本人への直接交渉、または管理者へのエスカレーション** の2つしかない。前者を成立させるために予約者名の表示（G-U10）が必須である。

### 3.4 達成基準

以下を全て満たしたとき、利用者要件を満たしたと判断する。

1. LINE の友だち追加以外の初期設定なしに、初回の予約が完了できる
2. 予約・確認・変更・キャンセルの全操作が、LINE アプリ内で完結する
3. 利用人数を入力すると、その人数を収容できない部屋は選択肢に現れない
4. 2回目以降の予約で、氏名およびメールアドレスの入力を求められない
5. 日時を入力せずに、今から利用可能な個人ブースを3タップ以内で押さえられる
6. 他人の予約に対して、変更・キャンセルの操作導線が一切存在しない
7. 空き状況照会において、埋まっている枠には予約者の氏名と予約名が表示される
8. 同一の部屋・同一の時間帯に、重複した予約が成立しない

## 4. 運用者要件（管理者）

管理者とは、会議室の運用を担う社員を指す。以下の前提が本セクション全体の制約となる。

- **複数名いる**（専任担当者はいない）
- **兼任である** — 会議室運用は本来業務ではなく、操作の頻度は低い
- **操作手段はスプレッドシートのみ** — 管理者は LINE Bot を一切操作しない

3点目が最も強い制約である。**管理者向けの LINE インターフェースは実装しない。スプレッドシートが管理画面そのものである。** 管理者が行う全ての操作は、シート上のセル編集として表現できなければならない。

2点目からは別の要件が導かれる。兼任で操作頻度が低いということは、**前回の操作方法を覚えていない状態で操作する**ということである。シートは、手順書を参照せずとも列の意味と入力方法が分かる状態に保つ必要がある。

### 4.1 管理者のゴール

**上位ゴール** — 専任担当を置かず、スプレッドシートを触るだけで会議室運用を回し続けられる。

| ID | ゴール | 満たされている状態 |
|---|---|---|
| G-A1 | 稼働状況を集計作業なしで把握できる | シートを開けば、どの部屋がいつ埋まっているかが一目で分かる |
| G-A2 | 営業時間・稼働日を自分で変更できる | 実装者に依頼せず、シート上の設定変更だけで反映される |
| G-A3 | 部屋の増減・名称変更に自分で追従できる | 部屋の追加・削除・改名・定員変更が、シートへの行追加や書き換えで完結する |
| G-A4 | 定例枠・臨時の使用不可を自分で設定できる | 毎週の定例枠と、特定日だけの使用不可を、どちらも自分で塞げる |
| G-A5 | 例外対応を自分の手でできる | 代理予約・強制キャンセル・部屋の付け替えを、シート上で実行できる |
| G-A6 | 問い合わせ対応の負荷が下がる | ユーザーが自力で予約・変更・キャンセルを完結し、管理者への依頼が発生しない |
| G-A7 | トラブル時に事実を確認できる | 誰がいつ何を予約・変更・削除したかを、後から追跡できる |
| G-A8 | 新規予約をリアルタイムに把握できる | 予約が入った時点で通知を受け取れる |
| G-A9 | システムが止まっても運用を継続できる | Bot が動かなくなっても、シートを見れば当日の予約状況が分かる |
| G-A10 | 運用コストをゼロに保つ | 月額の固定費が発生しない |
| G-A11 | 個人情報を適切に管理できる | 保持している個人情報の範囲が明確で、削除の手段がある |

**意図的に持たせないゴール**

| 除外したゴール | 理由 |
|---|---|
| 空予約（押さえたまま使わない）を減らす | 現在の運用課題として顕在化していないため |
| 会議室が足りているかを判断する（利用実績レポート） | 第1版のスコープ外。ただし後から集計できるよう、データ設計では実績を欠損なく蓄積する（7章） |
| 部屋を用途で制限する（例：大会議室は少人数利用を禁止） | 第1版では不要。人数を取得するため、将来的には実装可能 |

### 4.2 管理者の担当業務

| 頻度 | 業務 | 関係するゴール |
|---|---|---|
| 随時（通知契機） | 新規予約の通知を受け取り、必要に応じて内容を確認する | G-A8 |
| 随時（依頼契機） | 代理予約を登録する（LINE を使わない利用者、外部来訪者向けなど） | G-A5 |
| 随時（依頼契機） | 予約の強制キャンセル、部屋の付け替えを行う | G-A5 |
| 週次〜月次 | 定例枠のブロックを設定・見直す | G-A4 |
| 随時 | 臨時の使用不可（工事・貸切など）を特定日に設定する | G-A4 |
| 稀 | 部屋の追加・削除・改名・定員変更を行う | G-A3 |
| 稀 | 営業時間・稼働日を変更する | G-A2 |
| 稀 | トラブル発生時に操作履歴を確認する | G-A7 |

### 4.3 管理者ができること／できないこと

**できること（すべてスプレッドシート上の操作）**

- 予約を直接追加する（代理予約）
- 既存の予約を直接編集する（日時・部屋・予約名・人数・備考の変更）
- 既存の予約を直接キャンセルする（他人の予約を含む）
- 部屋を追加・削除・改名し、定員を変更する
- 部屋ごとの予約可能時間を、曜日単位で設定する
- 特定日を指定して枠をブロックする（臨時の使用不可）
- 営業時間・稼働日を変更する
- 予約の操作履歴を参照する
- 予約ルールの数値を変更する（受付締切、予約可能な日数、時間の刻み、最短予約時間、人数入力の初期値、管理者の通知先）

**できないこと**

- LINE Bot 経由での管理操作（管理者向けの LINE インターフェースは存在しない）
- Bot のメッセージ文面や会話フローそのものの変更
- ユーザーの LINE アカウントの管理

**設定値の扱い**

予約ルールの数値は、コード内に定数として埋め込まず、**設定シート上のセルとして保持する**。Bot は判定のたびにその値を読む。管理者はセルを書き換えるだけでルールを変更でき、実装者を介する必要がない。

管理者が誤った値（空欄、0以下、数値以外）を入力する可能性があるため、**不正な値を検出した場合は既定値で動作を継続し、警告を残す**。設定ミスでシステム全体が停止する状態にはしない。

**管理者の直接編集をどう扱うか**

管理者がシートに書いた内容は **正として受け入れる**。重複予約や予約可能時間外といった、通常なら弾かれる内容であっても拒否しない。管理者は例外対応のために意図してそれを行っているためである。

ただし黙って受け入れるのではなく、**異常を検知した行には警告を表示する**。管理者が意図した例外なのか、単純な入力ミスなのかは、管理者本人にしか判断できない。システムの役割は判断ではなく、気づかせることである。

**管理者が他人の予約を変更・キャンセルした場合、対象ユーザーへ LINE で通知する。** 強制キャンセルや部屋の付け替えは、当人が知らないままでは会議に支障が出る。これは push 通知となり無料枠を消費するが、例外対応に限られるため件数は少ない。

### 4.4 達成基準

以下を全て満たしたとき、運用者要件を満たしたと判断する。

1. 管理者が行う全ての運用操作が、スプレッドシート上のセル編集だけで実行できる
2. 管理者向けの LINE インターフェースが存在しない
3. 部屋を1室追加する操作が、行を1行追加するだけで完了し、追加後ただちに予約対象になる
4. 営業時間・稼働日・曜日別の予約可能時間・臨時ブロックが、いずれもシート上の設定で変更できる
5. 受付締切・予約可能な日数・時間の刻みなどの予約ルールが、設定シート上の値で変更できる
6. 設定シートに不正な値が入力された場合も Bot は停止せず、既定値で動作を継続し警告を残す
7. 管理者がシート上で追加・編集・削除した予約が、Bot 側の空き判定に反映される
8. 管理者の編集によって重複予約や設定外の予約が生じた場合、当該行に警告が表示される
9. 管理者が他人の予約を変更・キャンセルした場合、対象ユーザーに LINE で通知が届く
10. 予約が新規に登録された際、管理者に通知が届く
11. 予約の作成・変更・削除について、実施者と日時が記録され後から参照できる
12. 月額の固定費が発生しない
13. Bot が停止していても、シートを開けば当日の予約状況が判読できる

## 5. 業務ルール

### 5.1 リソース定義

会議室は全12室。1室を1行として、部屋マスタに定義する。

| 種別 | 室数 | 定員 |
|---|---|---|
| 大会議室 | 1 | 制限なし |
| 12人部屋 | 2 | 12 |
| 6人部屋 | 5 | 6 |
| 個人ブース | 4 | 1 |

**部屋が持つ属性**

| 属性 | 内容 | 変更 |
|---|---|---|
| 部屋ID | 部屋を一意に識別する不変の値。予約データはこれを参照する | 不可 |
| 部屋名 | ユーザーに表示される名称 | 可 |
| 定員 | 収容可能な人数。割当判定に使う。**空欄は「制限なし」を意味する** | 可 |
| 表示順 | 選択肢に並べる順序。同定員時の割当順序も兼ねる | 可 |
| 有効フラグ | 新規予約の対象とするか | 可 |

**部屋IDと部屋名を分ける理由** — 部屋を改名しても、過去の予約との結びつきが切れないようにするため。予約データが部屋名を直接持つと、改名した瞬間に過去の予約がどの部屋のものか分からなくなる。

**定員なしの表現** — 大会議室は定員を設けない。部屋マスタの定員列を **空欄にした場合を「制限なし」と定義する**。判定処理では、定員なしの部屋は収容可能人数を無限大として扱う。したがって、どれだけ大きな人数を入力しても大会議室は常に候補に含まれ、おまかせ割当では常に最後に選ばれる。

**部屋の削除は行わず、無効化で表現する。** 過去の予約が部屋IDを参照しているため、行を物理削除すると履歴が壊れる。無効化された部屋は新規予約の選択肢に現れないが、既存の予約はそのまま残り、参照もできる。

### 5.2 予約可能時間の設定

予約できる時間帯は、3つの階層の設定から決まる。

| 階層 | 設定単位 | 用途 |
|---|---|---|
| 全体の稼働日・営業時間 | 曜日 | 会社全体の休業日と営業帯 |
| 部屋別の予約可能時間 | 部屋 × 曜日 | 部屋ごとの利用可能帯。**定例枠はここで塞ぐ** |
| 臨時ブロック | 部屋 × 日付 × 時間帯 | 工事・貸切など単発の使用不可 |

**ある枠が予約可能である条件** — 以下をすべて満たす場合のみ予約できる。

1. 全体の稼働日であり、営業時間内である
2. その部屋の、その曜日の予約可能時間内である
3. 臨時ブロックに該当しない
4. 既存の予約と重複しない
5. 受付期間内である（5.3参照）

設定が競合した場合は **狭い方を採用する**（AND条件）。部屋別の予約可能時間が全体の営業時間より広く設定されていても、営業時間外は予約できない。

**部屋別の予約可能時間は、1つの曜日に複数の区間を持てなければならない。** 定例枠を塞ぐには、これが必須となる。例えば大会議室が毎週火曜の10:00-12:00に定例会議で使われる場合、大会議室の火曜の予約可能時間を `9:00-10:00` と `12:00-18:00` の2区間として登録する。この2区間の隙間が定例枠であり、そこは予約できない。1曜日1区間しか持てない構造では定例枠を表現できない。

### 5.3 受付・変更・キャンセルのルール

| 項目 | 値 | 設定シートで変更 |
|---|---|---|
| 予約可能な期間 | 本日から60日先まで | 可 |
| 受付締切 | 開始時刻の1時間前まで | 可 |
| 時間の刻み | 30分 | 可 |
| 最短予約時間 | 30分 | 可 |
| 最長予約時間 | 開始時刻からその日の営業終了まで（実質的に終日予約が可能） | — |
| 日跨ぎ予約 | 不可 | — |
| 1人あたりの同時保有数 | 上限なし | — |
| キャンセルペナルティ | なし | — |

受付締切は **新規・変更・キャンセルに共通で適用する**。開始1時間前を過ぎた予約は、ユーザーは取り消せない（管理者はシート上で操作できる）。

**変更の扱い** — 変更は「キャンセル＋新規予約」ではなく、**同一の予約IDを保持したまま内容を更新する**。予約IDが変わると、変更前後の履歴が別物として記録され、追跡できなくなるためである。変更内容は操作履歴に記録する。

**変更時の空き判定における注意** — 予約の時間や部屋を変更する際、変更後の枠が空いているかを判定するが、**このとき変更対象の予約自身を「埋まっている予約」として数えてはならない**。

例えば 10:00-11:00 の予約を 10:00-12:00 に延長する場合、10:00-11:00 の枠は変更対象の予約自身が占めている。これを重複とみなすと、その予約は永久に変更できなくなる。空き判定の対象から、変更対象の予約IDを必ず除外すること。

### 5.4 部屋の割当ルール

**本節は事前予約フロー（6.1）にのみ適用する。** 飛び込み利用（6.2）は人数1名・個人ブース固定であり、以下の割当ルールは適用しない。

ユーザーは予約時に、部屋を **指名する** か **おまかせにする** かを選べる。いずれの場合も利用人数の入力を必須とし、入力欄の初期値は6名とする。

**指名の場合** — ユーザーが部屋を選ぶ。ただし **入力人数を収容できない部屋は選択肢に表示しない**。6名で検索したユーザーに個人ブースを見せない、ということである。

**おまかせの場合** — 入力人数を収容でき、かつ空いている部屋のうち、**定員が最小の部屋**を自動で割り当てる。個人ブース → 6人部屋 → 12人部屋 → 大会議室 の順に埋まるため、大きい部屋が少人数に占有されて後続の大人数予約が入らなくなる事態を防げる。

**定員が同じ部屋が複数空いている場合**は、部屋マスタの **表示順が最も若い部屋** を選ぶ。順序を明示しないと実装ごとに挙動が変わり、再現性のない割当になるため、ここは必ず表示順で決定すること。

**収容可能な部屋がすべて埋まっている場合**、割り当てられる部屋は存在しない。この場合は予約を受け付けず、その旨を伝える。

**この場面で代替の部屋を提示してはならない。** 収容可能な部屋がすべて埋まっている以上、残っているのは入力人数が入らない部屋だけであり、提示しても予約できないためである。

G-U9（希望が埋まっていても代替が分かる）は、**部屋選択の場面（6.1 S5）で満たされる。** そこには収容可能な空室が一覧表示されるため、特定の部屋を使いたかったユーザーは、その場で他の空き部屋を確認できる。

なお大会議室に定員がないため、**「人数が大きすぎて収容できる部屋が存在しない」というケースは発生しない**。どれだけ大きな人数を入力しても、大会議室が空いてさえいれば必ず割り当てられる。

## 6. 会話フロー仕様

### 6.0 共通事項

**入口はリッチメニュー**とし、以下の4つを配置する。

| ボタン | 遷移先 | 対応するゴール |
|---|---|---|
| 予約する | 6.1 新規予約 | G-U1, G-U5 |
| 今すぐ使う | 6.2 飛び込み利用 | G-U4 |
| 予約の確認 | 6.3 予約確認 | G-U7, G-U8 |
| 空き状況 | 6.5 空き状況照会 | G-U9, G-U10 |

**ユーザーの入力手段は原則ボタン（postback）とする。** キーボード入力を求めるのは、予約名・氏名・メールアドレス・人数の直接指定の4箇所のみ。自由入力を増やすほど表記ゆれと入力エラーの処理が増え、G-U3（説明なしで使える）から遠ざかるためである。

**選択肢の上限に注意すること。** クイックリプライは13件、カルーセルテンプレートは10件、Flex Message のカルーセルは12件が上限である。営業時間が9:00-18:00なら開始時刻の候補は18件あり、クイックリプライでは表示しきれない。**時刻の選択と部屋の一覧は、縦に伸ばせる単一の Flex Message で構成する**こと。

### 6.1 新規予約フロー

| # | Bot が提示するもの | ユーザーの操作 | 実装上の注意 |
|---|---|---|---|
| S1 | 日付選択（datetimepicker、mode=date） | カレンダーから日付を選ぶ | 選択可能範囲を「本日〜60日後」に制限する（min/max を指定し、範囲外を選べなくする） |
| S2 | 開始時刻の一覧（Flex） | 時刻を選ぶ | **1室でも空きがある時刻のみ表示する。** 全室が埋まっている時刻、営業時間外、稼働日外は最初から出さない |
| S3 | 利用時間の選択肢 | 時間を選ぶ | `30分／1時間／1時間30分／2時間／3時間／営業終了まで`。**選択済みの開始時刻から確保できない長さは表示しない**（17:30開始で18:00終業なら30分のみ）。**「営業終了まで」は、選択した開始時刻からその日の営業終了時刻までを指す**（「終日」ではない。開始時刻を選んだ後に一日全体を指定することは論理的にできないため、この呼称を用いる） |
| S4 | 人数の選択肢 | 人数を選ぶ | `1名／2名／4名／6名／12名／人数を入力`。**6名を既定として視覚的に強調する** |
| S5 | おまかせ＋空き部屋の一覧 | 部屋または「おまかせ」を選ぶ | **入力人数を収容できる部屋のみ**を定員の昇順で表示する。おまかせを選んだ場合は5.4の規則で自動決定する |
| S6 | 予約名の入力依頼 | テキスト入力、または「入力せずに進む」 | 未入力時は「〈氏名〉の予約」を自動生成する |
| S7 | 氏名 → メールアドレスの入力依頼 | テキスト入力 | **初回利用時のみ。** 2回目以降は顧客マスタから補完し、この手順を丸ごと飛ばす（G-U6） |
| S8 | 予約内容の確認 | 「確定する」または「やり直す」 | **確定時に空き状況を再判定する**（6.7参照） |

### 6.2 飛び込み利用フロー（今すぐ使う）

飛び込み利用は **個人ブース専用** とする。複数名での利用は事前予約に誘導する。

| # | Bot が提示するもの | ユーザーの操作 |
|---|---|---|
| S1 | 案内文＋利用時間の選択肢 | `30分／1時間／2時間` から選ぶ |
| S2 | 割り当てられた個人ブースと利用時間の確認 | 「確定する」 |

**最短3タップで完了する。** このルートには以下の特則を適用する。

- **受付締切（開始1時間前）を適用しない。** 締切をそのまま適用すると、1時間以内に始まる予約が全て弾かれ、飛び込み利用が構造的に成立しなくなるためである。
- **開始時刻は、現在時刻を含む30分枠の先頭とする。** 10:17に操作した場合、10:00-11:00の枠を押さえる。切り上げて10:30開始とすると13分待つことになり「今すぐ」でなくなるため、切り下げを採用する。予約枠が30分刻みで一貫する利点もある。
- **人数は1名固定、部屋は個人ブースに固定する。** 人数と部屋の選択手順は設けない。
- 個人ブースが複数空いている場合は、部屋マスタの表示順が最も若い部屋を割り当てる。

**S1の案内文で、個人ブースが割り当てられる旨を必ず明示すること。** ユーザーが会議室を期待して操作した場合に、意図しない部屋を押さえてしまうのを防ぐ。

**個人ブースが4室とも埋まっている場合**は、満室である旨を伝え、**事前予約フロー（6.1）への導線ボタンを提示する**。他の部屋をその場で提示することはしない（飛び込み＝個人ブース固定という規則を保つため）。

なお個人ブースは事前予約でも予約でき、1名で予約すると自動割当で個人ブースが選ばれる。したがって **飛び込み用の取り置きは行わない**。第1版では満室が頻発するかどうかを運用で確認する方針とし、取り置きの仕組みは実装しない。

### 6.3 予約確認フロー

「予約の確認」を選ぶと、**自分の予約のみ**を開始日時の昇順で一覧表示する。**開始時刻が現在時刻以降**の予約を対象とし、既に開始した予約と過去の予約は表示しない。

各予約には「変更」「キャンセル」のボタンを添える。**受付締切を過ぎた予約についてもボタンは表示し、押された時点で操作できない理由を返す。** ボタンを非表示にすると、ユーザーには「なぜ操作できないのか」が分からず、管理者への問い合わせを誘発するためである（G-A6に反する）。

### 6.4 変更・キャンセルフロー

**変更** — 何を変えるかを最初に選ばせる（`日時／部屋／人数／予約名・備考`）。日時または部屋を変更する場合は、6.1のS1以降と同じ手順を再利用する。

変更処理では、**空き判定の対象から変更対象の予約自身を必ず除外する**（5.3参照）。除外を忘れると、時間を延長する変更が常に「重複」と判定され、永久に変更できなくなる。

**キャンセル** — 誤操作を防ぐため、確認を1回挟む。確認画面には予約内容（日時・部屋・予約名）を再掲する。

**他人の予約に対しては、変更・キャンセルのボタンを一切表示しない**（3.3）。予約者本人以外が操作導線に到達できないこと。

### 6.5 空き状況照会フロー

予約せずに空き状況だけを確認する導線（S-4）。日付 → 開始時刻の順に選ばせ、**その時刻における全12室の状況を縦のリストで表示する**。

12室 × 18時間帯の全体表をスマートフォンで表示しても判読できないため、**時刻で絞ってから部屋を縦に並べる**構成とする。

埋まっている部屋には、**予約者の氏名と予約名を表示する**（G-U10）。これは他人の予約を操作できない仕様（3.3）の下で、ユーザーが予約者に直接交渉するために必要な情報である。

このビューは G-U9（希望の部屋が埋まっているときに他の空き部屋が分かる）も兼ねる。

### 6.6 postback データ設計

**状態はサーバー側に持たず、postback データに載せて持ち回る（ステートレス方式）。**

LINE の postback データは最大300文字を格納できる。本フローで持ち回る情報（日付・時刻・利用時間・人数・部屋ID・予約ID）は、この範囲に十分収まる。セッションの生成・失効・破棄といった状態管理を丸ごと省けるため、実装量と不具合の余地が大きく減る。

**形式** — `キー=値` を `&` で連結する。

| キー | 意味 | 例 |
|---|---|---|
| `a` | 操作の種別 | `new` / `now` / `list` / `edit` / `cancel` / `avail` |
| `s` | フロー内の手順 | `date` / `time` / `dur` / `num` / `room` / `confirm` |
| `d` | 日付 | `20260810` |
| `t` | 開始時刻 | `1000` |
| `dur` | 利用時間（分） | `60` |
| `n` | 人数 | `6` |
| `r` | 部屋ID | `ROOM03`、おまかせは `AUTO` |
| `id` | 予約ID | `RSV00123` |

例：`a=new&s=room&d=20260810&t=1000&dur=60&n=6`

**例外はテキスト入力の手順である。** 予約名・氏名・メールアドレス・人数の直接入力は通常のテキストメッセージとして届き、postback データを伴わない。そのため **「次に届くテキストが何の入力か」だけは、ユーザー単位でサーバー側に一時保持する必要がある**。保持するのは入力待ちの種別と、それまでに確定した予約内容のみとする。

### 6.7 例外・エラー時の分岐

| 状況 | 挙動 |
|---|---|
| 確定時に、選択した枠が他者に取られていた | 確定処理の直前に空き状況を再判定し、失われていた場合は取得できなかった旨を伝えて時刻選択（S2）に戻す |
| 受付締切を過ぎている | 締切を過ぎているため操作できない旨と、締切の条件を伝える |
| 60日より先の日付が指定された | 予約可能な範囲を伝える。原則として S1 の選択範囲制限で発生しない |
| 収容可能な部屋がすべて埋まっている | 空きがない旨を伝え、空き状況照会（6.5）への導線を出す |
| 他人の予約IDに対する変更・キャンセル要求 | 操作できない旨を伝える。正常な導線からは到達しない |
| 想定外・解釈不能な入力 | 現在の手順を再提示する。無言で無視しない |

**古いメッセージのボタンが押される問題に必ず対処すること。** LINE では過去のメッセージのボタンがいつまでも押せる状態で残る。数日前の「この内容で確定する」ボタンを今押されても矛盾なく処理できなければならない。

対処は2段構えとする。第一に、**確定処理では postback データの内容を信用せず、必ずその時点の空き状況・締切・設定値を再判定する**。第二に、**既に過去となった日時への操作は、締切超過として拒否する**。ステートレス方式（6.6）はセッション失効による防御が効かないため、この再判定が唯一の防御線となる。

### 6.8 メッセージ文面の方針

具体的な文面は実装時に定めるが、以下を満たすこと。

- **次に何をすればよいかが、常に1文で分かること。** 初回利用者がマニュアルなしで完了できる状態（G-U3）を維持する。
- **エラーは理由と次の行動をセットで伝えること。** 「予約できません」だけで終えない。締切超過なら締切の条件を、満室なら次に取れる手段を示す。
- **確定時は予約内容を全項目再掲すること**（日付・時刻・利用時間・部屋・人数・予約名）。
- 飛び込み利用の入口では、**個人ブースが割り当てられることを明示すること**（6.2）。

## 7. データ設計（スプレッドシート）

**このスプレッドシートは、管理者にとっての管理画面そのものである**（4章）。データの入れ物としてだけでなく、兼任の管理者が手順書なしで読み書きできる状態を設計目標とする。列の意味が名前から分かること、どこを触ればよいかが明らかであることを、正規化やデータ量の効率より優先する。

### 7.1 シート構成

| シート名 | 役割 | 管理者の操作頻度 |
|---|---|---|
| 予約 | 予約の台帳。全ての予約を1行1件で保持する | 随時 |
| 部屋マスタ | 部屋の定義（5.1） | 稀 |
| 部屋別予約可能時間 | 部屋 × 曜日の予約可能な区間。定例枠はここで塞ぐ | 週次〜月次 |
| 臨時ブロック | 特定日の使用不可（工事・貸切など） | 随時 |
| 営業時間 | 全体の稼働日と営業帯（曜日別） | 稀 |
| 顧客マスタ | LINE userId と氏名・メールアドレスの対応 | 原則不要 |
| 操作履歴 | 予約の作成・変更・削除の記録 | 参照のみ |
| 設定 | 予約ルールの数値（4.3） | 稀 |

### 7.2 列定義

**日付・時刻の保持形式** — 日付は `YYYY-MM-DD`、時刻は `HH:mm` の **文字列**として保持する。スプレッドシートの日付型・時刻型は、シートとスクリプトのタイムゾーン設定が食い違うと1日ずれる事故を起こし、時刻型は内部的に1899年の日時として扱われるなど癖が強い。文字列で持てばこの種の事故が構造的に発生せず、辞書順のソートが時系列順と一致し、管理者が見ても曖昧さがない。集計関数が直接使えなくなる欠点はあるが、利用実績レポート（A9）は第1版のスコープ外であるため許容する。

| 終了時刻 | `HH:mm` | |
| 人数 | 利用人数 | |

| 予約者userId | LINE の userId。顧客の主キー | 管理者の代理予約では空欄になりうる |

**キャンセルは行を削除せず、状態列を `キャンセル` に変更して表現する。** 履歴を残すため（G-A7）。空き判定では状態が `確定` の行のみを対象とする。ただし管理者が行そのものを削除した場合も許容し、その枠は空きとして扱う。

#### 部屋別予約可能時間

| 列 | 内容 |

| 終了時刻 | `HH:mm` |

**同じ部屋・同じ曜日について複数行を書ける。** これが定例枠を塞ぐ仕組みである（5.2）。大会議室の火曜10:00-12:00が定例なら、`大会議室/火/9:00/10:00` と `大会議室/火/12:00/18:00` の2行を登録する。その隙間が予約不可になる。

### 7.3 管理者による直接編集の扱い

管理者はシート上で予約を直接追加・編集・削除する（4.3）。Bot はこれを検知して整合を取る必要がある。

**新規追加の判定** — 予約IDが空欄の行を新規追加とみなし、**予約IDを採番して書き込む**。管理者にID採番を求めてはならない。登録元は `管理者` とする。

**検証と警告** — 追加・編集された行に対して以下を検証し、該当すれば **警告列に内容を記入する**。ただし**編集を拒否したり、値を書き換えたりはしない**（4.3）。

- 同一部屋・同一時間帯に他の確定予約が存在する
- 営業時間外、部屋別予約可能時間外、臨時ブロックと重複している
- 終了時刻が開始時刻より前、または日をまたいでいる
- 部屋IDが部屋マスタに存在しない
- 人数が部屋の定員を超えている

**ユーザーへの通知** — 管理者が他人の予約を変更・キャンセルした場合、予約者userId 宛に LINE で通知する（4.3）。代理予約などで予約者userId が空欄の行については、通知先が存在しないため通知しない。

**編集の検知方法**は実装方式に依存するため、8章で扱う。

## 8. 処理仕様

### 8.0 実装方式

**Google Apps Script 単体で実装する。** 予約管理用スプレッドシートに紐づくコンテナバインドスクリプトとし、ウェブアプリとしてデプロイした URL で LINE の Webhook を受ける。

この方式を選んだ決定的な理由は **排他制御**である。Google Sheets API にはトランザクションも行ロックも存在せず、「読んで、確認して、書く」を不可分に実行する手段がない。二重予約の防止（G-U11）を確実に行うには GAS の `LockService` が必要となる。加えて、管理者のシート直接編集の検知（7.3）が `onEdit` トリガーで標準的に行え、運用コストがゼロになる（G-A10）。

**デプロイ設定** — 実行ユーザーは「自分」、アクセスできるユーザーは「全員」とする。LINE プラットフォームからの匿名 POST を受けるために必要である。既存のデプロイを更新すればURLは維持されるため、Webhook URL の再設定は不要となる。

**秘密情報の保持** — チャネルアクセストークン、チャネルシークレット、Webhook 検証用トークンは、スクリプトプロパティに保存する。コード内に直接記述しないこと。

### 8.1 Webhook の受信と検証

**GAS の `doPost(e)` はHTTPリクエストヘッダーを取得できない。** そのため LINE が付与する `X-Line-Signature` を用いた署名検証は実行できない。これは GAS を採用する以上、回避できない制約である。

代替として、**Webhook URL にクエリパラメータとして秘密トークンを付与し、`e.parameter` で受け取って検証する**。

```
https://script.google.com/macros/s/〈デプロイID〉/exec?token=〈推測不能な文字列〉
```

トークンが一致しないリクエストは処理せず破棄する。トークンはスクリプトプロパティに保存し、URL は LINE Developers コンソールの Webhook URL 設定にのみ記載する。

この方式は署名検証より弱い。URL が漏れれば第三者がリクエストを送れる。ただし送れるのは偽の予約リクエストのみであり、既存データの窃取はできない。実装時に、この制約を許容するか、署名検証のためにリバースプロキシを挟むかを最終判断すること。

**応答は速やかに返すこと。** 処理に時間がかかると LINE 側がタイムアウトする。また、同一イベントが再送される可能性を考慮し、予約の確定処理はイベントIDによる重複実行の抑止を検討する。

**reply token は、発言したユーザーへ1回だけ、短時間のみ有効である。** 管理者への通知や、管理者操作を受けたユーザーへの通知は別人宛となるため、必ず push API を使う。

### 8.2 空き判定アルゴリズム

**入力** — 日付、開始時刻、終了時刻、人数、除外する予約ID（変更時のみ）
**出力** — 予約可能な部屋の一覧（表示順）

1. 営業時間シートから当該曜日の行を取得する。稼働日でなければ、空の一覧を返す。
2. 要求された時間帯が営業帯に収まらなければ、空の一覧を返す。
3. 部屋マスタから有効な部屋を取得し、**人数を収容できる部屋に絞る**。定員が空欄の部屋（制限なし）は人数によらず常に含める。
4. 絞り込んだ各部屋について、以下をすべて満たすものを残す。
   1. **部屋別予約可能時間** — 当該部屋・曜日の行が存在する場合、要求時間帯がいずれかの区間に**完全に収まる**こと。開始・終了が空欄の行が存在する場合は終日不可として除外する。行が存在しない場合は営業帯に従う（手順2で確認済み）。
   2. **臨時ブロック** — 重複する行が存在しないこと。部屋IDが空欄のブロック行は全部屋に適用する。
   3. **既存の予約** — 状態が `確定` の予約と重複しないこと。**除外する予約IDが指定されている場合、その予約は判定対象から外す**（5.3）。
5. 残った部屋を、定員の昇順、次いで表示順の昇順で並べて返す。

**時間帯の重複判定** — 2つの時間帯 A と B が重複するのは、`A.開始 < B.終了 かつ B.開始 < A.終了` を満たす場合のみとする。境界は重複としない。**10:00-11:00 と 11:00-12:00 は重複せず、連続して予約できる。**

### 8.3 二重予約の排他制御

同一の枠を複数のユーザーが同時に取りにきた場合でも、成立する予約は1件でなければならない（G-U11）。

**`LockService.getScriptLock()` によるスクリプト単位の排他ロックを用いる。**

```javascript
const lock = LockService.getScriptLock();
if (!lock.tryLock(10000)) {
  // ロックを取得できなかった場合は、混雑している旨を伝えて再試行を促す
  return;
}
try {
  // ① 空き判定を再実行する
  // ② 空いていれば予約行を書き込む
} finally {
  lock.releaseLock();
}
```

**空き判定と書き込みの両方を、必ずロックの内側で行うこと。** 判定だけをロックして書き込みを外に出すと排他が成立せず、二重予約が発生する。ここが本仕様で最も壊れやすい箇所である。

ロックはスクリプト全体で1つであり、ユーザーをまたいで直列化される。12室・自社利用という規模では性能上の問題は生じない。

**確定処理では、postback データに含まれる情報を信用せず、空き状況を必ず再判定する**（6.7）。選択から確定までの間に他者が同じ枠を取っている可能性があり、また古いメッセージのボタンが押される可能性もあるためである。

### 8.4 シート直接編集の取り込み

**インストーラブルトリガーの `onEdit` を使用する。** 簡易トリガー（関数名 `onEdit` を定義するだけの方式）では、認可を必要とする操作が実行できず、**LINE への通知（`UrlFetchApp`）もメール送信も行えない**。管理者の編集を検知して通知する要件（4.3）を満たすには、インストーラブルトリガーの設定が必須となる。

**処理手順**

1. 編集されたシートが「予約」でなければ、何もしない。
2. **編集された列が、Bot自身が書き込む列（予約ID・警告・作成日時・更新日時）であれば、何もしない。** これを怠ると、Bot の書き込みが再び `onEdit` を発火させ、無限ループに陥る。
3. 予約IDが空欄であれば新規追加とみなし、予約IDを採番して書き込む。登録元を `管理者`、作成日時を記録する。
4. 当該行を検証し、該当する問題があれば警告列に記入する（7.3）。**編集の拒否や値の書き換えは行わない。**
5. 変更またはキャンセルであり、予約者userId が存在する場合、そのユーザーへ LINE の push API で通知する。予約者userId が空欄の行（代理予約など）は通知しない。
6. 操作履歴に記録する。

**行の削除は検知しない。** `onEdit` は行削除では発火せず、`onChange` では削除された行を特定できないためである。削除された予約は空き枠に戻るのみで実害が小さいため、第1版では許容する。

**そのうえで、管理者にはキャンセルを行削除ではなく状態列の変更で行うよう案内すること。** 行を削除すると履歴（G-A7）とユーザーへの通知が失われる。

### 8.5 予約の状態遷移

承認フローが存在しないため、状態は2つのみである。

```
(なし) ──[ユーザーの予約 / 管理者の代理予約]──▶ 確定
                                                 │
   確定 ──[内容変更：予約IDは保持]──▶ 確定 ◀────┘
                                                 │
                                                 ▼
                                              キャンセル
```

| 遷移 | 契機 | 備考 |
|---|---|---|
| なし → 確定 | ユーザーの予約確定、または管理者のシートへの行追加 | 承認を挟まず即時確定する |
| 確定 → 確定 | 内容変更 | **予約IDは変更しない**（5.3）。操作履歴に差分を記録する |
| 確定 → キャンセル | ユーザーまたは管理者によるキャンセル | 行は削除せず状態列を変更する |
| キャンセル → 確定 | 想定しない | 再度利用する場合は新規予約として扱う |

### 8.6 設定値とタイムゾーンの扱い

**設定値は毎回シートから読む。** キャッシュを挟むと、管理者が設定を変更しても即座に反映されず、G-A2（自分で変更できる）の体感を損なう。本システムの規模では毎回読んでも性能上の問題はない。

不正な値（空欄、0以下、数値以外）を検出した場合は、**既定値で動作を継続し、警告を残す**（4.3）。設定ミスでシステム全体が停止する状態にはしない。

**タイムゾーンは `Asia/Tokyo` に固定する。** スプレッドシートの設定と、Apps Script プロジェクトの設定（`appsscript.json` の `timeZone`）の両方を明示的に揃えること。片方だけの設定では日付がずれる。なお日付・時刻を文字列で保持する設計（7.2）により、この設定ミスの影響範囲は現在時刻の取得のみに限定される。

### 8.7 通知処理

本システムが送る通知は3種類ある。**手段を取り違えないこと。** LINE の push 通知は無料枠を消費するが、メールと応答メッセージ（reply）は消費しない。

| 契機 | 宛先 | 手段 | 理由 |
|---|---|---|---|
| 新規予約が確定した | 管理者 | **メール**（`MailApp`） | LINE の push は無料枠を消費する。予約1件ごとに1通消費すると無料プランの上限に容易に到達する |
| 管理者が他人の予約を変更・キャンセルした | 対象ユーザー | **LINE push** | 当人に届かなければ会議に支障が出る。例外対応に限られるため件数は少ない |
| 予約の確定処理が例外で失敗した | 管理者 | **メール**（`MailApp`） | 原因を追跡できるのは管理者だけであるため（9.1） |

**ユーザー自身への予約完了通知は、push で送らない。** ユーザーの「確定する」操作に対する**応答メッセージ（reply）として返す**。reply は無料・無制限であり、無料枠を一切消費しない。ここを push で実装すると、予約1件ごとに無料枠を消費することになる。

**宛先** — 管理者のメールアドレスは設定シートから読む（7.2）。複数名の場合はカンマ区切りで指定する。

**通知の失敗は、予約の成立に影響させないこと。** `MailApp` の送信上限（無料アカウントで1日100通、Google Workspace で1日1,500通）に達した場合や、push API がエラーを返した場合でも、**予約そのものは成立させる**。通知処理は予約の確定処理と分離し、通知の失敗は実行ログに記録するに留める。予約できたはずのユーザーが、通知の失敗を理由に予約できない事態を招いてはならない。

## 9. 非機能・運用

### 9.1 エラー処理

**無言で失敗しないこと。** ユーザーの操作に対して常に何らかの応答を返す。処理に失敗した場合も、失敗したことが伝わらなければユーザーは予約できたと誤解する。

**ユーザーに見せるエラーは、理由と次の行動をセットで伝えること**（6.8）。「予約できません」だけで終えず、締切超過なら締切の条件を、満室なら次に取れる手段を示す。

想定外の例外については、ユーザーには汎用のメッセージを返し、詳細は実行ログに記録する。内部のエラー内容をユーザーに露出させない。

**予約の確定処理が例外で失敗した場合は、管理者へメールで通知する。** ユーザーは予約できなかったことしか分からず、原因を追跡できるのは管理者だけであるため。

### 9.2 ログ

| 種別 | 保持先 | 用途 |
|---|---|---|
| 操作履歴 | 操作履歴シート | 予約の作成・変更・キャンセルの業務記録（G-A7） |
| 実行ログ | Apps Script の実行ログ | 例外・不具合の調査 |

操作履歴には、日時・実施者・操作種別・予約ID・変更内容を記録する。管理者によるシート編集も `管理者（シート編集）` として記録する。

### 9.3 性能

想定規模は12室・自社利用であり、年間の予約行数は数千行程度に収まる。この規模では、予約シートを全件読み込んで判定しても実用上の問題はない。

**ただし、シートへのアクセス方法には注意すること。** GAS では、行ごとに `getRange` を呼ぶ実装は極端に遅くなる。**`getValues()` で一括して読み込み、以降はメモリ上の配列で処理すること。** 書き込みも同様に一括で行う。これは GAS における最も典型的な性能問題である。

行数が増加した場合は、一定期間を過ぎた予約を別シートへ退避する運用を検討する。第1版では実装しない（10章）。

### 9.4 タイムゾーンと設定値

8.6 に記載のとおり。タイムゾーンは `Asia/Tokyo` に固定し、スプレッドシートと Apps Script プロジェクトの双方で明示的に設定する。設定値は毎回シートから読み、不正値は既定値へフォールバックして警告を残す。

### 9.5 セキュリティ・個人情報

**保持する個人情報** — LINE の userId、氏名、メールアドレス。予約シートには予約者氏名も保持する（7.2）。

**スプレッドシートの共有範囲を管理者に限定すること。** 全ユーザーの氏名とメールアドレスが含まれるため、閲覧権限を広く付与してはならない。これは技術ではなく運用で担保する事項であり、**設定を誤ると全社員の個人情報が閲覧可能になる**。

**秘密情報はスクリプトプロパティに保存する。** チャネルアクセストークン、チャネルシークレット、Webhook 検証用トークンをコード内に記述しないこと。スクリプトを共有した相手にそのまま渡ることになる。

**Webhook URL を秘匿すること。** 署名検証が使えない制約（8.1）により、URL の秘匿がリクエスト検証の実質的な防御線となる。URL は LINE Developers コンソールの設定にのみ記載し、他所に控えない。

**個人情報の削除手段** — 退職者などのデータを削除する場合、顧客マスタの該当行を削除する。予約シートに残る氏名は履歴として残るため、必要に応じて個別に削除する。保持期間は定めない（自社運用のため）。

### 9.6 バックアップと復旧

スプレッドシートの版履歴により、誤操作や誤削除からの復旧が可能である。**管理者が直接編集する設計（4.3）である以上、誤操作は起こりうる前提とし、版履歴からの復旧手順を運用として周知すること。**
