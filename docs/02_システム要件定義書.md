## 2. 会話フロー仕様

### 2.1 共通事項

**入口はリッチメニュー**とし、3列×2行の6区画を配置する。

| 位置 | ボタン | postback | 遷移先 |
|---|---|---|---|
| 左上 | 今日 | `a=new&d=today` | 2.3 予約フロー（当日） |
| 中上 | 明日 | `a=new&d=tomorrow` | 2.3 予約フロー（翌日） |
| 右上 | 日付を選ぶ | `a=new` | 2.3 予約フロー（P1 から） |
| 左下 | 予約の確認 | `a=list` | 2.4 予約確認 |
| 中下 | 空き状況 | `a=avail` | 2.6 空き状況照会 |
| 右下 | 使い方 | `a=help` | 操作の案内 |

**リッチメニューは Messaging API から登録すること。** LINE 公式アカウントマネージャーの画面で作成したリッチメニューは、各区画に「テキストの送信」しか設定できず、postback を割り当てられない。API から登録することで1タップで予約フローに入れる。

**「今日」「明日」の日付を postback に焼き込まないこと。** リッチメニューは登録後に内容が固定されるため、日付を埋め込むとメニューを毎日作り直す運用になる。`today` / `tomorrow` の相対指定で送り、受信側で実際の日付に解決する。

**未登録ユーザーが押した場合、復帰用に保存する操作は相対指定のまま保つこと。** 初回登録の途中で日をまたいだ場合、解決済みの日付を保存していると「今日」を押したのに前日の予約が始まる。

なお、テキストで `予約する` `予約の確認` `空き状況` が送られた場合も同じ操作として解釈する。リッチメニューを表示できない環境への保険である。

**ユーザーの入力手段は原則ボタン（postback）とする。** キーボード入力を求めるのは、氏名・メールアドレス・予約名・備考・人数の直接指定に限る。自由入力を増やすほど表記ゆれと入力エラーの処理が増え、G-U3（説明なしで使える）から遠ざかるためである。

**選択肢の上限に注意すること。** クイックリプライは13件、カルーセルテンプレートは10件、Flex Message のカルーセルは12件が上限である。営業時間が09:00-18:00なら開始時刻の候補は18件あり、クイックリプライでは表示しきれない。**時刻の選択と部屋の一覧は、縦に伸ばせる単一の Flex Message で構成する**こと。ただし Flex Message にも JSON サイズと構成要素数の上限があるため、無制限ではない。

**選択肢は設定値から生成すること。** 利用時間の選択肢は「時間の刻み」の倍数として生成する。これらを定数として直書きすると、管理者が設定シートを変更しても選択肢が追従せず、UI が提示する値と検証ロジックが食い違う（運用要件4.6-6 に違反する）。

**人数の選択肢は、部屋マスタの定員から生成する。** 具体的には、有効な部屋の定員の異なり値を昇順に並べ（本構成なら 1／6／12）、設定値の「人数の初期値」を加え、末尾に「人数を入力」を置く。**定員体系と無関係な数値を直書きしないこと。** 部屋の定員を変更したり部屋を追加したりしたときに、選択肢が追従しなくなる（G-A3 に反する）。

**開始時刻の刻みの起点は、その日の営業開始時刻とする。** 営業時間が 09:00-18:00、刻みが30分なら、候補は 09:00, 09:30, …, 17:30 となる。起点を 00:00 に固定すると、営業開始が 09:15 のような設定で候補がずれる。

### 2.2 初回登録・登録情報の更新フロー（F-01, F-15）

#### 初回登録

**利用者マスタに未登録のユーザーが、いずれかの操作を行った時点で開始する。**

| # | Bot が提示するもの | ユーザーの操作 |
|---|---|---|
| R1 | 利用開始の案内と、氏名の入力依頼 | 氏名をテキスト入力 |
| R2 | メールアドレスの入力依頼 | メールアドレスをテキスト入力 |
| R3 | 登録完了の通知と、元の操作への復帰 | — |

**初回登録を予約フローから独立させる理由** — 予約名の自動生成（「〈氏名〉の予約」）は氏名を前提とするため、氏名取得より前に予約名を確定させることができない。初回登録を予約より前に済ませることで、以降の全フローが氏名の存在を前提にできる。

登録完了後は、ユーザーが最初に押したボタンの操作へ復帰させること。初回登録のために操作が失われてはならない。

**R3 の完了メッセージで「登録内容は後から変更できます」と案内すること。** 変更手段があること自体が伝わらないと、誤入力に気づいたユーザーが管理者へ問い合わせることになる（G-A6に反する）。

#### 登録情報の更新

**導線は「予約の確認」画面の末尾に置く「登録情報の変更」ボタンとする。** リッチメニューには追加しない。使用頻度が極めて低い機能に、限られたリッチメニューの枠を割く必要がないためである。

**このボタンは、予約が1件もない場合にも必ず表示すること。** 想定される最も多い用途は初回登録時の誤入力の訂正であり（運用要件5.5）、**その瞬間のユーザーは必ず予約0件である。** 一覧が空のときにボタンを出さないと、主用途において唯一の導線に到達できない。予約0件時は「予約はありません」というメッセージと共に、このボタンを表示する。

| # | Bot が提示するもの | ユーザーの操作 |
|---|---|---|
| U1 | 現在の登録内容と、変更対象の選択肢（`氏名`／`メールアドレス`） | 変更したい項目を選ぶ |
| U2 | 新しい値の入力依頼 | テキスト入力 |
| U3 | 変更完了の通知 | — |

**氏名を変更した場合、まだ終わっていない自分の予約について、予約者氏名と予約名を更新する**（運用要件5.5）。対象は「終了時刻が現在時刻以降」かつ「状態が `確定`」の予約に限り、終了済み・キャンセル済みの予約は当時の記録として残す。**共有カレンダーへ同期済みの予定についても、同様に更新すること。**

**予約名の更新を見落とさないこと。** 予約名は未入力時に「〈氏名〉の予約」として自動生成されるため（2.3 P6）、**氏名の第2のコピーになっている。** しかも「入力せずに進む」は既定の経路である。予約名が旧氏名から自動生成された値と完全一致する場合のみ、新しい氏名で置き換える。ユーザーが手入力した予約名は変更しない。

この更新を実装しないと、予約シートが氏名をコピー保持している設計（3.3）により、**氏名を直しても、空き状況照会・本日の予約ビュー・共有カレンダーのタイトルに古い氏名が表示され続ける。**

**メールアドレスの変更は、予約シートへ波及しない**（予約シートはメールアドレスを保持しないため）。

**氏名・メールアドレスの入力検証** — 空文字、空白のみ、および極端に長い文字列は受け付けず、入力し直すよう促す。**氏名は空にできない。** 氏名は全社員に表示され（2.6）、予約名の自動生成元でもあるため、不正な値が入ると波及処理によって既存の予約にまで伝播する。メールアドレスは形式（`@` を含むこと）を確認する。

### 2.3 予約フロー（F-02）

**当日の直前予約も、数週間先の計画予約も、このフロー1本で扱う。** 受付締切を設けないため（運用要件1.4）、両者を分ける必要がない。

| # | Bot が提示するもの | ユーザーの操作 | 要件 |
|---|---|---|---|
| P1 | 日付選択 | **「今日」「明日」のボタン**、または datetimepicker（mode=date） | ショートカットで当日利用の手数を減らす。カレンダーの選択可能範囲は「本日〜設定値の日数後」に制限する（min/max を指定し、範囲外を選べなくする） |
| P2 | 人数の選択肢 | 人数を選ぶ | 設定値の初期値（既定6名）を視覚的に強調する。「人数を入力」を選んだ場合はテキスト入力へ |
| P3 | 開始時刻の一覧（Flex） | 時刻を選ぶ | **表示条件と並び順は下記** |
| P4 | 利用時間の選択肢 | 時間を選ぶ | 「時間の刻み」の倍数で生成し、`営業終了まで` を末尾に置く。**選択済みの開始時刻から確保できない長さは表示しない** |
| P5 | おまかせ＋空き部屋の一覧 | 部屋または「おまかせ」を選ぶ | 収容可能な空室のみを、定員の昇順、次いで表示順、次いで部屋IDの昇順で表示する |
| P6 | 予約名の入力依頼 | テキスト入力、または「入力せずに進む」 | 未入力時は「〈氏名〉の予約」を自動生成する |
| P7 | 備考の入力依頼 | テキスト入力、または「入力せずに進む」 | 任意。未入力なら空欄 |
| P8 | 予約内容の確認 | 「確定する」または「やり直す」 | **確定時に空き状況・締切・設定値を再判定する** |

**P1 に「今日」「明日」を置く理由** — 当日利用（S-2）は頻度が高く、カレンダーを開いて日付を選ぶ操作は手数として重い。専用フローを作らずに手数を減らす手段として、日付選択のショートカットを用いる。

**P3（開始時刻）の表示条件** — 以下をすべて満たす時刻のみを表示する。

1. その日付の営業時間内である
2. **P2で選択した人数を収容できる部屋のうち、少なくとも1室が、その時刻から「最短予約時間」だけ空いている**
3. **受付締切を過ぎていない。** 既定値 `0` の場合、これは「開始時刻が現在時刻以降である」ことを意味する

人数（P2）を開始時刻（P3）より前に取得する理由は、2番目の条件のためである。人数が未確定では「空いている部屋があるか」を判定できず、判定基準が実装者ごとに分岐する。**この順序を入れ替えてはならない。**

**P3 の並び順** — 時刻の昇順とする。当日を選んだ場合、条件3により過去の時刻は候補から消えるため、**結果として直近の時刻が自動的に先頭に来る**。特別な並べ替えは不要である。

候補が0件になる場合は、**その旨と理由（稼働日外／全室満室／本日の営業時間が終了）を明示すること。** 時刻が表示されないだけでは理由が伝わらない。

**「営業終了まで」の定義** — 選択した開始時刻から、その日の営業終了時刻までを指す。「終日」ではない。開始時刻を選んだ後に一日全体を指定することは論理的にできないため、この呼称を用いる。なお部屋別予約可能時間が営業時間より狭い場合、実際に確保できるのは部屋別の区間の終わりまでとなるため、**P4 の時点では営業終了までを上限として提示し、P5 の部屋一覧で収まらない部屋を除外する**。

**予約が確定したら、2つの経路でカレンダー登録の手段を提供する。**

**① メールで `.ics` を送る（F-10）** — 予約の**作成・変更・キャンセルのそれぞれ**で、予約者へメールを送り `.ics` ファイルを添付する。ユーザーはメールクライアント上で1クリックしてカレンダーに追加できる。**変更時は予定が更新され、キャンセル時は予定が削除される**（同一の識別子で通知を再送する仕組み。技術仕様書8.1）。

**② LINE 上に追加リンクを出す（F-16）** — 予約完了の応答メッセージに、以下のボタンを添える。

| ボタン | 遷移先 |
|---|---|
| Google カレンダーに追加 | Google カレンダーの予定作成画面（事前入力済み） |
| Outlook に追加 | Outlook の予定作成画面（事前入力済み） |

両方を常に表示すること。ユーザーがどちらを使うかは判別できず、社内のグループウェアも未確定であるため（運用要件 T-17）、選ばせる形にする。

**②を残す理由** — `.ics` の更新・キャンセル通知はクライアントによって挙動が異なり（運用要件1.5）、意図どおり動かない環境への保険となる。また、メールを開く前にその場で登録したいユーザーへの即時性も提供する。

**②のリンクは自動登録ではなく、変更にも追随しない。** ユーザーがタップし、開いた画面で保存する操作が必要である。**メッセージ本文でその旨を伝えること。**「追加しました」と誤解させてはならない。**カレンダーの自動更新を求めるユーザーには、①のメールを使うよう案内する。**

**LINE の push 通知は使用しない。** 予約完了の応答は reply、それ以外の通知はすべてメールとする（運用要件1.3）。

### 2.4 予約確認フロー（F-03）

「予約の確認」を選ぶと、自分の予約を開始日時の昇順で一覧表示する。

**抽出条件** — 以下をすべて満たす行のみを対象とする。

1. 予約者userId が操作者と一致する
2. **状態が `確定` である**（キャンセル済みを含めない）
3. **終了時刻が現在時刻以降である**

条件3を「開始時刻が現在時刻以降」としないのは、**利用中の予約を一覧に残すため**である。ユーザーが今どの部屋を押さえているかを確認できる状態を保つ。

各予約には「変更」「キャンセル」のボタンを添える。**開始時刻を過ぎた予約についてもボタンは表示し、押された時点で操作できない理由を返す**（運用要件3.4）。ボタンを非表示にすると、ユーザーには「なぜ操作できないのか」が分からず、管理者への問い合わせを誘発する（G-A6に反する）。

**一覧の末尾に「登録情報の変更」ボタンを置く**（2.2）。これが登録情報を更新する唯一の導線であるため、**予約が0件の場合も必ず表示すること。**

**予約が0件の場合の挙動** — 「予約はありません」と伝え、「予約する」への導線と「登録情報の変更」ボタンを提示する。無言で空の一覧を返さないこと。

### 2.5 変更・キャンセルフロー（F-04, F-05）

**変更** — 何を変えるかを最初に選ばせる。選択肢によって再利用する手順が異なる。

| 変更対象 | 再利用する手順 | 備考 |
|---|---|---|
| 日時 | P1（日付）→ P3（開始時刻）→ P4（利用時間）→ P5（部屋） | 人数は現在値を引き継ぎ、P2 は省略する |
| 部屋 | P5（部屋）のみ | 日時・人数は現在値を使う |
| 人数 | P2（人数）。**変更後の人数を現在の部屋が収容できない場合は P5 へ進ませる** | 人数列だけを更新してはならない |
| 予約名・備考 | P6・P7 相当のテキスト入力 | 空き判定は不要 |

**空き判定の対象から、変更対象の予約自身を必ず除外する**（運用要件5.3）。除外を忘れると、時間を延長する変更が常に「重複」と判定され、永久に変更できなくなる。

**受付締切は、変更前と変更後の両方の開始時刻に対して判定する**（運用要件5.3）。どちらか一方でも締切を過ぎていれば変更を受け付けない。既定値 `0` の場合、「既に始まっている予約は変更できない」「過去の時刻へは変更できない」ことを意味する。

**キャンセル** — 誤操作を防ぐため、確認を1回挟む。確認画面には予約内容（日時・部屋・予約名）を再掲する。キャンセルは行を削除せず、状態列を `キャンセル` に変更して表現する。

**他人の予約に対しては、変更・キャンセルのボタンを一切表示しない。** 加えて、**変更・キャンセルの処理側でも予約者userId と操作者の一致を必ず検証すること。** ボタンを出さないだけでは、postback を直接送られた場合に防げない。

### 2.6 空き状況照会フロー（F-06）

予約せずに空き状況だけを確認する導線。日付 → 開始時刻の順に選ばせ、**その時刻から「最短予約時間」の枠における、全部屋の状況を縦のリストで表示する**。

**開始時刻の候補からは、受付締切を過ぎた時刻を除外する**（2.3 P3 の条件3と同じ規則）。除外しないと、「空き」と表示された枠が実際には予約できないという食い違いが生じる。

12室 × 18時間帯の全体表をスマートフォンで表示しても判読できないため、**時刻で絞ってから部屋を縦に並べる**構成とする。

**各部屋は3つの状態のいずれかで表示する。** 2値（空き／埋まり）にしてはならない。

| 表示 | 条件 | 表示内容 |
|---|---|---|
| 予約済み | 状態が `確定` の予約と重複する | 部屋名・**予約者の氏名・予約名** |
| 予約不可 | 営業時間外／部屋別予約可能時間外（定例枠）／臨時ブロック | 部屋名・理由（定例・使用不可 等） |
| 空き | 上記のいずれでもない | 部屋名・定員 |

**判定の順序は「予約済み → 予約不可 → 空き」とし、予約と設定上の不可を明確に区別すること。** 「予約可能な部屋の補集合＝予約済み」と実装してはならない。定例枠や臨時ブロックの部屋が「予約者不明で埋まっている」と表示され、ユーザーが存在しない予約者への交渉を試みることになる。

**有効フラグが `FALSE` の部屋は一覧に含めない。**

予約者の氏名と予約名の表示は、ユーザーが予約者に直接交渉するために必要である（G-U10）。このビューは G-U9（希望の部屋が埋まっているときに他の空き部屋が分かる）も兼ねる。

### 2.7 postback データ設計

**会話の状態はサーバー側に持たず、postback データに載せて持ち回る（ステートレス方式）。**

LINE の postback データは最大300文字を格納できる。本フローで持ち回る情報はこの範囲に十分収まる。セッションの生成・失効・破棄といった状態管理を丸ごと省けるため、実装量と不具合の余地が大きく減る。

**形式** — `キー=値` を `&` で連結する。

| キー | 意味 | 値の形式 | 例 |
|---|---|---|---|
| `a` | 操作の種別 | `new`／`list`／`edit`／`cancel`／`avail`／`reg`／`profile`／`help` | `new` |
| （参考） | テキスト入力待ちの保持 | `profile` の `name`・`mail` を含め、テキスト入力を待つ全ての手順で、待機状態をサーバー側に保持する（技術仕様書7章） | — |
| `s` | フロー内の手順 | `date`／`num`／`time`／`dur`／`room`／`title`／`note`／`confirm`／`field`／`name`／`mail` | `room` |
| `d` | 日付 | `yyyyMMdd`、またはリッチメニュー用の相対指定 `today`／`tomorrow` | `20260810` |
| `t` | 開始時刻 | `HHmm` | `1000` |
| `dur` | 利用時間（分） | 整数、`end` は営業終了まで | `60` |
| `n` | 人数 | 整数 | `6` |
| `r` | 部屋ID | 部屋IDまたは `AUTO` | `ROOM03` |
| `id` | 予約ID | 予約ID | `R20260810-K3F9QZ` |
| `f` | 変更対象の項目 | `datetime`／`room`／`num`／`text` | `room` |

例：`a=new&s=room&d=20260810&t=1000&dur=60&n=6`

**postback とシートの形式変換** — postback は区切り文字を持たない形式（`yyyyMMdd` / `HHmm`）、シートは区切り文字を持つ形式（`YYYY-MM-DD` / `HH:mm`）を用いる。**変換は必ず共通関数で行い、各所で個別に実装しないこと。**

**テキスト入力の手順は例外である。** 氏名・メールアドレス・予約名・備考・人数の直接入力は通常のテキストメッセージとして届き、postback データを伴わない。そのため「次に届くテキストが何の入力か」と、それまでに確定した予約内容を、ユーザー単位でサーバー側に一時保持する必要がある。**保持先・有効期限・破棄条件は技術仕様書に定める。**

### 2.8 例外・エラー時の分岐

| 状況 | 挙動 |
|---|---|
| 確定時に、選択した枠が他者に取られていた | 取得できなかった旨を伝え、開始時刻の選択（P3）に戻す |
| 開始時刻を過ぎている（受付締切超過） | 操作できない旨と、**設定値に基づく実際の締切条件**を伝える |
| 変更後の日時が受付締切を過ぎている | 同上。変更前・変更後のどちらが原因かを伝える |
| 予約可能な日数より先の日付 | 予約可能な範囲を伝える。原則として P1 の選択範囲制限で発生しない |
| 収容可能な部屋がすべて埋まっている | 空きがない旨を伝え、空き状況照会への導線を出す |
| 人数変更により現在の部屋に収容できない | 収容できない旨を伝え、部屋の選択（P5）へ進ませる |
| 選択可能な開始時刻が0件 | 該当日に予約できない旨と、理由（稼働日外／全室満室／本日の営業時間が終了）を伝える |
| 他人の予約IDに対する変更・キャンセル要求 | 操作できない旨を伝える。正常な導線からは到達しない |
| 人数の直接入力が不正 | 下記参照 |
| 想定外・解釈不能な入力 | 現在の手順を再提示する。**無言で無視しない** |

**人数の直接入力の検証** — 全角数字は半角に変換したうえで解釈する。**1以上の整数のみを受け付ける。** 0以下、小数、数値として解釈できない文字列は受け付けず、入力し直すよう促す。上限は設けない（大会議室が定員なしのため、どれだけ大きくても割当可能である）。

**古いメッセージのボタンが押される問題に必ず対処すること。** LINE では過去のメッセージのボタンがいつまでも押せる状態で残る。数日前の「この内容で確定する」ボタンを今押されても矛盾なく処理できなければならない。

対処は2段構えとする。第一に、**確定処理では postback データの内容を信用せず、必ずその時点の空き状況・締切・設定値を再判定する**。第二に、**既に開始時刻を過ぎた枠への操作は、受付締切超過として拒否する**。ステートレス方式はセッション失効による防御が効かないため、この再判定が唯一の防御線となる。

受付締切を設けない設計であっても、**「開始時刻を過ぎた枠は予約できない」という判定は必ず残ること**に注意する。締切 `0` はこの判定そのものであり、無効化ではない。

### 2.9 メッセージ文面の方針

具体的な文面は実装時に定めるが、以下を満たすこと。

- **次に何をすればよいかが、常に1文で分かること**（G-U3）
- **エラーは理由と次の行動をセットで伝えること。** 「予約できません」だけで終えない
- **締切や予約可能日数をエラー文面に書く際は、設定シートの値から生成すること。** 「1時間前まで」のように直書きすると、管理者が設定を変えたときに文面と実際の挙動が食い違う。**既定値 `0` の場合の文面は「開始時刻を過ぎているため」となる**
- **確定時は予約内容を全項目再掲すること**（日付・開始時刻・終了時刻・部屋・人数・予約名）

## 3. データ要件

**このスプレッドシートは、管理者にとっての管理画面そのものである。** データの入れ物としてだけでなく、兼任の管理者が手順書なしで読み書きできる状態を設計目標とする。列の意味が名前から分かること、どこを触ればよいかが明らかであることを、正規化やデータ量の効率より優先する。

### 3.1 シート構成

| シート名 | 役割 | 管理者の操作 |
|---|---|---|
| 予約 | 予約の台帳。全ての予約を1行1件で保持する | 随時編集 |
| 本日の予約 | 当日分を時系列で表示する自動ビュー | 参照のみ |
| 部屋マスタ | 部屋の定義 | 稀に編集 |
| 部屋別予約可能時間 | 部屋 × 曜日の予約可能な区間。定例枠はここで塞ぐ | 週次〜月次 |
| 臨時ブロック | 特定日の使用不可（工事・貸切・祝日・全社休業） | 随時編集 |
| 営業時間 | 全体の稼働曜日と営業帯 | 稀に編集 |
| 利用者マスタ | LINE userId と氏名・メールアドレスの対応 | 原則不要 |
| 操作履歴 | 予約の作成・変更・キャンセルの記録 | 参照のみ |
| 設定 | 予約ルールの数値 | 稀に編集 |

### 3.2 共通のデータ形式

**日付・時刻は文字列として保持する。** 日付は `YYYY-MM-DD`、時刻は **`HH:mm`（2桁ゼロ埋め）** とする。

スプレッドシートの日付型・時刻型は、シートとスクリプトのタイムゾーン設定が食い違うと1日ずれる事故を起こし、時刻型は内部的に1899年起点のシリアル値として扱われるなど癖が強い。文字列で持てばこの種の事故が構造的に発生しない。

**ゼロ埋めは必須である。** 本設計は時刻の大小比較を文字列比較で行う前提に立っており、`9:00` のような1桁表記が混入すると `"9:00" < "10:00"` が偽になり、**午前が午後より後ろと判定される**。例外は発生せず「予約可能な部屋が0件」という結果になるだけなので、原因の特定が極めて困難になる。**シートの入力規則で `HH:mm` 形式を強制し、初期データも必ずゼロ埋めで投入すること。**

**曜日は `月` `火` `水` `木` `金` `土` `日` の1文字で表記する。** 他の表記（`月曜`、`Mon` 等）は用いない。曜日文字列のマッチに失敗すると、部屋別予約可能時間の行が見つからず「営業時間に従う」と解釈されて**定例枠が塞がれないまま静かに通る**ため、表記の統一は必須である。

**管理者が編集する全シートに「警告」列を設ける。** 対象は 予約・部屋マスタ・部屋別予約可能時間・臨時ブロック・営業時間・設定 の6シートである。**利用者マスタ・操作履歴・本日の予約には設けない**（前2つは管理者が編集せず、最後の1つは数式による参照専用ビューであり列を追加できないため）。

システムが検出した不正値や異常は、必ずこの列に記入する。管理者はスプレッドシートしか見ないため、実行ログにのみ記録した警告は永久に読まれない。

**マスタ・設定シートの検証は、`onEdit` ではなくリクエスト処理時に行う。** `onEdit` は予約シートの編集しか監視しないため（3.6）、マスタや設定の不正値を検知する契機がない。**各シートを読み込んだ時点で検証し、問題があればその行の警告列に記入する。** 対象は以下である。

| シート | 検証内容 |
|---|---|
| 設定 | 項目名が想定と一致するか、値が項目ごとの許容範囲か |
| 部屋マスタ | 部屋IDの重複・空欄、表示順の重複、定員が負数でないか |
| 部屋別予約可能時間 | 部屋IDが存在するか、曜日の表記、時刻の形式、片方のみ空欄でないか |
| 臨時ブロック | 日付・時刻の形式、片方のみ空欄でないか |
| 営業時間 | 曜日が7行揃っているか、時刻の形式、終了が開始より後か |

**これを実装しないと、F-14 と運用要件4.6-8 が満たせない。** 検知契機がどこにもない状態で「警告を残す」とだけ書かれた要件は、実装者に読み飛ばされる。

### 3.4 本日の予約シート（自動ビュー）

**当日の予約を、開始時刻の昇順で表示する参照専用シート。** G-A1（集計作業なしで稼働状況を把握）と G-A9（Bot が止まってもシートで運用継続）を満たすために設ける。

予約シートは追記順であり、キャンセル行も混在し、管理者が任意の位置に行を追加する。1年で数千行に達するため、**予約シートを直接見て当日の稼働を把握することは実際にはできない。** このビューがそれを補う。

**スプレッドシートの数式（`QUERY` 等）で構成し、スクリプトで生成しないこと。** 数式であれば Bot が停止していても動作し続けるため、G-A9 を真に満たせる。表示対象は「日付が当日」かつ「状態が `確定`」の行とし、開始時刻・部屋名・予約名・予約者氏名・人数を表示する。

### 3.5 マスタ・設定シート

#### 部屋マスタ

| 列 | 内容 |
|---|---|
| 部屋ID | 不変の識別子。**管理者が入力する**（システムは採番しない） |
| 部屋名 | 表示名 |
| 定員 | **空欄は「制限なし」** |
| 表示順 | 同一定員内での並び順。整数 |
| 有効 | `TRUE` / `FALSE`。削除ではなく無効化で表現する |
| 警告 | 部屋IDの重複、表示順の重複などを記入 |

部屋IDは管理者が入力するため、**重複と空欄を検出して警告すること**。表示順の重複も、割当の再現性を損なうため警告の対象とする（重複時は部屋IDの昇順で決定するため動作は破綻しないが、管理者の意図とは異なる並びになる）。

#### 部屋別予約可能時間

| 列 | 内容 |
|---|---|
| 部屋ID | |
| 曜日 | `月`〜`日` の1文字 |
| 開始時刻 | `HH:mm` |
| 終了時刻 | `HH:mm` |
| 警告 | |

**同じ部屋・同じ曜日について複数行を書ける。** これが定例枠を塞ぐ仕組みである。

**行が1つもない部屋・曜日は、営業時間シートの設定に従う。** 全12室 × 7曜日で84行を書かせるのは兼任の管理者に対して過大な負担であり、部屋の追加も煩雑になる。定例枠がある部屋・曜日についてのみ行を書けばよい。

**その曜日を終日予約不可にしたい場合は、開始時刻と終了時刻の両方を空欄にした行を登録する。** 片方のみ空欄の行は不正とみなし、警告を記入したうえで**終日予約不可**として扱う（安全側に倒す）。

| 列 | 内容 |

**祝日・全社休業日は、部屋ID空欄・時刻両方空欄の行1行で表現する。** これは正規の運用手段である。

**メールアドレスは必須項目である。** 予約の作成・変更・キャンセルの通知と、`.ics` によるカレンダー連携（G-U12）がこの宛先に依存する。**未登録のユーザーには通知が届かず、個人カレンダーへの自動反映も機能しない。** 初回登録（2.2）で必ず取得すること。

管理者が代理予約を登録した行など、**メールアドレスを特定できない予約には通知を送らない**（技術仕様書8章）。

**行が削除されたユーザーが操作した場合は、初回登録フロー（2.2）から再開させること。** 利用者マスタの存在を前提とした参照を行い、行がない場合に例外で停止する実装にしてはならない。退職者のデータ削除後に該当ユーザーが操作する経路が実際に存在する。

#### 操作履歴

| 列 | 内容 |
|---|---|
| 日時 | |
| 実施者 | userId、または `管理者（シート編集）` |
| 操作 | `作成` / `変更` / `キャンセル` |
| 予約ID | |
| 内容 | 変更前後の差分など |

**ユーザー経由の予約についても記録すること。** 管理者のシート編集だけを記録する実装にしてはならない（G-A7 は操作主体を問わない）。

**予約シートと操作履歴シートを分ける理由** — 両者は持つものが違う。予約シートは **現在の状態**（1予約＝1行）、操作履歴は **変化の記録**（1操作＝1行）である。1件の予約を3回変更した場合、予約シートは1行のままだが、操作履歴には4行（作成＋変更3回）が積み上がる。

| 観点 | 予約シート | 操作履歴シート |
|---|---|---|
| 保持するもの | 現在の状態 | 変化の記録 |
| 読むタイミング | **毎リクエスト**（空き判定に使う） | トラブル発生時のみ |
| 編集する人 | 管理者が直接編集する | 誰も編集しない（追記専用） |

**混ぜると3つ壊れる。**

1. **空き判定のたびに履歴行まで読むことになり、性能が落ちる。** これは全リクエストで発生する（4.1の一括読み込み要件に反する）
2. **管理者が直接編集するシートに履歴が混ざり、履歴が壊される**
3. 「今この枠は空いているか」という判定に、**過去の変更記録は一切不要**である

逆に、履歴を持たないと **G-A7（誰がいつ何を変えたか追跡できる）が満たせない。** 予約シートの更新日時列だけでは、「何を」「誰が」変えたかが残らないためである。

#### 設定

| 列 | 内容 |
|---|---|
| 項目 | 設定名。**下表の文字列と完全一致させる** |
| 値 | 管理者が書き換える対象 |
| 説明 | 何を意味する値かの説明 |
| 警告 | 不正値を検出した際に記入 |

**保持する項目と既定値**

| 項目（この文字列で固定） | 既定値 | 説明 |
|---|---|---|
| `受付締切（分前）` | **`0`** | 開始時刻の何分前まで予約・変更・キャンセルを受け付けるか。**`0` は開始時刻まで受付を意味する** |
| `予約可能日数` | `60` | 何日先まで予約できるか |
| `時間の刻み（分）` | `30` | 予約時間の最小単位 |
| `最短予約時間（分）` | `30` | |
| `人数の初期値` | `6` | 人数選択で強調する値 |
| `管理者通知先メール` | （未確定） | 複数の場合はカンマ区切り |

**`受付締切（分前）` は `0` 以上の整数を受け付ける。** 負数は不正値として扱い、既定値 `0` にフォールバックして警告を出す。`0` は正当な値であり、不正値として扱ってはならない。

**タイムゾーンは設定項目としない。** `Asia/Tokyo` に固定であり、スプレッドシートと Apps Script プロジェクトの設定で担保する。設定シートに置くと、実際には効かない項目が残るか、3箇所の設定が食い違う。

**項目名の文字列不一致は静かな障害を生む。** 項目が見つからない場合は既定値で動作を継続するため、管理者は「変更したのに反映されない」という状態に陥る。**項目が1つでも見つからなかった場合は、設定シートの警告列にその旨を記入すること。**

### 3.6 管理者による直接編集の要件（F-08）

管理者はシート上で予約を直接追加・編集する。システムはこれを検知して整合を取る。

**新規追加の判定** — 予約IDが空欄の行を新規追加とみなし、**予約IDを採番して書き込む**。管理者にID採番を求めてはならない。登録元は `管理者` とする。

**受付締切は管理者の編集には適用しない。** 管理者は開始時刻を過ぎた予約も編集・キャンセルできる（運用要件4.3）。

**検証と警告** — 追加・編集された行に対して以下を検証し、該当すれば警告列に内容を記入する。ただし**編集を拒否したり、値を書き換えたりはしない**。

- 同一部屋・同一時間帯に他の確定予約が存在する
- 営業時間外、部屋別予約可能時間外、臨時ブロックと重複している
- 終了時刻が開始時刻より前、または同一である
- 日付・時刻の形式が不正である
- 部屋IDが部屋マスタに存在しない
- 人数が部屋の定員を超えている

**共有カレンダーへの同期** — 管理者がシート上で行った追加・変更・キャンセルも、**共有カレンダーへ反映する**（F-17）。Bot 経路と `onEdit` 経路は同じ共通処理を通ること（技術仕様書5.1）。これを落とすと、代理予約や強制キャンセルがカレンダーに反映されない。

**ユーザーへの通知** — 予約の実体を変える列（**日付・開始時刻・終了時刻・部屋ID・状態**）が編集され、かつ**利用者マスタにメールアドレスが登録されている**場合に、そのユーザーへ**メールで通知し、更新済み／キャンセル済みの `.ics` を添付する**。備考や予約名のみの編集では通知しない。

**LINE の push は使用しない。** 予約者userId しか分からずメールアドレスが不明な行（管理者が userId を手入力した場合など）は、通知できない。

**部屋を付け替える際は、部屋ID列と部屋名列の両方を書き換える必要がある**（運用要件4.4）。予約シートは部屋名を重複保持しているため、部屋IDだけを直すと古い部屋名が表示され続ける。**部屋IDと部屋名が部屋マスタと不一致である行は、検証で警告の対象とすること。**

**「他人の予約かどうか」による出し分けは行わない。** スプレッドシートの編集者は Google アカウントで識別され、予約者は LINE の userId で識別されるため、両者を突合する手段がないためである。

**管理者の代理予約についても、管理者への通知は送らない。** 新規予約の管理者通知を全廃した判断（技術仕様書8章）は、代理予約にも同じく適用する。他の管理者は共有カレンダー（F-17）で把握する（G-A8）。**この判断は共有カレンダーの同期が動いていることを前提とする。**

## 4. 非機能要件

### 4.1 性能

想定規模は12室・自社利用であり、年間の予約行数は数千行程度に収まる。

**1リクエスト内で、各シートの読み込みは1回までとすること。** これは最も重要な性能要件である。開始時刻の一覧（2.3 P3）は最大18個の時刻について空き判定を行うが、時刻ごとにシートを読み直すと、1リクエストで100回近いシートアクセスが発生し、LINE の Webhook タイムアウトと reply token の有効期限を超える。**必要なデータを一括で読み込み、以降はメモリ上で全ての判定を行う設計とすること。**

「設定値は毎回シートから読む」という要件（運用要件4.5）は、**リクエストごとに読み直す**ことを意味し、判定のたびに読むことを意味しない。

行数が増加した場合は、一定期間を過ぎた予約を別シートへ退避する運用を検討する。第1版では実装しない。

### 4.2 ログ

| 種別 | 保持先 | 用途 |
|---|---|---|
| 操作履歴 | 操作履歴シート | 予約の作成・変更・キャンセルの業務記録（G-A7） |
| 警告 | 各シートの警告列 | 管理者が気づくべき異常 |
| 実行ログ | Apps Script の実行ログ | 例外・不具合の調査 |

**管理者向けの情報を実行ログにのみ出力しないこと。** 管理者はスプレッドシートしか見ない。

### 4.3 エラー処理

**無言で失敗しないこと。** ユーザーの操作に対して常に何らかの応答を返す。処理に失敗した場合も、失敗したことが伝わらなければユーザーは予約できたと誤解する。

想定外の例外については、ユーザーには汎用のメッセージを返し、詳細は実行ログに記録する。内部のエラー内容をユーザーに露出させない。

**予約の確定処理が例外で失敗した場合は、管理者へメールで通知する。** ただし**同一の障害が連続する場合に通知を繰り返さないこと。** 例外が繰り返し発生するとメール送信のクォータを消費し、正常な予約通知（F-10）まで届かなくなる。

**通知の失敗は、予約の成立に影響させないこと。** メール送信の上限に達した場合や送信が例外を返した場合でも、予約そのものは成立させる。予約できたはずのユーザーが、通知の失敗を理由に予約できない事態を招いてはならない。

### 4.4 セキュリティ・個人情報

**保持する個人情報と、その保持先**

| 情報 | 保持先 |
|---|---|
| LINE userId | 利用者マスタ、予約シート |
| 氏名 | 利用者マスタ、予約シート（予約者氏名列）、予約名（自動生成時）、**共有カレンダーの予定** |
| メールアドレス | 利用者マスタ、**送信するメールの宛先および `.ics` の `ATTENDEE`** |

**共有カレンダーが保持先に含まれる点に注意すること。** 公開 iCal URL で共有する場合、URL を知る者は誰でも閲覧できる（運用要件1.5）。**個人情報が社外へ露出しうる唯一の経路である。** Google Workspace 環境であれば組織内共有で閉じられるため、そちらを優先する。

**スプレッドシートの共有範囲を管理者に限定すること。** 全ユーザーの氏名とメールアドレスが含まれるため、閲覧権限を広く付与してはならない。これは技術ではなく運用で担保する事項であり、**設定を誤ると全社員の個人情報が閲覧可能になる**。

**Bot 経由で開示する情報は、氏名と予約名に限る。** メールアドレスは開示しない。空き状況照会で全社員が予約者の氏名を見られること（G-U10）と、シートの共有を管理者に限ることは矛盾しない。前者は交渉に必要な最小限の情報、後者は連絡先を含む全データという違いである。

**個人情報の削除手段** — 以下をすべて実施する。**利用者マスタの行を消すだけでは不十分である。**

1. 利用者マスタの該当行を削除する
2. 予約シートの予約者氏名・予約名に残る氏名を、必要に応じて個別に削除する
3. **共有カレンダーに残る当該ユーザーの予定を確認し、必要に応じて削除する**

保持期間は定めない（自社運用のため）。

**秘密情報をコード内に記述しないこと。** 保持方法は技術仕様書に定める。

### 4.5 可用性・バックアップ

スプレッドシートの版履歴により、誤操作や誤削除からの復旧が可能である。**管理者が直接編集する設計である以上、誤操作は起こりうる前提とし、版履歴からの復旧手順を運用として周知すること。**

Bot が停止した場合も、「本日の予約」シート（3.4）により当日の運用は継続できる。
