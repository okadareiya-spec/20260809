## 1. 実装方式

**Google Apps Script 単体で実装する。** 予約管理用スプレッドシートに紐づくコンテナバインドスクリプトとし、ウェブアプリとしてデプロイした URL で LINE の Webhook を受ける。

**選定理由** — 決定的なのは**排他制御**である。Google Sheets API にはトランザクションも行ロックも存在せず、「読んで、確認して、書く」を不可分に実行する手段がない。二重予約の防止（G-U11）を確実に行うには GAS の `LockService` が必要となる。加えて、管理者のシート直接編集の検知が `onEdit` トリガーで標準的に行え、運用コストがゼロになる（G-A10）。

**既知の弱点** — ローカルでの自動テストが書きにくいこと、実行時間6分の上限、同時実行数の制限。12室・自社利用という規模では、後者2つは問題にならない。

**デプロイ設定** — 実行ユーザーは「自分」、アクセスできるユーザーは「全員」とする。LINE プラットフォームからの匿名 POST を受けるために必要である。既存のデプロイを更新すればURLは維持されるため、Webhook URL の再設定は不要となる。

**秘密情報の保持** — チャネルアクセストークン、チャネルシークレット、Webhook 検証用トークンは、**スクリプトプロパティ**に保存する。コード内に直接記述しないこと。スクリプトを共有した相手にそのまま渡ることになる。

## 2. Webhook の受信と検証

### 2.1 署名検証が使えない制約

**GAS の `doPost(e)` は HTTP リクエストヘッダーを取得できない。** そのため LINE が付与する `X-Line-Signature` を用いた署名検証は実行できない。これは GAS を採用する以上、回避できない制約である。

代替として、**Webhook URL にクエリパラメータとして秘密トークンを付与し、`e.parameter` で受け取って検証する**。

```
https://script.google.com/macros/s/〈デプロイID〉/exec?token=〈推測不能な文字列〉
```

トークンが一致しないリクエストは処理せず破棄する。トークンはスクリプトプロパティに保存し、URL は LINE Developers コンソールの Webhook URL 設定にのみ記載する。

### 2.2 この方式のリスク（正確な評価）

**この代替手段は署名検証より明確に弱い。** URL が漏洩した場合、攻撃者は**任意の userId を騙った任意の Webhook イベントを送信できる**。その結果、以下が可能になる。

- **他人の予約をキャンセル・変更できる。** 変更・キャンセルの権限判定は予約者userId の一致で行うが、その userId 自体を詐称されるため防げない。予約IDが推測可能な形式であれば、総当たりによる大量キャンセルも成立する。
- **任意ユーザーとして予約を作成できる。** 全枠を埋めることで業務妨害が可能。
- **メール送信のクォータを枯渇させられる。** 予約通知（F-10）を大量に発生させることで、正常な通知が届かなくなる。

**「既存データの窃取はできないが、既存データの破壊はできる」** というのが正確な評価である。応答は reply token 経由で正規ユーザーに返るため、攻撃者がデータを読み出すことは困難だが、書き込み系の被害は防げない。

社内利用であり URL が外部に露出する経路が限られることから、第1版ではこの方式を採用する。ただし**これは受容したリスクであって、安全だからではない**（13章 T-1）。

### 2.3 受信処理

**イベントIDによる重複実行の抑止を必ず実装すること。**（「検討する」ではなく必須要件とする。）

LINE は Webhook の応答が遅い場合に同一イベントを再送する。`LockService` による直列化（4章）と組み合わさると、1回の「確定する」操作で2件の予約が成立しうる。ロックは同時実行を防ぐだけで、**同一内容の正当なリクエストが2回届くことは防げない**。

各 Webhook イベントに含まれる `webhookEventId` を処理済みとして記録し、既に処理済みのイベントは無視する。記録先は `CacheService`（有効期限は数時間で十分）とする。

**応答は速やかに返すこと。** 処理に時間がかかると LINE 側がタイムアウトし、再送を招く。

**`events` が空配列のリクエストを正常に処理できること。** LINE Developers コンソールの「検証」ボタンは、空の `events` を持つリクエストを送る。ここで例外を投げると、実際には正常に動作していても検証が失敗する。

**reply token は、発言したユーザーへ1回だけ、短時間のみ有効である。** 管理者への通知や、管理者操作を受けたユーザーへの通知は別人宛となるため、reply では送れない（8章）。

## 3. データの読み込みと空き判定

### 3.1 一括読み込み（最重要の性能要件）

**1リクエストの処理の冒頭で、必要な全シートを1回ずつ読み込み、以降はメモリ上のデータのみで判定を行う。**

開始時刻の一覧（システム要件 2.3 P3）は最大18個の時刻について空き判定を行う。時刻ごとにシートを読み直すと、1リクエストで100回近いシートアクセスが発生し、実行時間が数秒〜十数秒に達する。LINE の Webhook タイムアウトと reply token の有効期限を超え、さらに `LockService` による直列化で状況が悪化する。

読み込みは `getValues()` による範囲一括取得とし、**行ごとに `getRange` を呼ぶ実装をしないこと**。これは GAS における最も典型的な性能問題である。書き込みも同様に一括で行う。

読み込んだデータは、以降の全処理に引き渡す1つのコンテキストとして保持する。

| 読み込むシート | 用途 |
|---|---|
| 設定 | 予約ルールの数値 |
| 営業時間 | 稼働曜日と営業帯 |
| 部屋マスタ | 部屋の定義 |
| 部屋別予約可能時間 | 定例枠を含む予約可能区間 |
| 臨時ブロック | 特定日の使用不可 |
| 予約 | 既存予約との重複判定 |
| 利用者マスタ | 氏名の補完、初回登録の要否判定 |

**列の解決はヘッダー名で行い、列インデックスを直書きしないこと。** 管理者がシートに列を挿入する可能性がある（直接編集を許可する設計であるため）。ヘッダー行を読み、列名から位置を解決する共通処理を設けること。

### 3.2 時刻の比較

日付は `YYYY-MM-DD`、時刻は `HH:mm`（2桁ゼロ埋め）の文字列で保持される。**この形式であれば、時刻の大小比較を文字列比較で行える。**

**ゼロ埋めされていない値が混入すると比較が破綻する。** `"9:00" < "10:00"` は文字列比較で偽となり、午前が午後より後ろと判定される。例外は発生せず「予約可能な部屋が0件」という結果になるだけなので、原因の特定が極めて困難である。

**読み込み時に正規化すること。** シートから読んだ時刻値がゼロ埋めされていない場合は、メモリ上で `HH:mm` に補正したうえで判定に用い、当該行の警告列にその旨を記入する。入力規則だけに頼らない。

### 3.3 時間帯の重複判定

2つの時間帯 A と B が重複するのは、`A.開始 < B.終了 かつ B.開始 < A.終了` を満たす場合のみとする。**境界は重複としない。** 10:00-11:00 と 11:00-12:00 は重複せず、連続して予約できる（バッファ時間を設けない仕様と整合する）。

### 3.4 予約可能な部屋を求める処理

**入力** — 日付、開始時刻、終了時刻、人数、除外する予約ID（変更時のみ）
**出力** — 予約可能な部屋の一覧（定員の昇順、次いで表示順、次いで部屋IDの昇順）

**手順**

**0. 受付期間の判定**（運用要件5.2の条件5に対応）

- 日付が本日から「予約可能日数」以内であること。範囲外なら空の一覧を返す。
- 開始日時が「現在時刻 ＋ 受付締切（分前）」以降であること。満たさなければ空の一覧を返す。

**受付締切の既定値は `0` である**（運用要件1.4）。この場合、判定式は実質的に「開始日時が現在時刻以降であること」となる。

**`0` だからといって、この判定を省略してはならない。** 締切 `0` は「締切なし」ではなく「開始時刻そのものが締切」という意味であり、既に始まった枠を予約できないようにする唯一の防御線である。省略すると、古い postback 経由で過去の枠に予約が入る。

管理者が設定値を `60` などに変更した場合も、**同じ判定式のまま締切が復活する。** 締切の有無で分岐を作らず、設定値を式に代入するだけで両方の運用に対応すること。分岐を作ると、設定変更が挙動に反映されない箇所が生まれる。

この手順を省いてはならない。UI 側の選択範囲制限（datetimepicker の min/max）だけで担保したつもりになると、古いメッセージのボタン経由で締切超過の予約が成立する。

**1. 営業時間の判定**
当該曜日が稼働日であり、要求時間帯が営業帯に完全に収まること。満たさなければ空の一覧を返す。

**2. 部屋の絞り込み**
部屋マスタから有効フラグが `TRUE` の部屋を取得し、**人数を収容できる部屋に絞る**。定員が空欄の部屋（制限なし）は人数によらず常に含める。

**3. 各部屋の判定**（以下をすべて満たす部屋を残す）

1. **部屋別予約可能時間** — 当該部屋・曜日の行が存在する場合、要求時間帯が**いずれか1つの区間に完全に収まる**こと。複数区間にまたがる場合は不可とする。開始・終了の両方または片方が空欄の行が存在する場合は、終日不可として除外する。行が存在しない場合は営業帯に従う（手順1で確認済み）。
2. **臨時ブロック** — 重複する行が存在しないこと。部屋IDが空欄のブロック行は全部屋に適用する。時刻が両方または片方空欄の行は終日ブロックとして扱う。
3. **既存の予約** — 状態が `確定` の予約と重複しないこと。**除外する予約IDが指定されている場合、その予約は判定対象から外す**。

**4. 並べ替え**
定員の昇順、次いで表示順の昇順、次いで部屋IDの昇順で並べて返す。**定員が空欄の部屋は無限大として扱い、常に末尾に置く。** 空欄を空文字や 0 として扱うと、大会議室が先頭に来て、おまかせ割当で常に最初に選ばれる。これは**運用要件5.4** が明示的に防ごうとした事態そのものである。

### 3.5 空き状況照会のための処理

空き状況照会（F-06）は、予約可能な部屋だけでなく**全部屋の状態**を必要とするため、3.4 とは別の処理として実装する。

**入力** — 日付、開始時刻、終了時刻（開始時刻＋最短予約時間）
**出力** — 有効な全部屋について、以下のいずれかの状態と付随情報

| 状態 | 判定 | 付随情報 |
|---|---|---|
| `予約済み` | 状態が `確定` の予約と重複する | 予約者氏名、予約名 |
| `予約不可` | 営業時間外／部屋別予約可能時間外／臨時ブロック | 理由の区別 |
| `空き` | 上記のいずれでもない | 定員 |

**「予約可能な部屋の補集合＝予約済み」と実装してはならない。** 定例枠や臨時ブロックの部屋が「予約者不明で埋まっている」と表示され、ユーザーが存在しない予約者への交渉を試みることになる。**判定の順序は「予約済み → 予約不可 → 空き」とし、予約と設定上の不可を明確に区別すること。**

有効フラグが `FALSE` の部屋は一覧に含めない。

### 3.6 受付締切の判定（独立した共通処理とすること）

受付締切の判定は、**3.4「予約可能な部屋を求める処理」の内部に閉じ込めてはならない。** その処理は新規予約と変更のときにしか呼ばれず、**キャンセルの経路では呼ばれない**ためである。

**独立した共通関数として実装し、以下の全経路から呼ぶこと。**

| 経路 | 判定対象の開始日時 |
|---|---|
| 新規予約の確定 | 予約しようとしている開始日時 |
| 変更の確定 | **変更前の開始日時と、変更後の開始日時の両方**。どちらか一方でも締切を過ぎていれば拒否する |
| キャンセルの確定 | 対象予約の開始日時 |

**判定式** — `開始日時 ≧ 現在時刻 ＋ 受付締切（分前）`

既定値 `0` では「開始日時が現在時刻以降であること」を意味する。**設定値を式に代入するだけで、締切の有無に関わらず同じ処理が機能する。** 締切の有無で分岐を作らないこと。

**この判定を省くと、既に始まった予約や終わった予約を、古い postback からキャンセルできてしまう。** システム要件2.4 は「開始時刻を過ぎた予約にもボタンを表示し、押された時点で理由を返す」設計であり、**この経路は正常な導線から日常的に踏まれる。** 例外的なケースではない。

**管理者のシート直接編集には、この判定を適用しない**（運用要件4.3）。

## 4. 二重予約の排他制御

同一の枠を複数のユーザーが同時に取りにきた場合でも、成立する予約は1件でなければならない（G-U11）。

**`LockService.getScriptLock()` によるスクリプト単位の排他ロックを用いる。**

```javascript
const lock = LockService.getScriptLock();
if (!lock.tryLock(10000)) {
  // 混雑している旨を伝えて再試行を促す
  return;
}
try {
  // ① 予約シートを読み直す
  // ② 空き判定を再実行する
  // ③ 空いていれば予約行を書き込む
} finally {
  SpreadsheetApp.flush();   // ④ 書き込みを確定させてからロックを手放す
  lock.releaseLock();
}
```

**空き判定と書き込みの両方を、必ずロックの内側で行うこと。** 判定だけをロックして書き込みを外に出すと排他が成立せず、二重予約が発生する。**ここが本仕様で最も壊れやすい箇所である。**

**ロックの内側では予約シートを読み直すこと。** ロック取得前に読んだデータは、待っている間に他のリクエストが書き込んで古くなっている可能性がある。

**ロックを手放す前に `SpreadsheetApp.flush()` を呼ぶこと。** Apps Script はシートへの書き込みをまとめて遅延実行するため、確定させないままロックを解放すると、**次にロックを取った処理が書き込み前の内容を読む。** ロックを保持していても古い判定材料で判断することになり、排他が成立しない。同様に、追記の直後に `getLastRow()` で行番号を得る場合も、確定前に呼ぶと追記前の行番号が返り、以後その予約への書き込みが1行上の予約を書き換える。

ロックはスクリプト全体で1つであり、ユーザーをまたいで直列化される。12室・自社利用という規模では性能上の問題は生じない。

**ロック取得に失敗した場合の応答は、reply token を1回消費する。** 元の処理は完了しないため、ユーザーには「混雑しているため、もう一度お試しください」と伝え、同じ操作へ戻すボタンを添えること。

**確定処理では、postback データに含まれる情報を信用せず、空き状況・締切・設定値を必ず再判定する。** 選択から確定までの間に他者が同じ枠を取っている可能性があり、また古いメッセージのボタンが押される可能性もあるためである。

## 5. 予約の書き込みと共通処理

### 5.1 2つの書き込み経路

予約が書き込まれる経路は2つあり、**どちらも同じ共通処理を通す必要がある**。

| 経路 | 契機 |
|---|---|
| Bot 経路 | ユーザーの「確定する」操作（`doPost`） |
| 管理者経路 | 管理者のシート直接編集（`onEdit`） |

**Apps Script による書き込みは `onEdit` トリガーを発火させない。** トリガーが発火するのは、人間が UI 上でセルを変更した場合のみである。したがって **Bot が予約行を書き込んでも `onEdit` は一切走らない。**

この事実には重要な帰結がある。**予約IDの採番・検証・操作履歴の記録・共有カレンダーへの同期を `onEdit` の処理内にだけ実装すると、ユーザー経由の予約ではそれらが一切実行されない。** 予約IDが振られず、履歴も残らず、カレンダーにも載らない状態になる。

**採番・検証・履歴記録・カレンダー同期は、両経路から呼ばれる共通関数として実装すること。**

### 5.2 予約IDの採番

**形式** — `R` ＋ `yyyyMMdd`（予約日）＋ `-` ＋ 6桁のランダムな英数大文字。例：`R20260810-K3F9QZ`

**この形式を選ぶ理由** — 2つの書き込み経路のうち、`onEdit` 側はロックを取得しない（5.3参照）。連番方式では、2経路が同時に採番するとID重複が発生する。また「最終行のIDをパースして+1」という素朴な実装は、**管理者がシートを日付順に並べ替えた瞬間に破綻する**。ランダム成分を含む形式であれば、経路間の調整なしに一意性が保たれる。

先頭に予約日を置くのは、管理者がIDを見て日付を判別できるようにするためである（G-A9）。

**採番時に既存の予約IDとの重複を確認し、衝突した場合は再生成すること。** 確率は極めて低い（36の6乗 ≒ 22億通り）が、確認処理自体は読み込み済みデータに対する走査で済む。

### 5.3 共通処理の内容

新規作成・変更・キャンセルのいずれにおいても、以下を実行する。

1. 予約IDが未採番であれば採番する
2. 検証を行い、問題があれば警告列に記入する（拒否はしない）
3. 作成日時・更新日時を記録する
4. **操作履歴に記録する**（実施者・操作種別・予約ID・内容）
5. **共有カレンダーへ同期する**（5.4）。作成なら予定を作成しイベントIDを保存、変更なら更新、キャンセルなら削除
6. 通知を送る（8章）

**手順5を落とさないこと。** この列挙はそのまま実装のチェックリストとして使われる。ここから漏れると、管理者の代理予約・強制キャンセル・部屋の付け替えが共有カレンダーに反映されない。しかも例外は出ず、「カレンダーイベントID」列が空欄のまま増えていくだけなので発覚が遅れる。

**`onEdit` 経路ではロックを取得しない。** `onEdit` は編集のたびに発火し、ロックを取得すると管理者の連続編集が直列化されて著しく遅くなる。管理者の編集は「正として受け入れる」設計であり、重複が生じても警告を出すに留める方針（運用要件4.4）であるため、排他は必須ではない。ただし**予約IDの採番だけは衝突しない方式（5.2）を用いることで、ロックなしでも安全性を確保している。**

### 5.4 共有カレンダーへの同期

全ての予約を1つの Google カレンダーへ書き込む（運用要件1.5）。**同期は Bot からカレンダーへの一方向のみとし、カレンダー側の変更を取り込むことはしない。**

**書き込み先** — GAS を動かす Google アカウント上に作成した「会議室予約」カレンダー。**カレンダーIDはスクリプトプロパティに保存する。** 社内のグループウェアが Google Workspace であるか否かに関わらず、書き込み側の実装は変わらない。分岐が生じるのは社員への共有方法のみであり、それは運用設定の領域である（運用要件 T-17・T-18）。

**操作の対応**

| 予約側の操作 | カレンダー側の操作 |
|---|---|
| 新規作成 | `createEvent` で予定を作成し、**返却されたイベントIDを予約シートの「カレンダーイベントID」列に保存する** |
| 内容変更 | イベントIDから予定を取得し、内容を更新する |
| キャンセル | イベントIDから予定を取得し、削除する |
| 氏名変更（5.5） | 対象となる未終了の予約について、予定の内容を更新する |

**イベントIDを予約シートに保持しなければ、変更もキャンセルも反映できない。** 日時や部屋名で予定を検索して特定する実装にしないこと。予約を変更した瞬間に検索条件が変わり、元の予定を見失う。

**イベントIDが空欄（未同期）の予約を操作した場合の扱い**

| 操作 | 挙動 |
|---|---|
| 内容変更 | **予定を新規作成し、イベントIDを保存する**（同期を回復させる）。「何もしない」にすると、一度同期に失敗した予約が永久にカレンダーへ載らない |
| キャンセル | **何もしない**（削除すべき予定が存在しないため）。例外を投げないこと |

**キャンセルで予定を削除した後、カレンダーイベントID列は空欄に戻さず、値を残したままとする。** システム要件3.3の「空欄なら未同期」という定義と衝突するため、**状態列が `キャンセル` の行については、この定義を適用しない**。空欄に戻すと、上の表の規則により「未同期」と判定され、変更操作で予定が再作成されてしまう。

**カレンダーへの書き込みは、`LockService` のロックの外側で行うこと**（4章）。イベントIDの取得は予定の作成後にしか行えないが、**外部 API の応答時間をロックの保持時間に含めてはならない。** ロック内に入れると、昼休み前後など操作が集中する時間帯に全ユーザーがカレンダー API の応答待ちで直列化され、`tryLock(10000)` の失敗（＝「混雑しています」応答、しかも reply token を1回消費する）が多発する。

具体的には、**ロック内で予約行を書き込んで確定させ、ロックを解放してからカレンダーへ同期し、イベントIDだけを追記する**。同期に失敗しても予約は既に成立しているため、下記の失敗時の扱いに従えばよい。

**予定の内容** — タイトルには部屋名と予約名を含める（運用要件 T-19 により、部屋ごとにカレンダーを分けないため、タイトルで部屋を判別できる必要がある）。場所には部屋名、説明には予約者氏名・人数・予約IDを入れる。

**この処理は両方の書き込み経路（Bot・`onEdit`）から呼ばれる共通処理とすること**（5.1）。`onEdit` 側だけに実装すると、ユーザー経由の予約がカレンダーに載らない。

**警告列へ書き込む処理は1箇所に集約すること。** カレンダー同期の失敗と、シート直接編集の検証結果（6.2 手順5）は同じ列を使う。両方が独立に書くと、**あとから書いた側が相手の警告を消す。** 呼び出し側の警告は共通処理へ引数で渡し、書き込みは共通処理側だけが行う形にする。

**同期の失敗は、予約の成立に影響させないこと。** カレンダーへの書き込みが失敗しても予約は成立させ、**予約シートの警告列にその旨を記録する**。イベントIDが空欄の行は未同期であることを意味し、管理者が気づける状態にしておく。通知処理と同じ原則である（8章）。

### 5.5 登録情報の更新に伴う波及処理

ユーザーが氏名を変更した場合、以下を更新する（運用要件5.5）。**対象は「終了時刻が現在時刻以降」かつ「状態が `確定`」である、当該ユーザーの予約に限る。**

1. 利用者マスタの氏名
2. 対象予約の **「予約者氏名」列**
3. 対象予約の **「予約名」列 — ただし旧氏名から自動生成された値である場合に限る**
4. 対象予約に対応する **共有カレンダーの予定**（タイトルと説明の両方。予約名がタイトルに含まれるため）

終了済み・キャンセル済みの予約は更新しない。当時の記録として残す。

**3番目を見落とさないこと。** 予約名は未入力時に「〈氏名〉の予約」として自動生成される（システム要件2.3 P6）。つまり **予約名は氏名の第2のコピーである。** しかも「入力せずに進む」は既定の経路であり、多くの予約がこの形になる。

予約名を更新しないと、**氏名を直しても、空き状況照会・本日の予約ビュー・共有カレンダーのタイトルに旧氏名が残り続ける**（システム要件2.6・3.4）。運用要件5.5が「想定される最も多い用途は初回登録時の誤入力の訂正」と述べている以上、これを取りこぼすと機能の目的そのものが達成されない。

**判定方法** — 予約名が「〈旧氏名〉の予約」と完全一致する場合のみ、「〈新氏名〉の予約」に置き換える。ユーザーが手入力した予約名は変更しない。旧氏名は利用者マスタを更新する前に退避しておくこと。

**この一括更新は、必ず `LockService` のロックの内側で行うこと。** 予約シートを一括読み込みしてメモリ上で書き換え、一括で書き戻す実装（3.1が推奨する形）をロック外で行うと、**その間に他ユーザーが確定させた予約行をまるごと上書きして消す。** 消えた予約は操作履歴にも残らず、原因を追えない。G-U11（二重予約が起きない）が氏名変更の経路から破れる。

**共有カレンダーの更新はロックの外で行う**（5.4と同じ理由）。対象件数だけ `CalendarApp` を呼ぶループになるため、**予約シートの更新を先に完了させ、カレンダーの更新はその後に行うこと。** カレンダー更新の途中で実行時間の上限に達しても、予約シート側は既に整合が取れている状態にする。

**操作履歴への記録** — 氏名変更に伴う予約行の更新は、操作履歴に記録しない。操作履歴の「操作」列は `作成`／`変更`／`キャンセル` の3値であり（システム要件3.5）、予約の実体は変わっていないためである。**利用者マスタの変更のみ、実行ログに記録する。**

メールアドレスの変更は、利用者マスタのみを更新する。予約シートはメールアドレスを保持しないためである。

## 6. シート直接編集の取り込み

### 6.1 トリガーの種別

**インストーラブルトリガーの `onEdit` を使用する。** 簡易トリガー（関数名 `onEdit` を定義するだけの方式）では、認可を必要とする操作が実行できず、**LINE への通知（`UrlFetchApp`）もメール送信も行えない**。管理者の編集を検知して通知する要件を満たすには、インストーラブルトリガーの設定が必須である。

**トリガーの重複登録に注意すること。** インストーラブルトリガーは同じ関数に対して複数登録でき、その場合1回の編集で処理が複数回走る。設定時および再デプロイ時に、既存トリガーの重複を確認すること。

### 6.2 処理手順

1. 編集されたシートが「予約」でなければ、何もしない。
2. 編集された列が、**システム自身が書き込む列（予約ID・カレンダーイベントID・警告・作成日時・更新日時）であれば、何もしない。**
3. **行が完成しているかを判定する**（下記）。未完成なら、警告列にその旨を記入して終了する。
4. 予約IDが空欄であれば新規追加とみなし、5章の共通処理で採番する。登録元を `管理者` とする。
5. 当該行を検証し、問題があれば警告列に記入する。**編集の拒否や値の書き換えは行わない。**
6. **共有カレンダーへ同期する**（5.4）。
7. 通知の要否を判定し、必要なら送る（8章）。
8. 操作履歴に記録する。

**行の完成判定（手順3）が必要な理由** — 管理者が代理予約の行を1セルずつ入力すると、最初のセルを入れた時点で `onEdit` が発火する。判定を設けないと、**日時が未確定のまま共有カレンダーにゴミ予定が作られ、ユーザーへの通知メールまで飛ぶ。** カレンダーへの書き込みとメール送信は外部への副作用であり、取り消せない。

**完成の条件は「日付・開始時刻・終了時刻・部屋ID がすべて埋まっていること」とする。** これらが揃わない行は、採番も同期も通知も行わない。予約者userId と人数は、代理予約では空欄になりうるため条件に含めない。

**日付・時刻の値は正規化して書き戻すこと。** 「値を書き換えない」という原則の唯一の例外とする。`9:00` を `09:00` に直し、シートが日付・時刻型へ自動変換した値を文字列に戻す。**意味は一切変えていない。** 直さないと2つの形で壊れる。1桁の時刻は文字列比較の前提を崩して「予約できる部屋が0件」になり、日付型は「本日の予約」の QUERY が文字列比較のため常に空表示になる。**どちらも例外が出ないため、管理者からは原因の分からない不具合にしか見えない。**

**手順2の目的について** — これは無限ループの防止ではない。**Apps Script による書き込みは `onEdit` を発火させないため、ループは構造的に発生しない。** 手順2の実際の効果は、管理者が警告列の内容を手で消した際などに、不要な再処理を避けることである。

**予約ID列とカレンダーイベントID列は例外扱いとする。** これらを管理者が誤って書き換えた場合は、手順2で打ち切らず **「システム管理用の列が変更された」という警告を記入する。** 予約IDが変わると操作履歴との対応が切れ、カレンダーイベントIDが消えると同期先を見失う。どちらも想定される入力ミスの典型であり、まさに検知すべきケースである。

**「カレンダーイベントIDが空欄＝未同期」という定義（システム要件3.3）があるため、管理者がこの列を消すと、実装によっては同期先を見失って重複予定が生まれる。** 警告を出すことが唯一の防御となる。

### 6.3 通知の判定

**予約の実体を変える列（日付・開始時刻・終了時刻・部屋ID・状態）が編集され、かつ利用者マスタにメールアドレスが登録されている場合**に、そのユーザーへ**メールで通知し、更新済み／キャンセル済みの `.ics` を添付する**（8.1）。**LINE の push は使用しない。**

**「他人の予約かどうか」による出し分けは行わない。** `onEdit` から取得できる編集者情報は Google アカウントのメールアドレスであり、予約者は LINE の userId で識別される。両者を突合する手段がない（利用者マスタにメールアドレスはあるが、一意性を保証していない）。

**通知対象の列を限定する理由** — 限定しないと、備考の誤字を1文字直しただけでもユーザーにメールが飛び、`.ics` の更新通知まで送られる。ユーザーのカレンダーに不要な更新が入り、メール送信のクォータも消費する。

### 6.4 変更前の値の取得（制約あり）

操作履歴に差分を記録するには編集前の値が必要だが、**`onEdit` のイベントオブジェクトから旧値を取得できるのは単一セルの編集時のみである。** 管理者が複数セルをまとめて貼り付けたり、行単位で編集した場合、旧値は取得できない。

差分の記録は **best-effort とする。** 旧値が取得できない場合は、変更後の値と「旧値取得不可」の旨を記録する。これにより G-A7（トラブル時に事実を確認できる）は部分的にしか満たせないが、GAS の制約上これ以上は困難である。

### 6.5 行削除の扱い

**行の削除は検知しない。** `onEdit` は行削除では発火せず、`onChange` では削除された行を特定できないためである。

**ただし、行削除の影響は「空き枠に戻るだけ」では済まない。** カレンダー同期の導入により、**行を削除するとカレンダーイベントIDごと失われ、共有カレンダー側の予定を二度と削除できなくなる。** 予約シートは「空き」、共有カレンダーは「予約済み」という**恒久的な不整合**が残り、システムには回復手段がない。週間の空き状況を俯瞰しているユーザー（G-U13）は、存在しない予約のせいで部屋を諦めることになる。

したがって、**管理者への周知を運用上の必須事項とする。**

- **キャンセルは、行削除ではなく必ず状態列を `キャンセル` に変更して行う**
- **やむを得ず行を削除した場合は、共有カレンダーからも該当の予定を手動で削除する**

この2点をシートの1行目、または管理者向けの説明欄に明記すること。第1版では、孤児となった予定を自動で検出・削除する仕組みは実装しない（13章 T-23）。

## 7. 会話状態の一時保持

会話の状態は原則として postback データに載せて持ち回る（システム要件2.7）。例外は**テキスト入力を待つ状態**のみである。

### 7.1 保持先

**`CacheService.getScriptCache()` を用い、LINE の userId をキーに含めて保持する。**

```
キー: pending_〈userId〉
値:   入力待ちの種別と、その手順までに確定した内容（JSON）
```

**入力待ちが発生する手順**

| 手順 | 待機する入力 |
|---|---|
| 初回登録 R1・R2 | 氏名、メールアドレス |
| 登録情報の更新 U2 | 新しい氏名、または新しいメールアドレス |
| 予約フロー P2 | 人数の直接入力 |
| 予約フロー P6・P7 | 予約名、備考 |

初回登録と登録情報の更新も対象である。**予約フローだけを想定した実装にしないこと。**

**`PropertiesService.getUserProperties()` を使ってはならない。** ウェブアプリは「自分（オーナー）」として実行されるため、ユーザープロパティは**全ての LINE ユーザーで共有される**。ユーザーAの入力待ち状態がユーザーBに適用される。

**`PropertiesService.getScriptProperties()` も適さない。** 有効期限を持たないため、放置された入力待ち状態が永久に残る。数日後にユーザーが送った無関係なテキストが、予約名として確定処理に流れ込む。

### 7.2 有効期限と破棄

**有効期限は30分とする。** `CacheService` は最大6時間まで保持でき、また容量都合で予告なく破棄されることがあるが、テキスト入力を待つ時間としては30分で十分である。

以下の場合に明示的に破棄する。

- テキスト入力を受け取り、次の手順へ進んだとき
- ユーザーがリッチメニューから別の操作を開始したとき
- 予約が確定またはキャンセルされたとき
- **初回登録が完了したとき**
- **登録情報の更新が完了したとき**

**キャッシュが破棄されていた状態でテキストが届いた場合は、入力として解釈せず、現在の操作を再提示すること。** 無言で無視してはならない。

## 8. 通知処理

**本システムは LINE の push 通知を一切使用しない。** ユーザーへの通知は、本人の操作に対する応答（reply）とメールで完結する。これにより無料プランの通知上限が制約にならない。**実装時に push API を使う箇所を作らないこと。**

| 契機 | 宛先 | 手段 | 理由 |
|---|---|---|---|
| ユーザーの予約が確定した | 当該ユーザー | **reply** ＋ **メール**（`.ics` 添付） | reply は即時性、メールはカレンダー登録と記録のため |
| ユーザーが予約を変更した | 当該ユーザー | **reply** ＋ **メール**（更新の `.ics` 添付） | 個人カレンダーの予定を更新させる |
| ユーザーが予約をキャンセルした | 当該ユーザー | **reply** ＋ **メール**（キャンセルの `.ics` 添付） | 個人カレンダーの予定を削除させる |
| ユーザーが登録情報を更新した | 当該ユーザー | **reply** | システム要件2.2 U3 |
| 管理者が予約の実体を変更・キャンセルした | 予約者 | **メール**（更新／キャンセルの `.ics` 添付） | 当人に届かなければ会議に支障が出る。`.ics` により当人のカレンダーも自動で直る |
| 予約の確定処理が例外で失敗した | 管理者 | **メール**（`MailApp`） | 原因を追跡できるのは管理者だけであるため |

**新規予約を管理者へ通知しない。** 12室 × 1日16枠なら理論上192件/日となり、全件をメールで流すと管理者の業務に支障が出る。**管理者は共有カレンダー（5.4）を見れば把握できる**（G-A8）。この判断は共有カレンダーの存在が前提であり、同期を実装しないと G-A8 を満たす手段が消える。

**氏名変更に伴う予約行の一括更新（5.5）では、予約の通知を送らない。** 予約の実体は変わっておらず、操作したのは本人であるため。登録情報更新の完了通知（reply）に含めて伝えれば足りる。

**宛先** — ユーザーへのメールは利用者マスタのメールアドレスへ送る。**メールアドレスが未登録の予約には通知できない**（管理者が代理予約で userId だけを入力した場合など）。管理者への例外通知は、設定シートの `管理者通知先メール` へ送る（複数ならカンマ区切り）。

**`MailApp` の送信上限** — 無料の Google アカウントで1日100通、Google Workspace で1日1,500通。**消費は予約1件につき1通**（作成時）で、変更・キャンセルのたびに追加で1通ずつ。管理者への新規予約通知を廃止したため、消費は約半分になっている。

**無料の Google アカウントで運用する場合、1日あたり実質50〜100件程度が上限**となる点に注意すること。理論上の最大（192件/日）には届かない。**Google Workspace であれば余裕がある。**

**例外通知の抑制** — 同一の障害が連続して発生した場合、通知を繰り返さないこと。例外がループするとメールのクォータを消費し、正常な新規予約通知まで届かなくなる。同種の例外については一定時間（1時間程度）に1通までとする。

**通知の失敗は、予約の成立に影響させないこと。** メールの送信上限に達した場合や送信が例外を返した場合でも、予約そのものは成立させる。通知処理は予約の確定処理と分離し、通知の失敗は実行ログに記録するに留める。

### 8.1 `.ics` ファイルの生成と添付

予約の作成・変更・キャンセル時に、予約者へ送るメールに iCalendar 形式（`.ics`）のファイルを添付する。**これが個人カレンダーへの主たる登録手段であり、変更・キャンセルを自動で反映させる仕組みでもある。**

**種別ごとの指定**

| 契機 | `METHOD` | `STATUS` | `SEQUENCE` |
|---|---|---|---|
| 作成 | `REQUEST` | `CONFIRMED` | `0` |
| 変更 | `REQUEST` | `CONFIRMED` | 前回値 ＋ 1 |
| キャンセル | `CANCEL` | `CANCELLED` | 前回値 ＋ 1 |

**`UID` は予約IDから生成し、絶対に変更しないこと。** 形式は `〈予約ID〉@〈任意のドメイン〉` とする。**UID が変われば、メールクライアントは別の予定として扱い、元の予定が残ったまま重複する。** 予約の変更で予約IDを保持する設計（運用要件5.3）が、ここで効いてくる。

**`SEQUENCE` は予約シートの「ics連番」列で管理し、送信のたびに加算する。** クライアントは `SEQUENCE` が前回より大きい通知だけを「新しい」と判断する。加算を怠ると、**更新通知もキャンセル通知も無視される。** これは無言で失敗するため、実装時に必ず動作確認すること。

**日時は UTC に変換し、末尾に `Z` を付ける。** `DTSTART:20260810T010000Z` の形式とする。`TZID=Asia/Tokyo` を使う場合は `VTIMEZONE` の定義が必要になり、省くと解釈しないクライアントがある。日本には夏時間がないため、UTC への変換は常に一意に定まる。**タイムゾーンの指定を省くと、受信側のタイムゾーンで解釈され予定がずれる。**

**1行は75オクテットを超えないこと（RFC 5545 3.1）。** 超える場合は折り返し、継続行の先頭に空白を1つ置く。**折り返さない長い行は、厳格なパーサーではファイルごと拒否される。** 日本語は1文字3オクテットなので、文字数ではなくオクテット数で数えること。またマルチバイト文字やサロゲートペアの途中で折ると文字が壊れるため、文字境界でのみ折る。

**`ATTENDEE` には `RSVP=TRUE` と `PARTSTAT=NEEDS-ACTION` を指定すること。** `RSVP=FALSE` では Gmail が招待として扱わず、カレンダーへの取り込み動作が働かない。単なる添付ファイルとして表示される。

**`PRODID` に非ASCII文字を入れないこと。** `PRODID` を読んで挙動を変えるクライアントがある。

**主催者と出席者が同一人物になる場合、招待として扱われない。** Bot を動かす Google アカウント自身が予約すると、`ORGANIZER` と `ATTENDEE` が一致し、Google は「自分が作った予定」と見なして追加のUIを出さない。**検証時は必ず別のアドレス宛で確認すること。**

その他の主な項目は、`SUMMARY`（予約名と部屋名）、`LOCATION`（部屋名）、`DESCRIPTION`（人数・予約ID）、`ORGANIZER`（Bot を動かす Google アカウント）、`ATTENDEE`（予約者のメールアドレス）とする。

**添付時の MIME タイプは `text/calendar` とすること。** `application/octet-stream` で添付すると、クライアントが単なるファイルとして扱い、カレンダーへの取り込み動作が働かない。

**クライアントによる挙動差がある。** Outlook は `METHOD:REQUEST` / `CANCEL` を会議招待として扱い、更新・キャンセルを確実に反映する。**Google カレンダー（特に Gmail 経由）では挙動が異なる場合がある。** 実装着手時に、両方の環境で作成・変更・キャンセルの3パターンを実機検証すること（12.1 V-7）。

### 8.2 カレンダー追加リンクの生成

予約完了メッセージには、Google カレンダーと Outlook の両方の追加リンクをボタンとして添える（システム要件2.3）。**リンクを開くと予定作成画面が事前入力状態で表示され、ユーザーが保存操作を行う。自動登録ではない。**

**Google カレンダー**

```
https://calendar.google.com/calendar/render
  ?action=TEMPLATE
  &text=〈予約名（部屋名を含める）〉
  &dates=〈yyyyMMdd'T'HHmmss〉/〈yyyyMMdd'T'HHmmss〉
  &ctz=Asia/Tokyo
  &location=〈部屋名〉
  &details=〈人数・予約ID等〉
```

**`ctz=Asia/Tokyo` を必ず付けること。** 省略すると、`dates` の値が UTC として解釈され、**予定が9時間ずれて登録される**。日時をローカル時刻の書式で渡す以上、タイムゾーンの明示は必須である。

**Outlook**

```
https://outlook.office.com/calendar/0/deeplink/compose
  ?path=/calendar/action/compose
  &rru=addevent
  &subject=〈予約名（部屋名を含める）〉
  &startdt=〈ISO 8601／オフセット付き〉
  &enddt=〈ISO 8601／オフセット付き〉
  &location=〈部屋名〉
  &body=〈人数・予約ID等〉
```

Outlook は日時をオフセット付きの ISO 8601（例 `2026-08-10T10:00:00+09:00`）で受け取る。**Google とは日時の書式が異なるため、共通化せず個別に組み立てること。**

**全てのパラメータ値を URL エンコードすること。** 予約名と備考は日本語であり、スペースや記号も含まれうる。

**LINE 内ブラウザではなく外部ブラウザで開かせること。** LINE の URI アクションは既定でアプリ内ブラウザを使うが、そこではカレンダーアプリへ引き渡されず保存操作が煩雑になる。URL の末尾に `openExternalBrowser=1` を付与して外部ブラウザで開く（12.1 V-5 で実機検証すること）。

**このリンクは変更に追随しない。** カレンダーの自動更新を必要とするユーザーには、メール添付の `.ics`（8.1）を使ってもらう。**リンクは即時性のための補助手段であり、`.ics` が主である。**

## 9. 予約の状態遷移

承認フローが存在しないため、状態は2つのみである。

| 遷移 | 契機 | 備考 |
|---|---|---|
| （なし）→ 確定 | ユーザーの予約確定、または管理者のシートへの行追加 | 承認を挟まず即時確定する |
| 確定 → 確定 | 内容変更 | **予約IDは変更しない。** 操作履歴に差分を記録する |
| 確定 → キャンセル | ユーザーまたは管理者によるキャンセル | 行は削除せず状態列を変更する |
| キャンセル → 確定 | **発生させない** | 再度利用する場合は新規予約として扱う |

**「キャンセル → 確定」を明示的に禁止すること。** 予約一覧の抽出条件に「状態が `確定`」を含めているため（システム要件2.4）、正常な導線からは到達しない。ただし古い postback から到達しうるため、変更・キャンセルの処理側で**対象の予約が `確定` であることを検証すること。**

## 10. 設定値とタイムゾーン

### 10.1 設定値の読み込み

**設定値はリクエストごとにシートから読む。** キャッシュを跨いで保持すると、管理者が設定を変更しても即座に反映されず、G-A2（自分で変更できる）の体感を損なう。ただし**1リクエスト内では1回だけ読み、以降はメモリ上の値を使うこと**（3.1）。

**不正な値の扱い** — 不正な値を検出した場合は、**既定値で動作を継続し、設定シートの警告列に内容を記入する**。設定ミスでシステム全体が停止する状態にはしない。

**「不正」の基準は項目ごとに異なる。共通のバリデータで一律に判定してはならない。**

| 項目 | 許容する値 | 既定値 |
|---|---|---|
| `受付締切（分前）` | **`0` 以上**の整数 | `0` |
| `予約可能日数` | `1` 以上の整数 | `60` |
| `時間の刻み（分）` | `1` 以上の整数 | `30` |
| `最短予約時間（分）` | `1` 以上の整数 | `30` |
| `人数の初期値` | `1` 以上の整数 | `6` |
| `管理者通知先メール` | 1件以上のメールアドレス（カンマ区切り） | — |

**`受付締切（分前）` の `0` は正当な値である。** 既定値そのものが `0` であるため、これを不正値として扱うと、正常な状態で毎リクエスト警告が書き込まれ続ける。さらに、フォールバック先を `60` などに置いた実装では、**開始1時間以内の予約が全て拒否され、直前予約を可能にした設計（運用要件1.4）が丸ごと無効化される。** 症状は「なぜか直近の時刻が候補に出ない」としてしか現れないため、原因の特定が極めて困難になる。

他の5項目は `0` を許容しない（刻み `0` 分、予約可能 `0` 日などは意味を成さないため）。**この違いを見落とさないこと。**

**項目名が見つからない場合も同様に扱う。** 項目名の文字列が想定と一致しないと、全項目が既定値のまま動作し、管理者は「変更したのに反映されない」という状態に陥る。**見つからなかった項目名を警告列に列挙すること。**

### 10.2 タイムゾーン

**`Asia/Tokyo` に固定する。** スプレッドシートの設定と、Apps Script プロジェクトの設定（`appsscript.json` の `timeZone`）の両方を明示的に揃えること。片方だけの設定では日付がずれる。

**タイムゾーンを設定シートの項目としないこと。** 設定シートに置いても実際には効かず、3箇所の設定が食い違う原因になる。

日付・時刻を文字列で保持する設計により、タイムゾーン設定の影響範囲は**現在時刻の取得と日付計算のみ**に限定される。ただしその2つは受付締切の判定（3.4 手順0）と予約可能日数の判定の根幹であるため、設定の正確さは依然として重要である。**タイムゾーンがずれると、締切判定が数時間単位で狂う。**

## 11. 開発とデプロイ

### 11.1 ソース管理

**`clasp` によるローカル同期を前提とする。** ブラウザの Apps Script エディタで直接編集する運用は、変更履歴が追えず、複数人での作業もできない。

コンテナバインドスクリプトであるため、`clasp clone` にはスプレッドシートに紐づくスクリプトIDが必要である。**プロジェクト作成時に取得し、記録しておくこと。**

Flex Message の JSON はコード内の文字列リテラルではなく、独立したファイルとして管理すること。長大な JSON をコードに埋め込むと可読性が著しく低下する。

### 11.2 デバッグの制約

**`doPost(e)` は Apps Script エディタから直接実行できない。** イベントオブジェクト `e` を自前で組み立てる必要がある。テスト用の `/dev` URL は Google 認証を要求するため、LINE プラットフォームからは叩けない。

したがって開発サイクルは以下になる。

1. コードを修正し、`clasp push`
2. 「デプロイを管理」から既存デプロイのバージョンを更新（URL は維持される）
3. スマートフォンの LINE アプリで操作して確認
4. Apps Script の実行ログで結果を確認

**このループは遅い。** 空き判定などのロジック部分は、イベント処理から分離し、**エディタから直接呼び出せる純粋な関数として実装すること。** そうすればロジックの検証をデプロイなしで行える。この分離は設計上の要請である。

### 11.3 初期データ

**開発の着手には初期データが必要である。** 部屋マスタ・営業時間・設定シートが空では、Webhook を通した動作確認が一切できない。

運用要件6章の T-9・T-10・T-11 は未確定だが、**開発中は仮の値を置いて進めること。** 確定した時点で差し替える。

| シート | 開発中の仮データ |
|---|---|
| 部屋マスタ | 大会議室×1（定員空欄）、12人部屋×2（定員12）、6人部屋×5（定員6）、個人ブース×4（定員1）。部屋名・IDは仮名でよい |
| 営業時間 | 月〜金：稼働、`09:00`-`18:00` ／ 土日：非稼働 |
| 設定 | **受付締切 `0` 分前**、予約可能日数60、時間の刻み30分、最短予約時間30分、人数の初期値6 |
| 部屋別予約可能時間 | 空（定例枠の実内容は T-12 で未確定）。**複数区間の動作確認のため、テスト用に1件は入れること** |

### 12.1 実装着手前に実機で検証すべき事項

| # | 検証内容 | 状態 |
|---|---|---|
| V-1 | GAS ウェブアプリの `/exec` は POST に対してリダイレクトを返す。**LINE の Webhook がこれを追従し、正常に処理されるか** | **✅ 通過**（2026-08-09） |
| V-2 | **クエリパラメータ付きの URL を Webhook URL に設定でき、`doPost` の `e.parameter` で受け取れるか** | **✅ 通過**（2026-08-09）。秘密トークンによる検証方式が成立することを確認 |
| V-3 | 空の `events` を持つリクエスト（コンソールの「検証」ボタン）で例外を起こさないか | **✅ 通過**（2026-08-09） |
| V-4 | Flex Message で18個の時刻ボタンと12室の一覧が、サイズ上限内に収まるか | **✅ 通過**（2026-08-10）。単一バブルの縦並びで表示できることを実機で確認 |
| V-5 | カレンダー追加リンクが実機で正しく開き、日時がずれずに事前入力されるか。`openExternalBrowser=1` が動くか | **✅ 通過**（2026-08-10） |
| V-6 | GAS から `CalendarApp` でカレンダーを作成・書き込み・共有できるか | **✅ 通過**（2026-08-10）。`setUpCalendar()` で作成し、作成・更新・削除の同期を確認 |
| V-7 | `.ics` の作成・変更・キャンセルが Google／Outlook の両方で動くか | **✅ 通過**（2026-08-10）。初回検証で不備を検出し、行の折り返し・`RSVP=TRUE`・UTC 表記に修正のうえ再検証 |

**V-1〜V-7 のすべてが通過した。** 実装方式の前提と、外部連携（カレンダー・メール・LINE 表示）の成立が実機で確認されている。
**各項目の詳細**

- **V-4** — Flex Message には JSON サイズと構成要素数の上限がある。収まらない場合、時刻を午前・午後に分割するなどの設計変更が必要。
- **V-5** — URL の仕様はサービス側の都合で変わりうる。特に**タイムゾーンの取り違えは9時間ずれとして表面化する**ため、必ず実際の端末で確認すること（Google／Outlook、iOS／Android）。
- **V-6** — 共有方法はグループウェアに依存する（運用要件 T-17・T-18）。書き込み自体は環境非依存で動くはずだが、権限の初回承認が必要。
- **V-7** — 作成・変更・キャンセルの3パターン × Google／Outlook の2クライアントで確認する。**更新・キャンセルが反映されないと、個人カレンダーに古い予定が残り続ける。** しかも `SEQUENCE` の扱いを誤ると無言で無視されるため、検証しないと気づけない。挙動差が大きい場合は、カレンダー追加リンク（8.2）を主手段に切り替える判断が要る。

### 12.1.1 検証で判明した運用上の注意

**`clasp push` はデプロイ済みのウェブアプリに反映されない。** デプロイは特定のバージョンに固定されており、`push` が更新するのは HEAD だけである。**コードを変更したら、デプロイを更新して新しいバージョンを割り当てること。** これを忘れると「直したはずなのに挙動が変わらない」状態になる。

**`clasp login` のコールバックはローカルポートで受ける。** 実行環境によっては `localhost` からそのポートに到達できないことがあり、その場合 `ERR_CONNECTION_REFUSED` となる。**認証は開発者自身のターミナルで実行すること。**

**Windows の PowerShell では実行ポリシーにより `clasp.ps1` が拒否される場合がある。** その場合は `clasp.cmd` を使う。実行ポリシーの変更は不要。

### 12.1.2 実装中に判明した事項

いずれも**例外を出さずに壊れる**種類の問題である。実装時に検出し、対処済み。

**スプレッドシート自身のタイムゾーンは、`appsscript.json` の設定とは別物である。** 既定のままだと時差分ずれた値が返り、`TODAY()` も別の日を指す。**両方を `Asia/Tokyo` に揃えること**（10.2）。自己診断（`selfCheck`）で検査する。

**列の書式固定は、初期構築時に予備行へまとめて掛けるだけでは不十分である。** 予備行を使い切った後に追加される行には書式が付かず、そこから静かに壊れ始める。**値を書き込む直前に、その行の書式を固定すること。** 順序が逆だと変換された後になり手遅れになる。

**Apps Script は複数ファイルを1つのスクリプトとして順に評価する。** トップレベルの `const` で他ファイルの定数を参照すると、評価順によっては未初期化で `ReferenceError` になる。**ファイルをまたぐ値は、関数の内側から参照すること。**

**`onEdit` トリガーの関数名を `onEdit` にしないこと。** 簡易トリガーとしても起動して1回の編集で2回走り、しかも簡易トリガー側は認可が要る操作（メール送信・カレンダー・外部通信）を実行できない。別名にしてインストーラブルトリガーとして登録する（6.1）。

**GAS ウェブアプリの `/dev` URL（テスト用のデプロイ）は常に Google のログインを要求する。** アクセス設定を「全員」にしても変わらない。**LINE の Webhook には `/exec` の URL を設定すること。**

**LINE Developers の「検証」ボタンは `302 Found` を失敗と表示する。** GAS のウェブアプリは必ずリダイレクトを返すため、これは正常である。実際の配信はリダイレクトを追従する（V-1）。**動作確認は実機からメッセージを送って行うこと。**

### 12.2 受容した制約

| 制約 | 内容 |
|---|---|
| 署名検証ができない | URL 漏洩時に他人の予約を破壊されうる（2.2） |
| 変更前の値が取得できない場合がある | 複数セル編集時、操作履歴の差分が記録できない（6.4） |
| 行削除を検知できない | 削除された予約は履歴も通知も残らない（6.5） |
| 開始時刻を過ぎた予約をユーザーが操作できない | 受付締切 `0` の帰結。利用中の部屋を早めに返す導線はない（運用要件3.4） |
| 進行中の30分枠は誰も予約できない | 30分刻みかつ「開始時刻が現在時刻以降」であるため、10:17時点で最も早い開始時刻は10:30になる。「今この瞬間から使う」ことはできない |
| 個人カレンダーへの登録は1クリックを要する | メール添付の `.ics` をユーザーが開く操作が必要（8.1）。**ただし一度登録すれば、以後の変更・キャンセルは自動で反映される** |
| LINE の追加リンクは変更に追随しない | 8.2 のリンクは補助手段であり、自動更新は `.ics` 経由でのみ機能する |
| 送信済みの追加リンクは無効化できない | 古いメッセージのリンクは外部サービスへの URL であり、確定処理の再判定（システム要件2.8）が効かない。キャンセル済みの予約のリンクを後から押すと、存在しない会議の予定が個人カレンダーに入る |
| 共有カレンダーは一方向のみ | カレンダー側で直接作成・編集された予定は予約データに反映されない（5.4） |
| 共有カレンダーに載るのは「予約」のみ | 定例枠・臨時ブロック・営業時間外はカレンダーに現れない。**カレンダー上で空いて見える枠が、実際には予約不可である場合がある**（5.4）。正確な空き状況は LINE の空き状況照会で確認する必要がある |
| 行削除は共有カレンダーに孤児予定を残す | 回復手段がない。運用での回避に依存する（6.5） |
| 自動テストが書きにくい | GAS の制約。ロジックの分離（11.2）で緩和する |
