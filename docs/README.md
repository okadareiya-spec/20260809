## この仕様の要点

- 対象は社内の会議室12室。自社運用、専任の管理担当を置かない
- ユーザーは **LINE の会話形式**で予約・確認・変更・キャンセルを行う
- 管理者は **スプレッドシートのみ**で運用する。管理者向けの LINE 機能は作らない
- 実装方式は **Google Apps Script 単体**。排他制御（LockService）とシート編集検知（onEdit）が決め手
- 予約は**即時確定**。承認フローはない
- **受付締切を設けない**（既定値 `0` ＝開始時刻まで受付）。会議室には準備が不要であるため。これにより予約フローは1本で済み、当日の直前予約も同じ導線で扱える（01の1.4）
- **LINE の push 通知を一切使わない。** ユーザーへの通知は、本人の操作への応答（reply）と**メール**で完結する。無料プランの通知上限が制約にならない
- **カレンダー連携を3経路持つ**（01の1.5）。**メール添付の `.ics`**（主。変更・キャンセルが個人カレンダーに自動反映される）、**LINE 上の追加リンク**（補助）、**共有カレンダーへの同期**（全社の俯瞰。管理者が新規予約を把握する手段でもある）
- **管理者への新規予約メール通知は行わない。** 1日最大192件になりうるため。管理者は共有カレンダーで把握する

## 実装者への注意

**「書かれていないこと」を補って実装しないこと。** 各文書には「やらないこと」「意図的に持たせないゴール」「未確定事項（TBD）」の節がある。これらは判断の結果として意図的に空けてある箇所であり、独断で埋めてはならない。

特に以下は、一見すると穴に見えるが**仕様どおり**である。

- **「今すぐ使う」のような即時予約専用フローを作らないこと**（01の1.3・1.4）。締切がないため通常フローで足りる
- 開始時刻を過ぎた予約をユーザーが操作できないこと（01の3.4）
- 満室時に収容できない部屋を代替提示しないこと（01の5.4）

**受付締切 `0` を「締切なし」と解釈しないこと。** `0` は「開始時刻そのものが締切」という意味であり、既に始まった枠への予約を防ぐ判定は必ず実装する（03の3.4）。設定値を `60` に変えれば同じ判定式のまま締切が復活する形にすること。

**`.ics` の `UID` は予約IDから作り、絶対に変えないこと。`SEQUENCE` は更新のたびに加算すること**（03の8.1）。UID が変わると元の予定が残ったまま重複し、SEQUENCE を加算しないと**更新もキャンセルも無言で無視されます**。実機検証項目 V-7 に含めてあります。

**カレンダー追加リンクに `ctz=Asia/Tokyo` を必ず付けること**（03の8.2）。省略すると日時が UTC として解釈され、**予定が9時間ずれて登録されます**。実機での確認項目に含めてあります（03の12.1 V-5）。

**予約IDの採番・検証・操作履歴・カレンダー同期は、Bot 経路と `onEdit` 経路の両方から呼ばれる共通処理として実装すること**（03の5.1）。`onEdit` は Apps Script 自身の書き込みでは発火しないため、`onEdit` 側にだけ実装すると**ユーザー経由の予約でこれらが一切走りません**。

**実機検証 V-1〜V-7 はすべて通過している**（03の12.1）。仕様を変更する場合は、該当する検証項目を再実行すること。

**コードを変更したら、必ずウェブアプリを再デプロイすること。** `/exec` はデプロイした時点のバージョンを実行し続けるため、`clasp push` だけでは LINE 側の挙動は変わらない（03の12.1.1）。
