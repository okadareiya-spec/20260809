## 1. 概要とスコープ

### 1.1 目的

社内の会議室12室について、**社員が LINE 上で予約・確認・変更・キャンセルを完結できる**状態をつくる。予約データは Google スプレッドシートに保持し、**管理者はそのスプレッドシートを管理画面として運用する**。

専任の管理担当を置かず、月額の固定費を発生させないことを前提条件とする。

### 1.2 対象範囲

- LINE 公式アカウントを通じた、社員向けの予約・確認・変更・キャンセル機能
- 会議室の空き状況照会
- スプレッドシートによる予約データの保持と、管理者による直接運用
- 部屋・営業時間・定例枠・臨時ブロック・予約ルールの、管理者による設定
- **予約の作成・変更・キャンセルを、予約者へメールで通知すること**（`.ics` ファイルを添付する）
- 管理者が予約を操作した際の、当該ユーザーへの通知
- ユーザーの登録情報（氏名・メールアドレス）の更新
- **予約を個人のカレンダーへ登録する手段の提供**（メール添付の `.ics`、および LINE 上の追加リンク）
- **全予約を共有カレンダーへ同期し、週間・月間の俯瞰を可能にすること**

### 1.3 やらないこと（スコープ外）

**以下は意図的に実装しない。** 本文に記載がないことを理由に、実装者が補って作ってはならない。

| 実装しないもの | 理由 |
|---|---|
| **新規予約の管理者へのメール通知** | **共有カレンダーで同じ情報が得られるため不要。** 12室 × 1日16枠なら理論上192件/日となり、全件をメールで流すと管理者の業務に支障が出る。管理者は共有カレンダーを見れば把握できる（G-A8） |
| **LINE の push 通知** | **本システムは push を一切使わない。** ユーザーへの通知は、本人の操作への応答（reply）とメールで完結する。これにより無料プランの通知上限が制約にならない |
| **「今すぐ使う」等の即時予約専用フロー** | 受付締切を設けないため、通常の予約フローで当日・直前の予約ができる。専用フローは不要であり、期待と挙動の食い違いを生むだけである（1.4参照） |
| LINE によるリマインダー通知（前日・当日の自動通知） | **カレンダー連携で代替する**（1.5）。LINE の push 通知は無料枠を消費するが、カレンダーアプリ自身の通知機能なら無料かつユーザーが自分で調整できる |
| 繰り返し予約（毎週◯曜など） | 実装量が提供価値に見合わない。定例枠は管理者の予約可能時間設定で代替する |
| 予約の承認フロー | 予約は即時確定とする |
| 利用実績レポート・稼働率の集計 | 第1版のスコープ外。データは後から集計可能な形で蓄積する |
| 空予約（押さえたまま使わない）の検知・抑止 | 現在の運用課題として顕在化していない |
| 管理者向けの LINE インターフェース | 管理者の操作手段はスプレッドシートのみとする |
| 部屋の用途制限（例：大会議室は少人数利用を禁止） | 第1版では不要 |
| LIFF による Web フォーム | UI は LINE 内の会話形式で完結させる |
| 特定用途のための予約枠の取り置き | 全ての部屋を同じ規則で扱う |
| 予約と予約の間のバッファ時間 | 第1版では設けない。将来の拡張余地は残す |
| **個人カレンダーへの API 連携（OAuth による自動書き込み）** | ユーザーごとの OAuth 認証と、LINE userId とアカウントの紐付けが必要になる。Outlook 環境では別の OAuth を二重に実装することになり、第1版には重すぎる。**追加リンク方式で代替する**（1.5） |
| 共有カレンダー側からの逆方向の取り込み | カレンダーで直接作成・編集された予定を予約データに反映することはしない。同期は Bot → カレンダーの一方向のみ |
| 多言語対応 | 日本語のみとする |
| 決済・課金 | 対象外 |
| 1人あたりの予約数上限、キャンセルのペナルティ | 設けない |

### 1.4 受付締切を実質的に設けない理由（設定値を `0` とする）

**本システムは、受付締切の設定値を `0` とする。** 開始時刻を過ぎていない枠であれば、直前であっても予約できる。

**「締切を設けない」＝「開始時刻の判定が不要」ではない。** 締切 `0` は「開始時刻そのものが締切」という意味であり、**既に始まった枠を予約・変更・キャンセルできないようにする判定は必ず残る。** この判定を省くと、古い操作から過去の枠へ予約が入る。

受付締切が必要になるのは、提供側に準備が発生する業種（美容室、飲食店など）である。**会議室には準備が要らない。** 部屋が空いていればその場で使える。管理者も通知を受け取るだけで、予約に対して事前に何かを行うわけではない。したがって、締切を設ける合理的な根拠が存在しない。

締切を設けないことで、以下が同時に達成される。

- 当日の急な打合せに対応できる（人数を問わない）
- 「今すぐ使う」ための専用フローが不要になる
- 予約の作成・変更・キャンセル・一覧表示に、締切を巡る例外規則が一切生じない

**なお受付締切は設定シート上の数値として保持し、既定値を `0`（開始時刻まで受付）とする。** 運用してみて直前予約が問題を生むようなら、管理者が値を変更するだけで締切を復活させられる。仕様上の分岐は増やさず、設定値だけで調整できる形にしてある。

### 1.5 カレンダー連携の方針

**目的の異なる2つの機能を設ける。混同しないこと。**

| 機能 | 目的 | 仕組み |
|---|---|---|
| **`.ics` の添付メール** | **個人**の予定表に予約を入れる。**LINE によるリマインダー通知の代替**となる | 予約の作成・変更・キャンセル時に、予約者へメールを送り `.ics` ファイルを添付する |
| カレンダー追加リンク | 同上（`.ics` が意図どおり動かない環境への保険、および即時性） | 予約完了時に、予定作成画面が事前入力された状態で開く URL をボタンとして LINE 上に出す |
| 共有カレンダー同期 | **全社**の会議室予定を、週間・月間で俯瞰する。**管理者が新規予約を把握する手段でもある**（G-A8） | Bot から1つの Google カレンダーへ全予約を書き込む。社員はそれを購読する |

**`.ics` の添付メールを主とする理由** — カレンダー追加リンクだけでは、**予約を変更・キャンセルしてもユーザー個人のカレンダーが直らない**。`.ics` であれば、同一の識別子で更新通知を再送すれば予定が書き換わり、キャンセル通知を送れば予定が削除される。**追加リンク方式の最大の弱点を構造的に解消できる。**

リマインドの目的は、いずれの方式でも **カレンダーアプリ自身の通知機能** で達成される。ユーザーが通知タイミングを自分で調整できる利点もある。

**`.ics` の更新・キャンセル通知の挙動には、クライアントによる差がある。** Outlook では確実に動くが、Google カレンダー（特に Gmail 経由）では挙動が異なる場合がある。実装着手時に実機で検証すること（技術仕様書 V-7）。カレンダー追加リンクを併存させるのは、この不確実性への保険でもある。

**個人カレンダー（メール経由）と共有カレンダー（自動同期）は別物である。** 混同しないこと。

**共有カレンダーに載るのは「予約」だけである。** 定例枠・臨時ブロック・営業時間外は同期されないため、**カレンダー上で空いて見える枠が、実際には予約不可である場合がある。** 正確な空き状況は LINE の空き状況照会で確認する必要がある。この制約を社員に周知すること。

**共有カレンダーは、社内のグループウェアが未確定でも実装できる。** 書き込み先は Bot を動かす Google アカウントのカレンダーであり、社内環境に依存しない。分岐が生じるのは閲覧方法のみである。

| 社内環境 | 社員の閲覧方法 | 新規予約の反映 |
|---|---|---|
| Google Workspace | カレンダーIDによる組織内共有。**最も安全** | **即時** |
| Microsoft 365 / Outlook | 公開 iCal URL を購読する（Outlook の標準機能） | **最大24時間程度の遅延** |
| 混在・その他 | 同上。iCal 購読はほぼ全てのカレンダーアプリが対応する | 同上 |

**反映の速さが G-A8 の充足に直結する。** 管理者は新規予約を共有カレンダーで把握する設計であるため、**iCal 購読では「リアルタイムに把握できる」を満たせない。** 購読側のポーリング間隔はこちらから制御できず、Google カレンダーの外部カレンダー購読は数時間から24時間程度の遅延が生じる。

したがって **G-A8 を満たすには、Google Workspace での組織内共有が事実上の前提**となる。Microsoft 365 環境を選ぶ場合、G-A8 は「リアルタイムに把握できる」から「翌日までに把握できる」へ格下げされることを、判断時に認識すること（T-17）。

**公開 iCal URL は、URL を知っていれば誰でも閲覧できる。** 予約者氏名が含まれるため、URL の秘匿が前提となる。Google Workspace 環境であれば組織内共有で閉じられるため、この方法を優先すること（未確定事項 T-17・T-18）。

**同期は Bot からカレンダーへの一方向のみとする。** カレンダー側で直接作成・編集された予定を予約データへ取り込むことはしない。双方向にすると、スプレッドシートとカレンダーの2つが編集元になり、整合の維持が困難になる。

## 2. 用語定義

**本章は3文書に共通して適用される。** 解釈が割れやすい語を意図的に集めている。

| 用語 | 定義 |
|---|---|
| ユーザー | 会議室を利用する社員。LINE 公式アカウントを友だち追加した者 |
| 管理者 | 会議室の運用を担う社員。複数名・兼任であり、**操作手段はスプレッドシートのみ** |
| 部屋 | 予約の対象となる会議室・ブース。本仕様における唯一のリソース単位 |
| 定員 | 部屋が収容できる人数。**空欄は「制限なし」を意味する**（大会議室が該当） |
| 枠 | 30分刻みで区切られた時間の単位。1件の予約は、連続する1つ以上の枠を占める |
| 営業時間 | **会社全体**の稼働帯。曜日ごとに稼働日か否かと開始・終了時刻を持つ |
| 部屋別予約可能時間 | **部屋ごと・曜日ごと**の予約可能な区間。営業時間との論理積（狭い方）が有効範囲となる。1つの曜日に複数の区間を持てる |
| 定例枠 | 定例会議などで恒常的に使用され、予約できない時間帯。**データとしての実体を持たず、部屋別予約可能時間の区間と区間の隙間として表現される**。「臨時ブロック」シートは使わない |
| 臨時ブロック | 工事・貸切・全社休業など、**特定の日付**を指定して予約不可にする設定 |
| 受付締切 | 予約・変更・キャンセルを受け付ける限界。開始時刻の何分前かで指定する。**既定値は `0`（開始時刻まで受付）** |
| 指名 | ユーザーが部屋を明示的に選んで予約すること |
| おまかせ割当 | 部屋を指定せず、システムが自動で部屋を決めること。人数を収容できる空室のうち定員が最小の部屋が選ばれる |
| 予約名 | 会議の名称。ユーザーの任意入力。未入力時は「〈氏名〉の予約」が自動生成される |
| 確定 | 予約が成立している状態。承認フローがないため、予約はすべて即時にこの状態になる |
| キャンセル | 予約が取り消された状態。**行は削除せず、状態列の値で表現する** |
| 代理予約 | 管理者がスプレッドシートに直接行を追加して登録する予約 |
| 初回登録 | ユーザーが最初に Bot を操作した際に、氏名とメールアドレスを一度だけ登録する手順。**予約フローとは独立している** |
| 登録情報 | 利用者マスタに保持する氏名とメールアドレス。**初回登録の後も変更できる** |
| カレンダー追加リンク | 予約完了時に LINE 上へ出す、カレンダーの予定作成画面を事前入力状態で開く URL。**自動登録ではなく、変更にも追随しない補助手段**。自動反映が必要な場合は `.ics` を使う |
| 共有カレンダー | 全予約を書き込む Google カレンダー。社員が週間・月間の空き状況を俯瞰するために購読する。**同期は Bot からの一方向のみ** |
| 設定シート | 予約ルールの数値を保持するシート。管理者が値を書き換えることでルールが変わる |
| 応答メッセージ（reply） | ユーザーの発言に対する返信。無料・無制限だが、**発言者本人にしか送れない** |
| プッシュ通知（push） | システム側から任意のユーザーへ送るメッセージ。無料枠に上限がある。**本システムでは使用しない**（1.3） |
| `.ics` | iCalendar 形式のファイル。メールに添付するとカレンダーへ登録でき、**同一の識別子で再送すれば予定の更新・削除も反映される** |

## 3. 利用者要件（ユーザー）

ユーザーとは、会議室を利用する社員を指す。LINE 公式アカウントを友だち追加した者が対象。

### 3.1 ユーザーのゴール

**上位ゴール** — 使いたい会議室を LINE 上の数タップで確実に押さえ、予定が変わったら自分で手放せる。

| ID | ゴール | 満たされている状態 |
|---|---|---|
| G-U1 | 最小手数で予約を完了できる | 新規予約が、日付選択から確定まで一本道で完了する |
| G-U2 | LINE だけで完結する | ブラウザ・PC・他の社内システムを開かずに、予約・確認・変更・キャンセルができる |
| G-U3 | 初回から説明なしで使える | マニュアルを読まずに、最初の予約を完了できる |
| G-U4 | 当日・直前でも予約できる | 急な打合せが決まった際、**人数を問わず**、開始時刻の直前まで空いている部屋を押さえられる |
| G-U5 | 人数に合った部屋を選べる | 利用人数を伝えるだけで、収容可能な部屋だけが提示される |
| G-U6 | 再入力が不要 | 初回登録を済ませた後は、氏名とメールアドレスの入力を求められない |
| G-U7 | 自分の予約を確認できる | いつ・どの部屋を・何時から押さえているかを、いつでも参照できる |
| G-U8 | 自分で変更・キャンセルできる | 管理者に依頼せず、自分の予約を変更・取り消しできる |
| G-U9 | 希望が埋まっていても代替が分かる | 希望の部屋が埋まっている場合、同じ時間帯で空いている他の部屋が提示される |
| G-U10 | 予約者が分かり交渉できる | 埋まっている枠について、予約者の氏名と予約名を確認できる |
| G-U11 | 二重予約が起きない | 同じ部屋・同じ時間帯に2件の予約が成立することがない |
| G-U12 | 予約を自分の予定表に入れられ、変更も追随する | 予約時にメールで届く `.ics` から自分のカレンダーへ登録でき、**予約を変更・キャンセルすると個人のカレンダーにも反映される**。予約を忘れないという目的は、カレンダーアプリ自身の通知機能で満たされる |
| G-U13 | 週間・月間の**予約状況**を俯瞰できる | 共有カレンダーを購読することで、使い慣れたカレンダーアプリから会議室の予約を一覧できる。**定例枠・臨時ブロックは同期されないため、「空き状況」の完全な把握はできない**（1.5） |
| G-U14 | 登録情報を後から直せる | 初回登録した氏名・メールアドレスを、自分で変更できる。**変更手段への導線が、探さなくても見つかる状態にあること** |
| G-U15 | 操作の途中でやめられる | どの手順からでも中断して別の操作に移れる。**その手段が画面上に見えていること。** 予約の途中で空き状況を確認したくなる、といった中断は日常的に起きる |

**意図的に持たせないゴール**（実装者はこれらを満たそうとしないこと）

| 除外したゴール | 理由 |
|---|---|
| 使わなくなった枠を手放しやすくする | 空予約は現在の運用課題ではないため（4.1の同名の除外ゴールと対で除外） |
| LINE で予約のリマインドを受け取る | **カレンダー連携（G-U12）で代替する。** LINE の push 通知は無料枠を消費するが、カレンダーアプリの通知なら無料で、タイミングもユーザーが自分で決められる |
| 定例会議を毎回入力しなくて済む（繰り返し予約） | 管理者が定例枠を塞ぐ運用（G-A4）で代替する |
| 希望時間帯が埋まっているとき別の時間帯を提案する | 実装量が提供価値に見合わないため。別の「部屋」の提示（G-U9）のみ行う |
| 利用中の部屋を早めに手放す | 開始時刻を過ぎた予約は操作できない（3.4）。空予約対策をスコープ外としているため、これも行わない |

### 3.2 想定利用シーン

| シーン | 内容 | 主に関係するゴール |
|---|---|---|
| S-1 計画予約 | 数日〜数週間先の会議のために部屋を押さえる | G-U1, G-U5 |
| S-2 当日利用 | 急な打合せが決まり、今日これから使う部屋を押さえる | G-U4 |
| S-3 予定変更 | 会議の日時がずれた、または中止になった | G-U7, G-U8 |
| S-4 空き確認のみ | 予約はせず、特定の日時に空きがあるかだけ調べる | G-U9, G-U10 |
| S-5 交渉 | 使いたい枠が埋まっているため、予約者に直接掛け合う | G-U10 |

**S-2 は会議室予約に固有かつ頻度が高い。** 受付締切を設けないことで、通常の予約フローがそのまま S-2 に対応する（1.4）。**そのための専用フローを設けてはならない。** 代わりに、日付選択で「今日」「明日」を1タップで選べるようにし、開始時刻の一覧では直近の時刻が先頭に来るようにすることで、手数を実質的に短縮する。

### 3.3 ユーザーができること／できないこと

**できること**

- 氏名とメールアドレスを初回登録する
- **登録した氏名・メールアドレスを後から変更する**
- **どの手順の途中でも操作をやめ、別の操作に移る**（初回登録の途中を含む）
- **登録する前に使い方を読む**
- **予約完了時に、カレンダー追加リンクから自分の予定表へ登録する**（Google／Outlook）
- 日付・人数・開始時刻・利用時間を指定して予約する
- 部屋を指名して予約する、または部屋を指定せず自動割当で予約する
- **開始時刻の直前まで予約する**（受付締切が既定で `0` のため）
- 指定した日時の空き状況を照会する（予約せずに参照のみも可）
- 自分の予約の一覧と詳細を確認する
- 自分の予約の日時・部屋・予約名・備考・人数を変更する
- 自分の予約をキャンセルする
- 他人の予約について、予約者の氏名・予約名・時間帯・部屋を参照する
- **同一時間帯に複数の部屋を同時に予約する**（同時保有数に上限を設けないため、これは許可された挙動である）

**できないこと**

- 他人の予約を変更・キャンセルする
- 予約可能時間外、稼働日外、ブロックされた枠を予約する
- 予約可能日数（既定60日）より先の予約
- **開始時刻を過ぎた予約の作成・変更・キャンセル**
- 日付をまたぐ予約
- 30分未満、または30分刻みでない時間の予約
- リソース（部屋）の追加・変更・削除
- 営業時間、稼働日、ブロック枠、予約ルールの設定

他人の予約を操作できない以上、変更が必要な場合の導線は **予約者本人への直接交渉、または管理者へのエスカレーション** の2つしかない。前者を成立させるために予約者名の表示（G-U10）が必須である。

**初回登録は、済ませない限り予約も空き状況の照会もできない。** これは制約ではなく設計上の前提である（予約名の自動生成と通知の宛先に必要なため）。**ただし、その旨と所要手数を利用者に伝えること。** 理由を示さずに入力だけを求めると、予約しようとした利用者には「関係のない手続きをさせられている」としか見えない。

### 3.4 開始時刻を過ぎた予約の扱い

受付締切が `0`（開始時刻まで）であるため、**開始時刻を過ぎた予約は、変更もキャンセルもできない。**

利用中の予約は **予約一覧には表示する**（自分が今どの部屋を押さえているかを確認できるようにするため）。ただし変更・キャンセルのボタンを押した場合は、開始時刻を過ぎている旨を伝える。

会議が早く終わって部屋を返したい、という要求は満たさない。空予約の抑止をスコープ外としているため（3.1・4.1の除外ゴール）、この導線は設けない。

### 3.5 達成基準

以下を全て満たしたとき、利用者要件を満たしたと判断する。

1. LINE の友だち追加後、氏名とメールアドレスの初回登録を経て、最初の予約が完了できる
2. 予約・確認・変更・キャンセルの全操作が、LINE アプリ内で完結する
3. 利用人数を入力すると、その人数を収容できない部屋は選択肢に現れない
4. 初回登録の完了後、氏名およびメールアドレスの入力を求められない
5. **開始時刻の直前まで予約できる**（例：現在10:17のとき、10:30開始・3名の予約が成立する）。**当日・直前であることを理由に、人数や部屋に制限がかからない**
6. 日付選択で「今日」「明日」を1タップで選べる
7. 開始時刻の一覧で、既に過ぎた時刻が候補に現れない
8. **自分の未終了の予約が、開始日時の昇順で一覧表示される**（利用中の予約を含む）
9. **一覧から、自分の予約の日時・部屋・人数・予約名・備考を変更できる**
10. **一覧から、自分の予約をキャンセルできる**
11. 他人の予約に対して、変更・キャンセルの操作導線が一切存在しない
12. **部屋を選ぶ場面で、入力人数を収容できる空室が一覧表示される**（希望の部屋が埋まっていても代替が分かる）
13. 空き状況照会において、埋まっている枠には予約者の氏名と予約名が表示される
14. 同一の部屋・同一の時間帯に、重複した予約が成立しない
15. 利用人数を変更した結果、現在の部屋に収容できなくなる場合、その変更が成立しない
16. 予約の作成・変更・キャンセルのそれぞれで、予約者にメールが届き `.ics` が添付されている
17. **予約を変更すると、個人のカレンダーに登録済みの予定も更新される**
18. **予約をキャンセルすると、個人のカレンダーに登録済みの予定も削除される**
19. 予約完了時に、LINE 上でも Google カレンダーと Outlook の追加リンクが提示される
20. 登録した氏名・メールアドレスを、ユーザー自身が変更できる
21. **予約が1件もない状態でも、登録情報の変更に到達できる**
22. **氏名を変更すると、まだ終わっていない自分の予約の予約者氏名と、自動生成された予約名も更新される**
23. 確定した予約が共有カレンダーに反映され、変更・キャンセルも反映される

## 4. 運用者要件（管理者）

管理者とは、会議室の運用を担う社員を指す。以下の前提が本章全体の制約となる。

- **複数名いる**（専任担当者はいない）
- **兼任である** — 会議室運用は本来業務ではなく、操作の頻度は低い
- **操作手段はスプレッドシートのみ** — 管理者は LINE Bot を一切操作しない

3点目が最も強い制約である。**管理者向けの LINE インターフェースは実装しない。スプレッドシートが管理画面そのものである。** 管理者が行う全ての操作は、シート上のセル編集として表現できなければならない。

2点目からは別の要件が導かれる。兼任で操作頻度が低いということは、**前回の操作方法を覚えていない状態で操作する**ということである。シートは、手順書を参照せずとも列の意味と入力方法が分かる状態に保つ必要がある。

### 4.1 管理者のゴール

**上位ゴール** — 専任担当を置かず、スプレッドシートを触るだけで会議室運用を回し続けられる。

| ID | ゴール | 満たされている状態 |
|---|---|---|
| G-A1 | 稼働状況を集計作業なしで把握できる | シートを開けば、当日どの部屋がいつ埋まっているかが一目で分かる |
| G-A2 | 営業時間・稼働日・予約ルールを自分で変更できる | 実装者に依頼せず、シート上の設定変更だけで反映される |
| G-A3 | 部屋の増減・名称変更に自分で追従できる | 部屋の追加・無効化・改名・定員変更が、シートへの行追加や書き換えで完結する |
| G-A4 | 定例枠・臨時の使用不可を自分で設定できる | 毎週の定例枠と、特定日だけの使用不可を、どちらも自分で塞げる |
| G-A5 | 例外対応を自分の手でできる | 代理予約・強制キャンセル・部屋の付け替えを、シート上で実行できる |
| G-A6 | 問い合わせ対応の負荷が下がる | ユーザーが自力で予約・変更・キャンセルを完結し、管理者への依頼が発生しない |
| G-A7 | トラブル時に事実を確認できる | 誰がいつ何を予約・変更・キャンセルしたかを、後から追跡できる |
| G-A8 | 新規予約を把握できる | **共有カレンダーを見れば、入っている予約が分かる。** メールでの都度通知は行わない（1日最大192件になりうるため）。**Google Workspace で組織内共有した場合のみ「リアルタイム」となる**（1.5） |
| G-A9 | システムが止まっても運用を継続できる | Bot が動かなくなっても、シートを見れば当日の予約状況が分かる |
| G-A10 | 運用コストをゼロに保つ | 月額の固定費が発生しない |
| G-A11 | 個人情報を適切に管理できる | 保持している個人情報の範囲が明確で、削除の手段がある |

**意図的に持たせないゴール**

| 除外したゴール | 理由 |
|---|---|
| 空予約（押さえたまま使わない）を減らす | 現在の運用課題として顕在化していないため |
| 会議室が足りているかを判断する（利用実績レポート） | 第1版のスコープ外。ただし後から集計できるよう、データ設計では実績を欠損なく蓄積する |
| 部屋を用途で制限する（例：大会議室は少人数利用を禁止） | 第1版では不要。人数を取得するため、将来的には実装可能 |
| 直前予約を抑止する | 会議室に準備が不要であるため、締切を設けない（1.4）。必要になれば設定値の変更だけで対応できる |

### 4.2 管理者の担当業務

| 頻度 | 業務 | 関係するゴール |
|---|---|---|
| 随時 | 共有カレンダーで予約状況を確認する | G-A8 |
| 随時（依頼契機） | 代理予約を登録する（LINE を使わない利用者、外部来訪者向けなど） | G-A5 |
| 随時（依頼契機） | 予約の強制キャンセル、部屋の付け替えを行う | G-A5 |
| 週次〜月次 | 定例枠を設定・見直す（部屋別予約可能時間の区間調整） | G-A4 |
| 随時 | 臨時ブロックを設定する（工事・貸切・**祝日や全社休業日**） | G-A4 |
| 稀 | 部屋の追加・無効化・改名・定員変更を行う | G-A3 |
| 稀 | 営業時間・稼働日・予約ルールを変更する | G-A2 |
| 稀 | トラブル発生時に操作履歴を確認する | G-A7 |

**祝日・全社休業日の設定について** — 営業時間の設定は曜日単位であり、特定日を非稼働にする機能は持たない。**祝日・年末年始・創立記念日などは、臨時ブロックシートに「部屋ID空欄（＝全部屋）・日付指定・時刻空欄（＝終日）」の行を1行登録することで表現する。** これは正規の運用手段である。

### 4.3 管理者ができること／できないこと

**できること（すべてスプレッドシート上の操作）**

- 予約を直接追加する（代理予約）
- 既存の予約を直接編集する（日時・部屋・予約名・人数・備考の変更）
- 既存の予約をキャンセルする（他人の予約を含む）。**状態列を `キャンセル` に変更する方法で行う**
- **開始時刻を過ぎた予約も編集・キャンセルできる**（受付締切はユーザー操作にのみ適用される）
- 部屋を追加・無効化・改名し、定員を変更する
- 部屋ごとの予約可能時間を、曜日単位で設定する（定例枠の設定を含む）
- 特定日を指定して枠をブロックする（臨時の使用不可・祝日・全社休業）
- 営業時間・稼働日を変更する
- 予約ルールの数値を変更する。設定シート上の項目名は以下で固定される（**この文字列と完全に一致していなければ設定が反映されない**）

  `受付締切（分前）` ／ `予約可能日数` ／ `時間の刻み（分）` ／ `最短予約時間（分）` ／ `人数の初期値` ／ `管理者通知先メール`
- 予約の操作履歴を参照する

**できないこと**

- LINE Bot 経由での管理操作（管理者向けの LINE インターフェースは存在しない）
- Bot のメッセージ文面や会話フローそのものの変更
- ユーザーの LINE アカウントの管理
- タイムゾーンの変更（`Asia/Tokyo` に固定であり、設定項目としても持たない）

**予約行の削除について** — 行を物理削除する操作は技術的に可能だが、**行うべきではない**。削除すると操作履歴が残らず、ユーザーへの通知も送られない。キャンセルは必ず状態列の変更で行うこと。この運用ルールは管理者に周知する必要がある。

### 4.4 管理者の直接編集をどう扱うか

管理者がシートに書いた内容は **正として受け入れる**。重複予約や予約可能時間外といった、通常なら弾かれる内容であっても拒否しない。管理者は例外対応のために意図してそれを行っているためである。

ただし黙って受け入れるのではなく、**異常を検知した行には警告を表示する**。管理者が意図した例外なのか、単純な入力ミスなのかは、管理者本人にしか判断できない。システムの役割は判断ではなく、気づかせることである。

**管理者が予約を変更・キャンセルした場合、予約者へメールで通知する。** 強制キャンセルや部屋の付け替えは、当人が知らないままでは会議に支障が出る。**メールには更新済み／キャンセル済みの `.ics` を添付し、当人のカレンダーも自動で直るようにする。**

**LINE の push 通知は使わない。** ユーザーへの通知手段はメールに一本化する（1.3）。

ただし**「他人の予約かどうか」による通知の出し分けは行わない。** スプレッドシートの編集者は Google アカウントで識別され、予約者は LINE の userId で識別されるため、両者を突合する手段がないからである。代わりに、**通知の対象を「予約の実体を変える列」に限定する**（日付・開始時刻・終了時刻・**部屋ID**・状態）。備考の誤字修正のような編集で通知が飛ぶことを防ぐためである。

**部屋を付け替える際は、部屋ID列と部屋名列の両方を書き換えること。** 予約シートは部屋名を別列として重複保持しているため（G-A9のための意図的な非正規化）、部屋IDだけを直すと、予約一覧・本日の予約ビュー・共有カレンダーに古い部屋名が表示され続ける。**部屋名列だけを直した場合は通知が飛ばない。**

### 4.5 設定値の扱い

予約ルールの数値は、コード内に定数として埋め込まず、**設定シート上のセルとして保持する**。管理者はセルを書き換えるだけでルールを変更でき、実装者を介する必要がない。

**受付締切もこの仕組みの上に載る。** 既定値は `0`（開始時刻まで受付）だが、運用してみて直前予約が問題を生むようなら、管理者が値を変更するだけで締切を復活させられる（1.4）。

管理者が誤った値（空欄、負数、数値以外）を入力する可能性があるため、**不正な値を検出した場合は既定値で動作を継続し、設定シート上に警告を表示する**。設定ミスでシステム全体が停止する状態にはしない。

**警告は必ずスプレッドシート上に表示すること。** 管理者はスプレッドシートしか見ないため、実行ログにのみ記録した警告は永久に読まれない。

### 4.6 達成基準

以下を全て満たしたとき、運用者要件を満たしたと判断する。

1. 管理者が行う全ての運用操作が、スプレッドシート上のセル編集だけで実行できる
2. 管理者向けの LINE インターフェースが存在しない
3. 部屋を1室追加する操作が、行を1行追加するだけで完了し、追加後ただちに予約対象になる
4. 営業時間・稼働日・曜日別の予約可能時間・臨時ブロックが、いずれもシート上の設定で変更できる
5. 祝日・全社休業日を、臨時ブロックの1行追加で設定できる
6. 受付締切・予約可能日数・時間の刻みなどの予約ルールが、設定シート上の値で変更でき、**変更が選択肢の提示内容にも反映される**
7. **受付締切を `0` から `60` に変更すると、開始1時間前を過ぎた予約操作が拒否されるようになる**
8. 設定シートに不正な値が入力された場合も Bot は停止せず、既定値で動作を継続し、**設定シート上に警告が表示される**
9. 管理者がシート上で追加・編集した予約が、Bot 側の空き判定に反映される
10. 管理者の編集によって重複予約や設定外の予約が生じた場合、当該行に警告が表示される
11. 管理者が予約の日時・部屋・状態を変更した場合、予約者にメールで通知が届き、**添付された `.ics` によって当人のカレンダーも更新される**
12. 管理者が備考のみを編集した場合、通知が飛ばない
13. **LINE の push 通知が一度も送信されない**（無料プランの通知上限が制約にならない）
14. 予約の作成・変更・キャンセルについて、実施者と日時が記録され後から参照できる。**これはユーザー経由の予約についても成立する**
15. **管理者がシート上で行った予約の追加・変更・キャンセルが、共有カレンダーにも反映される**
16. 月額の固定費が発生しない
17. **通常運用時に、シートを開けば当日の予約状況が開始時刻順に一覧できる**（G-A1）
18. Bot が停止していても、17 が成立し続ける（G-A9）
19. **予約に関する問い合わせが管理者に発生しない**。ユーザーは予約・変更・キャンセル・登録情報の修正を自力で完結できる（G-A6）
20. 保持している個人情報の範囲が文書化され、特定ユーザーのデータを削除する手順が存在する

## 5. 業務ルール

### 5.1 リソース定義

会議室は全12室。1室を1行として、部屋マスタに定義する。

| 種別 | 室数 | 定員 |
|---|---|---|
| 大会議室 | 1 | 制限なし |
| 12人部屋 | 2 | 12 |
| 6人部屋 | 5 | 6 |
| 個人ブース | 4 | 1 |

**部屋が持つ属性**

| 属性 | 内容 | 変更 |
|---|---|---|
| 部屋ID | 部屋を一意に識別する不変の値。予約データはこれを参照する | 不可 |
| 部屋名 | ユーザーに表示される名称 | 可 |
| 定員 | 収容可能な人数。割当判定に使う。**空欄は「制限なし」を意味する** | 可 |
| 表示順 | **同一定員の部屋が複数ある場合の、選択肢の並び順および割当順序**。一覧の第1ソートキーは定員であり、表示順は第2キーである | 可 |
| 有効 | 新規予約の対象とするか | 可 |

**部屋IDと部屋名を分ける理由** — 部屋を改名しても、過去の予約との結びつきが切れないようにするため。予約データが部屋名を直接持つと、改名した瞬間に過去の予約がどの部屋のものか分からなくなる。

**定員なしの表現** — 大会議室は定員を設けない。部屋マスタの定員列を **空欄にした場合を「制限なし」と定義する**。判定処理では、定員なしの部屋は収容可能人数を無限大として扱う。したがって、どれだけ大きな人数を入力しても大会議室は常に候補に含まれ、おまかせ割当では常に最後に選ばれる。

**部屋の削除は行わず、無効化で表現する。** 過去の予約が部屋IDを参照しているため、行を物理削除すると履歴が壊れる。無効化された部屋は新規予約の選択肢に現れないが、既存の予約はそのまま残り、参照もできる。

**無効化した部屋に将来の予約が残っている場合** — システムは自動でキャンセルも付け替えも行わない。予約はそのまま有効であり、ユーザーは変更・キャンセルできる。**部屋を廃止する際は、管理者が残存する予約を確認し、必要なら手動で付け替えること。** これは運用手順であり、システムは支援しない。

### 5.2 予約可能時間の設定

予約できる時間帯は、3つの階層の設定から決まる。

| 階層 | 設定単位 | 用途 |
|---|---|---|
| 営業時間 | 曜日 | 会社全体の休業曜日と営業帯 |
| 部屋別予約可能時間 | 部屋 × 曜日 | 部屋ごとの利用可能帯。**定例枠はここで塞ぐ** |
| 臨時ブロック | 部屋 × 日付 × 時間帯 | 単発の使用不可。**祝日・全社休業日もここで設定する** |

**ある枠が予約可能である条件** — 以下をすべて満たす場合のみ予約できる。

1. 営業時間の設定上、その曜日が稼働日であり、要求時間帯が営業帯に収まる
2. その部屋の、その曜日の予約可能時間の**いずれか1つの区間に完全に収まる**
3. 臨時ブロックに該当しない
4. 状態が `確定` の既存予約と重複しない
5. 受付期間内である（5.3参照）

設定が競合した場合は **狭い方を採用する**（AND条件）。部屋別の予約可能時間が営業時間より広く設定されていても、営業時間外は予約できない。

**部屋別の予約可能時間は、1つの曜日に複数の区間を持てなければならない。** 定例枠を塞ぐには、これが必須となる。例えば大会議室が毎週火曜の10:00-12:00に定例会議で使われる場合、大会議室の火曜の予約可能時間を `09:00-10:00` と `12:00-18:00` の2区間として登録する。この2区間の隙間が定例枠であり、そこは予約できない。1曜日1区間しか持てない構造では定例枠を表現できない。

**予約は1つの区間に完全に収まる必要がある。** 上の例で 09:30-12:30 の予約は、2区間にまたがるため成立しない（間の定例枠を踏むため当然である）。

### 5.3 受付・変更・キャンセルのルール

| 項目 | 既定値 | 設定シートで変更 |
|---|---|---|
| 予約可能な期間 | 本日から60日先まで | 可 |
| **受付締切** | **0分前（＝開始時刻まで受付）** | 可 |
| 時間の刻み | 30分 | 可 |
| 最短予約時間 | 30分 | 可 |
| 人数の初期値 | 6名 | 可 |
| 最長予約時間 | 開始時刻からその日の営業終了まで | 不可 |
| 日跨ぎ予約 | 不可 | 不可 |
| 1人あたりの同時保有数 | 上限なし | 不可 |
| キャンセルペナルティ | なし | 不可 |

**受付締切は、新規作成・変更・キャンセルに共通で適用する。** 既定値が `0` であるため、実際の意味は「**開始時刻を過ぎた予約は操作できない**」となる。専用フローや例外規則は一切設けない（1.4）。

**受付締切はユーザー操作にのみ適用する。** 管理者のシート直接編集には適用しない。

**変更時の締切判定は、変更前と変更後の両方の開始時刻に対して行う。** どちらか一方でも締切を過ぎていれば、変更を受け付けない。既定値 `0` の場合、これは「既に始まっている予約は変更できない」「過去の時刻へは変更できない」ことを意味する。

**変更の扱い** — 変更は「キャンセル＋新規予約」ではなく、**同一の予約IDを保持したまま内容を更新する**。予約IDが変わると、変更前後の履歴が別物として記録され、追跡できなくなるためである。変更内容は操作履歴に記録する。

**変更時の空き判定における注意** — 予約の時間や部屋を変更する際、変更後の枠が空いているかを判定するが、**このとき変更対象の予約自身を「埋まっている予約」として数えてはならない**。

例えば 10:00-11:00 の予約を 10:00-12:00 に延長する場合、10:00-11:00 の枠は変更対象の予約自身が占めている。これを重複とみなすと、その予約は永久に変更できなくなる。空き判定の対象から、変更対象の予約IDを必ず除外すること。

**人数のみを変更する場合も、定員の判定を行う。** 6人部屋の予約を12名に変更しようとした場合、その部屋では収容できないため**変更を受け付けない**。収容できる部屋を選び直すよう促すこと。人数列だけを更新する実装にしてはならない。

### 5.4 部屋の割当ルール

ユーザーは予約時に、部屋を **指名する** か **おまかせにする** かを選べる。いずれの場合も利用人数の入力を必須とし、入力欄の初期値は設定シートの値（既定6名）とする。

**指名の場合** — ユーザーが部屋を選ぶ。ただし **入力人数を収容できない部屋は選択肢に表示しない**。6名で検索したユーザーに個人ブースを見せない、ということである。

**おまかせの場合** — 入力人数を収容でき、かつ空いている部屋のうち、**定員が最小の部屋**を自動で割り当てる。個人ブース → 6人部屋 → 12人部屋 → 大会議室 の順に埋まるため、大きい部屋が少人数に占有されて後続の大人数予約が入らなくなる事態を防げる。

**定員が同じ部屋が複数空いている場合**は、部屋マスタの **表示順が最も若い部屋** を選ぶ。表示順も同値の場合は、**部屋IDの昇順**で決定する。順序を明示しないと実装ごとに挙動が変わり、再現性のない割当になるため、ここは必ずこの順序で決定すること。

**収容可能な部屋がすべて埋まっている場合**、割り当てられる部屋は存在しない。この場合は予約を受け付けず、その旨を伝える。

**この場面で代替の部屋を提示してはならない。** 収容可能な部屋がすべて埋まっている以上、残っているのは入力人数が入らない部屋だけであり、提示しても予約できないためである。

G-U9（希望が埋まっていても代替が分かる）は、**部屋選択の場面で満たされる。** そこには収容可能な空室が一覧表示されるため、特定の部屋を使いたかったユーザーは、その場で他の空き部屋を確認できる。

なお大会議室に定員がないため、**「人数が大きすぎて収容できる部屋が存在しない」というケースは発生しない**。どれだけ大きな人数を入力しても、大会議室が空いてさえいれば必ず割り当てられる。

### 5.5 登録情報の更新ルール

ユーザーは初回登録した氏名・メールアドレスを、後から自分で変更できる（G-U14）。**想定される最も多い用途は、初回登録時の誤入力の訂正である。**

**氏名を変更した場合、まだ終わっていない自分の予約の予約者氏名も更新する。**

| 対象 | 扱い |
|---|---|
| 終了時刻が現在時刻以降で、状態が `確定` の自分の予約 | **予約者氏名を新しい氏名に更新する。加えて、予約名が旧氏名から自動生成された値である場合は、それも更新する** |
| 終了済み、またはキャンセル済みの予約 | 更新しない。**当時の記録として残す** |

この規則が必要な理由は、予約シートが氏名を予約時点の値としてコピーしているためである（意図的な非正規化）。**更新処理を書かないと、氏名を直しても空き状況照会には古い氏名が表示され続ける。** 予約者氏名は他の社員に表示される情報であり（G-U10）、誤字のまま固定されることになる。

**予約名の更新を見落とさないこと。** 予約名は未入力時に「〈氏名〉の予約」として自動生成される。つまり **氏名の第2のコピーである。** しかも「入力せずに進む」は既定の経路であり、多くの予約がこの形になる。予約名を更新しないと、氏名を直しても **予約名・空き状況照会・本日の予約ビュー・共有カレンダーのタイトルに旧氏名が残り続ける。** ユーザーが手入力した予約名は変更しない。

**メールアドレスの変更は、予約シートへ波及しない。** 予約シートはメールアドレスを保持しないためである。

**共有カレンダーへ同期済みの予定についても更新すること**（1.5）。
