# 会議室予約 LINE Bot ／ 稼働手順書

実装が完了した状態から、実際に社内で使えるようにするまでの手順書です。
**上から順に、飛ばさずに実行してください。** 順序に意味がある箇所には理由を書いています。

作成日: 2026-08-09

---

## 0. この手順書の読み方

**関数の実行場所** — すべて Apps Script エディタです。左側のファイル一覧から `.gs` ファイルを選び、上部の関数プルダウンで関数名を選んで「実行」を押します。実行結果は下部の「実行ログ」に出ます。

**エディタは、コードを更新するたびに再読み込みしてください。** 開いたままだと古いコードが動き続けます。

**所要時間の目安** — 全体で1〜2時間。うち大半は STEP 8（実データの入力）です。

## STEP 1. 共有カレンダーを作る

| 項目 | 内容 |
|---|---|
| ファイル | `core_calendar.gs` |
| 関数 | `setUpCalendar` |
| 外部への作用 | **あり** — あなたの Google アカウントにカレンダーを1つ新規作成します |

### 手順

1. エディタ左のファイル一覧から **`core_calendar.gs`** を開く
2. 上部の関数プルダウンで **`setUpCalendar`** を選ぶ
3. 「実行」を押す
4. 初回は権限の確認画面が出ます。**Google カレンダーへのアクセス**を許可してください
5. 実行ログに出たカレンダーIDを控える

### 確認すること

ログに `カレンダーを作成しました: 会議室予約` と出ること。
2回目以降に実行しても作り直されません（`設定済みです` と出ます）。

### 社員への共有設定

Google カレンダーを開き、左側の「マイカレンダー」に **会議室予約** が増えています。
その「⋮」→「設定と共有」→「特定のユーザーとの共有」または「アクセス権限」から、社員が閲覧できるようにしてください。

**権限は「予定の表示（すべての詳細）」までにしてください。** 編集権限を渡すと、カレンダー側で消された予定が予約シートに反映されず、シートは「予約済み」・カレンダーは「空き」という不整合が起きます。同期は Bot からカレンダーへの一方向だけです。

> **なぜ最初にやるのか** — カレンダーIDが未設定の間は、予約が成立してもカレンダーに載りません。後から設定しても、それ以前の予約は同期されないままです。

## STEP 2. シート編集トリガーを登録する

| 項目 | 内容 |
|---|---|
| ファイル | `core_admin_edit.gs` |
| 関数 | `setUpEditTrigger` |
| 外部への作用 | なし |

### 手順

1. **`core_admin_edit.gs`** を開く
2. 関数プルダウンで **`setUpEditTrigger`** を選ぶ
3. 「実行」を押す

### 確認すること

ログに `編集トリガーを登録しました。` と出ること。

エディタ左端の「トリガー」（時計のアイコン）を開き、**`onReservationEdit` が1件だけ**登録されていることを確認してください。

**複数あったら余分を削除してください。** 同じ関数に複数登録すると、1回の編集で処理が複数回走り、通知が二重に飛びます。`setUpEditTrigger` は既存を消してから作るので、通常は1件になります。

> **これを実行しないとどうなるか** — 管理者がシートに予約を直接書いても、予約IDの採番もカレンダー同期も通知も行われません。行が増えるだけの状態になります。

## STEP 3. 通知とカレンダーの実機検証

| 項目 | 内容 |
|---|---|
| ファイル | `test_notify.gs` |
| 関数 | `verifyNotifyLive` |
| 外部への作用 | **あり** — カレンダーに予定を作成・更新・削除し、メールを3通送ります |

### 手順

1. **`test_notify.gs`** を開く
2. 関数プルダウンで **`verifyNotifyLive`** を選ぶ
3. 「実行」を押す
4. 初回は **Gmail の送信権限**の確認が出ます。許可してください

宛先は設定シートの「管理者通知先メール」です。

### 確認すること — ここは目視が必要です

ログに `OK 予定を作成しました` `OK 予定を 14:00-16:00 に更新しました` `OK 予定を削除しました` が出ること。

そのうえで、**届いた3通のメールを古い順に開いてください。**

| 開く順 | 件名 | 添付を開いた後の期待動作 |
|---|---|---|
| 1通目 | `[検証] 【会議室予約】予約を受け付けました` | カレンダーに予定が**1件追加される** |
| 2通目 | `[検証] 【会議室予約】予約内容を変更しました` | 同じ予定が**更新される**（2件目が増えない） |
| 3通目 | `[検証] 【会議室予約】予約をキャンセルしました` | その予定が**消える** |

**2件目が増えてしまう場合**、`.ics` の `UID` が別物として扱われています。
**3通目で消えない場合**、`SEQUENCE` の加算が届いていません。
どちらもクライアント側の挙動差なので、その場合は結果を共有してください。

**Outlook と Google カレンダーの両方で確認できると理想です。** この2つは `.ics` の扱いが異なり、Outlook は会議招待として確実に反映しますが、Gmail 経由の Google カレンダーは挙動が変わることがあります。

> **なぜ目視が要るのか** — `.ics` の更新・キャンセルが効かないとき、**エラーは一切出ません。** 送信は成功し、受信側が黙って無視するだけです。コードのテストでは検出できません。

## STEP 4. ウェブアプリとして再デプロイする

**ここが最も間違えやすい手順です。**

### なぜ必要か

いま LINE に設定されている Webhook URL は、**疎通検証用の古いコードを実行しています。**
Apps Script のウェブアプリは、`/exec` の URL が「デプロイした時点のバージョン」に固定されるためです。コードを更新しても、**新しいバージョンを作らない限り、古いコードが動き続けます。**

このまま LINE から話しかけると、Bot は「受信しました: 〜」とオウム返しするだけです。

### 手順

1. エディタ右上の **「デプロイ」** ボタンを押す
2. **「デプロイを管理」** を選ぶ（「新しいデプロイ」ではありません）
3. 既存のデプロイが一覧に出ます。右上の **鉛筆アイコン（編集）** を押す
4. **「バージョン」** のプルダウンを開き、**「新しいバージョン」** を選ぶ
5. 説明欄に `本実装 v1` などと入れる
6. 次の2つが正しいか確認する
   - **次のユーザーとして実行**: `自分`
   - **アクセスできるユーザー**: `全員`
7. **「デプロイ」** を押す

### 確認すること

- **ウェブアプリの URL が変わっていないこと。** 「デプロイを管理」から更新した場合、URL は同じままです。これが狙いです
- URL が変わってしまった場合は、STEP 5 で LINE 側の設定も更新する必要があります

> **「新しいデプロイ」を選ぶと URL が変わります。** その場合、LINE Developers 側の Webhook URL も差し替えないと、Bot は動きません。

### アクセス設定の意味

**「アクセスできるユーザー: 全員」は必須です。** LINE のサーバーは Google アカウントを持たない匿名アクセスとして届くためです。
URL 自体は推測不能なトークン付きなので、URL を知らない相手からは操作できません。

## STEP 5. Webhook URL を LINE に設定する

| 項目 | 内容 |
|---|---|
| ファイル | `main.gs` |
| 関数 | `showWebhookUrl` |

### 手順

1. **`main.gs`** を開く
2. 関数プルダウンで **`showWebhookUrl`** を選ぶ
3. 「実行」を押す
4. ログに出た URL をコピーする（`https://script.google.com/macros/s/.../exec?token=...` の形式）

次に LINE Developers コンソール（https://developers.line.biz/console/）を開きます。

5. 該当のチャネル（Channel ID `2011027238`）を選ぶ
6. **「Messaging API設定」** タブを開く
7. **「Webhook URL」** の「編集」を押し、コピーした URL を貼り付けて「更新」
8. **「Webhookの利用」** を **オン** にする
9. **「検証」** ボタンを押す

### 「検証」ボタンの結果は当てにならない

**`302 Found` が返りますが、これは正常です。** GAS のウェブアプリは `/exec` へのアクセスに対して必ずリダイレクトを返す作りで、LINE の「検証」ボタンはリダイレクトを追わないため失敗と表示されます。
**一方、LINE の実際の配信はリダイレクトを追従します。** これは実装前に V-1 として検証済みです。

`401 Unauthorized` が返る場合は本物の問題です。次のどちらかです。

| 原因 | 直し方 |
|---|---|
| URL の末尾が `/dev`（テスト用のデプロイ） | 上の手順で `/exec` の URL に貼り替える |
| アクセスできるユーザーが「全員」でない | STEP 4 に戻って設定を直す |

### 本当の確認方法

**LINE から実際にメッセージを送ってください。**

1. LINE で該当の公式アカウントを開く（未追加なら友だち追加）
2. 何でもよいのでメッセージを1通送る
3. **`メニューから操作を選んでください。` と返ってくれば成功です**
   （キーボードの上にボタンが3つ表示されます）
4. 続けて `予約する` と送ると、初回登録が始まります

反応がない場合は、Apps Script の「実行数」画面（左端のアイコン）を開きます。

| 表示 | 意味 |
|---|---|
| `doPost` の実行が記録されている | 届いています。ログの中身を確認する |
| 何も記録されない | LINE から届いていない。「Webhookの利用」がオンか、応答モードが Bot かを確認 |
| ログに `トークンが一致しません` | URL の `?token=` 以降が欠けている |

> **`?token=` を含めた URL 全体を貼り付けてください。** GAS は HTTP ヘッダーを読めないため、LINE の署名検証が使えません。このトークンが唯一の検証手段です。
> **この URL は社外に出さないでください。** 漏れると、第三者が任意の利用者になりすまして予約の作成・キャンセルができます。

## STEP 6. LINE 公式アカウントの応答設定

自動応答が Bot の返信に混ざるのを止めます。

1. LINE 公式アカウントマネージャー（https://manager.line.biz/）を開く
2. 該当のアカウントを選ぶ
3. 右上の **「設定」** → **「応答設定」**

以下のとおりに設定します。

| 項目 | 設定 | 理由 |
|---|---|---|
| 応答モード | **Bot** | チャットモードでは Webhook が届きません |
| あいさつメッセージ | **オフ** | Bot 側が友だち追加時に氏名の入力を求めるため、二重になります |
| 応答メッセージ | **オフ** | **これがオンだと、Bot の返信と定型文が両方届きます** |
| Webhook | **オン** | オフだとイベントが届きません |

> **「応答メッセージ」のオフを忘れる例が最も多いです。** ユーザーからは「変な返事が混ざる」という形で見えます。

## STEP 7. リッチメニューを登録する

Bot の入口です。3列×2行の6区画を置きます。

### なぜ管理画面から作らないのか

LINE 公式アカウントマネージャーで作るリッチメニューは、各区画に **「テキストを送信」** しか設定できません。**postback を割り当てられない**ため、「今日」「明日」から1タップで予約に入る導線が作れません。

そこで **Messaging API から登録**します。画像の生成と登録を1つのスクリプトにまとめてあります。

### 手順

パソコンのターミナルで、プロジェクトのフォルダに移動して実行します。

```
cd C:/Users/surij/Documents/line-reservation-bot
python tools/make_richmenu.py
```

チャネルアクセストークンは `src/.env` から読み込みます。実行すると次を行います。

1. 画像（2500×1686）を生成して `tools/richmenu.png` に保存
2. リッチメニューを作成し、画像をアップロード
3. 全ユーザーの既定メニューに設定

`--image` を付けると画像の生成だけを行い、登録はしません。デザインを確認したいときに使います。
`--clean` を付けると、登録前に既存のリッチメニューを削除します。**既定では消しません。**

### 登録される内容

| 位置 | ボタン | 動作 |
|---|---|---|
| 左上 | 今日 | その日の予約フローへ直行 |
| 中上 | 明日 | 翌日の予約フローへ直行 |
| 右上 | 日付を選ぶ | 日付選択から |
| 左下 | 予約の確認 | 変更・キャンセル・登録情報 |
| 中下 | 空き状況 | 部屋を探す |
| 右下 | 使い方 | 操作の案内 |

### 確認すること

LINE のトーク画面を開き直すと、メニューが切り替わります。切り替わらない場合はトークルームを一度閉じるか、アプリを再起動してください。

**「今日」を押して日付選択が飛ばされ、人数の質問から始まれば成功です。**

> **「今日」「明日」は再デプロイが済んでいないと動きません。** 日付を postback に焼き込まず `today` / `tomorrow` の相対指定で送り、受信側で解決しているためです（毎日メニューを作り直さずに済ませるための設計）。解決する処理は STEP 4 でデプロイしたコードに含まれます。

### 文字入力での操作も残してあります

リッチメニューを表示できない環境への保険として、`予約する` `予約の確認` `空き状況` のテキストも同じ操作として解釈します（`予約` `予約確認` `空き` でも認識します）。

## STEP 8. 実データを入力する

シートを開いて、仮の値を実際の値に置き換えます。

### 8-1. 部屋マスタ

現在は仮の名前が入っています。

| 部屋ID | 部屋名（仮） | 定員 |
|---|---|---|
| ROOM01〜04 | 個人ブース1〜4 | 1 |
| ROOM05〜09 | 6人部屋A〜E | 6 |
| ROOM10〜11 | 12人部屋A〜B | 12 |
| ROOM12 | 大会議室 | （空欄＝制限なし） |

**書き換えてよいのは「部屋名」「定員」「表示順」「有効」です。**
**部屋IDは変更しないでください。** 予約データがこの値を参照しているため、変えると既存の予約が部屋を見失います。

部屋を廃止するときは、行を削除せず **「有効」のチェックを外して**ください。

### 8-2. 営業時間

いまは平日 09:00〜18:00、土日は非稼働です。実際に合わせてください。

**時刻は必ず2桁ゼロ埋めで書いてください**（`09:00` は正しく、`9:00` は誤り）。
なお、直接編集した場合はシステムが自動で `09:00` に直します。

### 8-3. 部屋別予約可能時間（定例枠）

**毎週決まった時間に使う会議は、ここで枠をつぶします。**

例）大会議室を毎週火曜10:00-12:00 の定例会議で使う場合、火曜の行を**2行に分けて**登録します。

| 部屋ID | 曜日 | 開始時刻 | 終了時刻 |
|---|---|---|---|
| ROOM12 | 火 | 09:00 | 10:00 |
| ROOM12 | 火 | 12:00 | 18:00 |

**この2行の隙間（10:00-12:00）が予約できない時間になります。**

このシートは「予約**できる**時間帯」を定義します。**時刻を両方空欄にすると、その曜日は終日予約不可**になります。
（「臨時ブロック」シートとは空欄の意味が逆なので注意してください）

### 8-4. 設定シート

| 項目 | 現在値 | 意味 |
|---|---|---|
| 受付締切（分前） | 0 | 開始時刻まで受け付ける。**「締切なし」ではありません** |
| 予約可能日数 | 60 | 60日先まで予約できる |
| 時間の刻み（分） | 30 | 選択肢が30分単位で並ぶ |
| 最短予約時間（分） | 30 | 1件の最短の長さ |
| 人数の初期値 | 6 | 人数選択で強調される値 |
| 管理者通知先メール | ...@... | 障害通知の宛先。カンマ区切りで複数可 |

**項目名は1文字でも変えないでください。** 変えるとその設定は読み込まれず、既定値で動作します。

### 8-5. 入力後の確認

| ファイル | 関数 |
|---|---|
| `selfcheck.gs` | `selfCheck` |

実データを入れたら **`selfCheck`** を実行し、**警告が0件**であることを確認してください。
部屋数や営業時間の想定値がずれると NG が出ますが、実データに合わせた結果であれば問題ありません。

## STEP 10. 管理者への周知

**必ず伝えてください。システムでは防げない事項です。**

### 予約の行を削除しないこと

キャンセルは **「状態」列を `キャンセル` に変える**ことで行います。

行を削除すると、カレンダーイベントIDごと失われ、**共有カレンダー側の予定を二度と削除できなくなります。**
シートは「空き」、カレンダーは「予約済み」という**恒久的な不整合**が残り、システムに回復手段はありません。
週の空き状況を見ている利用者は、存在しない予約のせいで部屋を諦めることになります。

やむを得ず行を削除した場合は、**共有カレンダーからも手動で該当の予定を削除してください。**

### 部屋を付け替えるときは2列とも直すこと

予約シートは部屋名を重複して保持しています。**部屋IDだけを直すと、古い部屋名が表示され続けます。**
（不一致は警告列に出ますが、自動では直りません）

### 警告列を見る習慣

各シートの「警告」列に文字が入っていたら、システムが異常を検出しています。
**入力が拒否されることはありません。** 意図した例外なのか入力ミスなのかは、人が判断してください。

この内容は「はじめに」シートにも書いてあります。

## 付録B. 困ったときの確認場所

| 症状 | 見るところ |
|---|---|
| LINE が反応しない | LINE Developers の「検証」／Apps Script の「実行数」画面 |
| Bot が「受信しました: 〜」と返す | **STEP 4 の再デプロイができていません** |
| 返信と定型文が両方届く | **STEP 6 の応答メッセージがオンのままです** |
| メニューを押すと「メニューから操作を選んでください」 | STEP 7 のテキストが一致していません |
| 予約できる時間が0件になる | 時刻が2桁ゼロ埋めか、`selfCheck` で確認 |
| カレンダーに載らない | STEP 1 が未実行／予約シートの警告列を確認 |
| シートを直接編集しても何も起きない | **STEP 2 が未実行です** |
| 「本日の予約」が常に空 | 日付列が文字列か確認（`repairSheets` で直ります） |

コードの修正が必要な場合は、変更後に **エディタを再読み込み**し、**STEP 4 の再デプロイ**をやり直してください。再デプロイを忘れると、修正が LINE 側に反映されません。
